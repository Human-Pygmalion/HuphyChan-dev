# 151. 실물 IMU 값 검토 — 쿼터니언 순서가 가속도계와 안 맞는다

> **정정 (2026-10-13)**: 원인은 쿼터니언 순서가 아니라 **좌표계 차이**다. EBIMU 데이터시트 (사용자 확인): 자세 (오일러·쿼터니언) 좌표계와 자이로·가속도 좌표계는 X 가 같고 Y·Z 가 반대, 둘 다 오른손 법칙. HUPHY 가 변환 없이 $R^\top(0,0,-1)$ 을 쓰면 중력 x 만 정확히 반대가 된다. 아래 §3 에서 "보낸 순서 그대로 읽으면 맞는다" 는 것은 순서를 바꿔 읽는 것도 중력 x 를 뒤집어 우연히 상쇄된 결과다. 자세한 것은 [sim2real 분석 §4-1c](sim2real/2026-10-13_sim2real_gap_analysis.md).

작성일: 2026-09-20 KST
발단: 사용자 지시 — *"실제 imu 값 검토해봐."*
성격: **읽기만 했습니다.** 모터에 힘을 넣지 않았고 센서 설정도 안 바꿨습니다.

## ELI5 — 한 문장

센서 하나가 두 가지 방법으로 "아래가 어디인지"를 알려주는데, **그 둘이 6.87도 어긋나고
어긋남이 전부 한 축의 부호에서 옵니다.**

---

## 1. 센서는 정상입니다

| | 값 |
|---|---|
| 장치 | `/dev/ebimu -> ttyUSB0` (udev 규칙 살아 있음) |
| 통신 속도 | 115200 |
| 출력 속도 | **100.0 Hz** (20초에 2,000줄, 한 줄도 안 빠짐) |
| 한 줄 구성 | 15개 = 쿼터니언 4 · 각속도 3 · 가속도 3 · 거리 3 · 온도 1 · 시각 1 |
| 가속도 크기 | **1.0000 g** (정지 상태에서 정확) |

정지 상태 측정값 (20초, 2,000 표본):

| 축 | 각속도 [도/초] 평균 | 표준편차 |
|---|--:|--:|
| x | 0.110 | 0.177 |
| y | 0.151 | 0.079 |
| z | 0.416 | 0.027 |

각속도 치우침은 최대 0.42 도/초 = **0.0073 rad/s** 입니다. 학습이 넣는 각속도 잡음
±0.2 rad/s 의 **27분의 1** 이라 문제가 안 됩니다.

## 2. ★ 그런데 "아래 방향"이 두 값에서 다르게 나옵니다

정지한 센서에서는 **가속도계가 중력의 반대 방향**을 가리킵니다. 그래서 쿼터니언에서 푼
중력 방향과 가속도계에서 온 것이 같아야 합니다.

| 축 | 쿼터니언에서 푼 중력방향 | 가속도계에서 온 것(−a) | |
|---|--:|--:|---|
| x | **+0.0588** | **−0.0609** | ★ **부호 반대** |
| y | −0.0695 | −0.0679 | 맞음 |
| z | −0.9958 | −0.9958 | 맞음 |

**두 벡터 사이의 각 = 평균 6.87도 (최대 7.07도).** 잡음이 아닙니다 — 중력 성분의
표준편차가 0.0004~0.001 이라, 6.87도는 그보다 **천 배** 큽니다.

## 3. 원인을 좁혔습니다 — 쿼터니언 네 값의 순서

HUPHY 는 센서가 `(z, y, x, w)` 순으로 보낸다고 보고 뒤집습니다
(`sensors/ebimu/protocol.py:113`). 그런데 **그 순서의 출처가 코드에 안 적혀 있습니다** —
데이터시트 인용도, 확인했다는 기록도 없습니다.

그래서 가능한 24가지 순서 × 켤레 여부를 **전부** 시험해 가속도계와 가장 잘 맞는 것을
찾았습니다.

| 순서 (w,x,y,z 가 원본의 몇 번째) | 켤레 | 가속도계와의 각 |
|---|---|--:|
| **(0, 1, 2, 3)** — 보낸 순서 그대로 | 아니오 | **0.15 도** |
| (0, 1, 2, 3) | 예 | 0.35 도 |
| (0, 2, 1, 3) | 예 | 0.72 도 |
| … | | |
| **(3, 2, 1, 0) — HUPHY 가 쓰는 것** | 아니오 | **6.87 도** |

0.15 도는 "맞다" 는 수준이고 6.87 도는 아닙니다.

### 아직 못 가린 것 (정직하게)

두 가지 설명이 남아 있고, **가만히 있는 센서만으로는 못 가립니다.**

1. **순서가 틀렸다** — 센서는 `(w, x, y, z)` 로 보내는데 `(z, y, x, w)` 로 읽고 있다
2. **가속도계의 x 축이 자세 계산의 x 축과 반대다** — 순서는 맞고 축 규약이 다르다

1번이 훨씬 그럴듯합니다. 자세는 **그 센서 자신의 가속도계와 자이로로** 계산되는데,
제조사가 자기 가속도계와 반대 방향의 x 축으로 자세를 내놓는 것은 이상합니다. 그리고
순서에 대한 근거가 코드에 없습니다.

**가리는 방법**: 로봇을 **x 축 둘레로 손으로 기울이면서** 기록하면 됩니다. 어느 해석의
중력 x 성분이 실제 기울인 방향과 같이 움직이는지 보면 끝납니다. 사람이 있어야 합니다.

## 4. 왜 지금 중요한가

중력 방향은 **정책이 균형을 잡는 데 쓰는 입력**입니다. 학습은 이 값에 ±0.05 의 잡음을
넣는데, 단위벡터 성분 0.05 는 약 **2.9도** 입니다.

**6.87도는 학습이 겪어 본 범위 밖입니다.** 게다가 잡음처럼 흔들리는 것이 아니라
**한쪽으로 치우친 오차**라, 정책은 로봇이 실제로 기울지 않았는데 기울었다고 믿고
계속 한쪽으로 밀게 됩니다.

## 5. 다음

1. **로봇을 x 축 둘레로 기울여 기록** — 두 해석 중 어느 쪽이 맞는지 확정. 사람 필요,
   모터는 안 씀
2. 확정되면 `protocol.py:113` 을 고치고 **출처를 주석에 적는다**. HUPHY 는 우리
   저장소가 아니므로 브랜치에서 작업하고 `docs/128` 장부에 적는다
3. 그 전에는 **정책을 실물에서 돌리지 않는다**
