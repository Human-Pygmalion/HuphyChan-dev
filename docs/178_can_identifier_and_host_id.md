# 178. CAN ID 는 어떻게 동작하나 — "0xFD 를 나누려면 호스트(PC)를 바꿔야 한다", "모터는 이미 모터 ID 로 나뉘어 있다" 판정 (2026-10-19)

> 사용자 질문 (2026-10-19): 0xFD 를 분리하려면 호스트 (CAN 수신자, PC) 를 바꿔야 한다는데? 모터는 이미 모터 ID 로 분리되어 있다는데, 맞나? CAN 프로토콜에서 ID 가 어떻게 동작하는지 조사해서 알려 달라.
> 원문 발췌: [[research_raw/2026-10-19_can_identifier_sources]]. 앞선 기록: [[174_findings_digest_bench_can_2026-10-17]] §3, [[171_can_bus_budget_6motors]].

## 0. 결론

| 주장 | 판정 |
|---|---|
| "모터는 이미 모터 ID 로 분리되어 있다" | **반만 맞다.** PC → 모터 방향 (명령) 은 모터 ID 로 나뉘어 있다. 모터 → PC 방향 (응답) 은 모든 모터가 같은 `0x0FD` 를 쓴다. 이쪽은 나뉘어 있지 않다. 충돌은 이쪽에서 난다. |
| "0xFD 를 나누려면 호스트 (PC) 를 바꿔야 한다" | **틀린 표현이다.** PC 에는 CAN 주소가 없다. 바꾸는 것은 **각 모터 안에 저장된 "Host CAN ID" 설정값** 이다. 모터마다 Command 9 를 보내 서로 다른 값으로 바꾼다. PC 하드웨어나 어댑터는 그대로다. PC 프로그램은 새 응답 번호들을 받아들이게만 고치면 된다. |

## 1. CAN 에서 ID 가 하는 일

1. **ID 는 주소가 아니다.** ID 는 "이 프레임이 무슨 내용인가" 를 나타낸다. 받는 쪽을 가리키지 않는다 (Bosch CAN 2.0 Part A p.6).
2. **모든 노드가 모든 프레임을 받는다.** 각 노드는 ID 를 보고 자기가 쓸 프레임인지 스스로 거른다 (메시지 거르기, message filtering). PC 도 버스의 모든 프레임을 받는다.
3. **ID 는 우선순위다.** 여러 노드가 동시에 보내기 시작하면, ID 를 한 비트씩 비교한다 (비트 단위 중재, bitwise arbitration). 0 (dominant) 이 1 (recessive) 을 이긴다. 그래서 ID 값이 작을수록 먼저 나간다. 진 쪽은 즉시 멈추고 버스가 빌 때 다시 보낸다. 이긴 프레임은 손상되지 않는다 (Part A p.7).
4. **그래서 같은 ID 를 두 노드가 동시에 보내면 안 된다.** 같은 ID 끼리는 중재 구간에서 승부가 안 난다. 둘 다 데이터 구간까지 계속 보낸다. 데이터가 처음 다른 비트에서 1 을 보낸 쪽이 0 을 읽는다. 이는 비트 오류 (BIT ERROR) 다 (Part A p.23). 오류 프레임이 나가고 두 프레임 모두 버려진다. 둘 다 다시 보내고, 또 동시에 시작하면 또 깨진다.
5. 리눅스 CAN 문서도 같은 결론을 쓴다: CAN ID 는 중재에 쓰이므로 버스에서 유일해야 한다. CAN ID 는 사실상 **보내는 쪽의 이름** 처럼 다루는 것이 맞다 (`Documentation/networking/can.rst`).

## 2. RobStride MIT 프로토콜에 대입

| 방향 | 11비트 ID | 누가 보내나 | 지금 값 | 유일한가 |
|---|---|---|---|---|
| 명령 (Command 1 ~ 11, Command 3 = MIT 제어) | 대상 모터 ID | PC 1 대 | 1 ~ 6 (왼다리), 7 ~ 12 (오른다리) | **유일** — 보내는 쪽이 PC 하나뿐이다 |
| 파라미터 읽기 요청 (Command 14) | `0x300` + 모터 ID | PC 1 대 | `0x301` ~ | 유일 |
| 상태 응답 (Response Command 1), Command 14 응답 | **Host CAN ID** | 모터 6 대 | 6 대 모두 `0x0FD` (공장값) | **유일하지 않음** — 보내는 쪽 6 대가 같은 ID 를 쓴다 |

- 응답 안의 Byte0 = 모터 ID 다. 이 값으로 PC 는 누가 보냈는지 **받은 뒤에** 안다. 하지만 중재는 ID 로만 한다. Byte0 는 중재에 쓰이지 않는다. 그래서 Byte0 가 다르다는 것이 충돌을 막지 못한다. 오히려 Byte0 가 다르기 때문에 위 §1-4 의 비트 오류가 난다.
- **언제 충돌하나**: 여러 모터의 응답이 같은 순간에 시작될 때다. CAN 노드는 버스가 빌 때 보내기 시작한다. 몰아 보내기에서는 명령 6 개가 연달아 지나가는 동안 모터들이 응답을 준비한다. 그러면 버스가 비는 순간 여러 모터가 동시에 시작한다.
- **실측과 맞는다**: HUPHY `2fdc139` 개발자 실측 (2026-10-16) 에서 몰아 보내기는 무응답 주기 39 ~ 43 %, 버스 오류 약 1,300 이었다. 하나씩 보내기는 무응답 0 %, 버스 오류 4 였다. 하나씩 보내기는 한 번에 모터 1 대만 응답하므로 동시 시작이 없다.

## 3. "호스트 ID" 라는 이름의 함정

- 매뉴얼은 응답 ID 를 "Host ID" 라고 부른다. 이 이름 때문에 "PC 의 ID" 로 읽기 쉽다.
- 실제로는 **모터가 응답할 때 붙이는 ID** 다. 모터마다 따로 저장된다 (파라미터 `CAN_MASTER`, `0x200A`).
- PC 는 이 값을 갖지 않는다. SocketCAN 은 거르기를 걸지 않으면 모든 ID 를 받는다.
- 따라서 바꾸는 방법은 모터마다 Command 9 를 1 번씩 보내는 것이다.
  - 프레임: ID = 그 모터 ID, 데이터 `FF FF FF FF FF FF <새 Host ID> 01`.
  - 6 번째 바이트 (F_CMD 자리) 에 0xFF 가 아닌 값이 들어간다. 다른 명령으로 바뀌는 자리이므로 보내기 전에 바이트를 확인한다 ([[reference-robstride-fcmd-byte]]).
- 매뉴얼에는 Command 9 가 바로 저장되는지 쓰여 있지 않다. 그래서 Command 9 → Command 12 (저장) → 전원 재투입 → `0x200A` 읽기로 확인한다 ([[174_findings_digest_bench_can_2026-10-17]] §3-1).

## 4. 새 Host ID 를 고를 때 지킬 것

1. **모터 ID 와 겹치면 안 된다.** 예: 모터 1 의 Host ID 를 7 로 하면, 모터 1 의 응답 (ID 7) 을 모터 7 이 자기 명령으로 받는다. 모터 7 이 그 데이터를 MIT 제어 명령으로 해석할 수 있다. 위험하다.
2. **버스의 다른 ID 와도 겹치면 안 된다.** `0x300` 대 (Command 14 요청) 와 다른 장치의 ID 를 피한다.
3. **우선순위를 생각한다.** ID 가 작을수록 먼저 나간다. 응답 ID 를 명령 ID (1 ~ 12) 보다 크게 두면, 명령이 응답보다 먼저 나간다. 지금 `0x0FD` 도 그렇다.
4. Host ID 는 8비트 칸이다 (`F_CMD` 1 바이트). 그래서 0 ~ 255 안에서 고른다. 예: 왼다리 `0xF1` ~ `0xF6`, 오른다리 `0xF7` ~ `0xFC`. 이 예는 제안이며 실측하지 않았다.
5. Command 14 응답도 Host ID 로 오는지 확인해야 한다. 지금은 Host ID = `0x0FD` 인 상태에서만 보았다. 바꾼 뒤에도 같은 Host ID 로 오는지는 실측 전이다.

## 5. Host ID 를 나눠도 남는 것

- **중재 대기는 남는다.** 응답 6 개가 동시에 시작하면 ID 가 작은 것부터 하나씩 나간다. 프레임은 깨지지 않지만 선 위에서는 줄을 선다. 응답 6 개는 6 × 111 ~ 135 µs = 0.67 ~ 0.81 ms 다.
- **모터당 미응답 프레임 한도는 남는다** (2026-09-09 실측 3 개, 2026-10-19 slcan 에서는 4 개도 통과. [[177_slcan_vs_gs_usb_fact_check]] §3-3).
- **PC 프로그램**: HUPHY `biped` (`2fdc139`) 의 모터 코드 (`src/huphy/motors/robstride/*.py`, `canbus.py`) 에는 수신 ID 로 거르는 코드가 없다 (`0x0FD` 상수·소켓 거르기 설정 0 건, 2026-10-19 검색). 응답을 Byte0 (모터 ID) 로 구분한다. 그래서 Host ID 를 바꿔도 수신 코드는 그대로 동작할 것으로 본다. 실측하지 않았다. 몰아 보내기로 돌아가는 것은 별도 결정이다.

## 6. 남은 확인 (실측 필요)

1. 벤치 RS04 1 대로: Command 9 → 응답 ID 변화 확인 → Command 14 응답 ID 확인 → Command 12 → 전원 재투입 → 유지 여부. 모터의 영구 설정을 바꾸는 시험이라 사용자 승인 뒤에 한다.
2. 로봇 6 대 버스에서 Host ID 를 나눈 뒤 몰아 보내기의 무응답·버스 오류를 하나씩 보내기와 비교한다.

## 7. "0xFD 병목은 PC 쪽 USB-CAN 어댑터의 병목이 아닌가" 검토 (2026-10-19)

> 사용자 질문: CAN 통신 구조를 다시 검토하라. 병목인 0xFD 는 PC 에 붙은 USB-CAN 의 병목이 아닌가?
> 근거 자료: HUPHY `biped` `2fdc139` 의 `docs/can_communication.md` (개발자 실측, 2026-10-12 ~ 16), 우리 벤치 실측 ([[177_slcan_vs_gs_usb_fact_check]] §3).

### 7-1. 로봇 통신 구조 (HUPHY 문서 §1)

```
Jetson (커널 5.15.148-tegra)
 ├─ USB ─ EM Tech USB-CAN (STM32F072, candleLight, gs_usb 6.1 백포트) ─ canr ─ 오른다리 모터 7~12
 └─ USB ─ 같은 어댑터                                                ─ canl ─ 왼다리 모터 1~6
```

- 어댑터도 CAN 버스의 노드 1 개다. 어댑터에는 받는 ID 가 따로 없다. 버스의 모든 프레임을 받는다.
- `0x0FD` 는 어댑터의 번호가 아니다. 모터들이 응답에 붙이는 번호다 (§3).

### 7-2. 어댑터 쪽 병목은 실제로 있었다 — 그리고 고쳐졌다

| 순서 | 원인 | 어디 문제 | 상태 |
|---|---|---|---|
| 1 | slcan 펌웨어: 느리고 버스 오류를 숨김 | 어댑터·USB | candleLight 로 교체 (`395952c`, `32b156a`) |
| 2 | 커널 5.15 판 gs_usb 드라이버가 USB 패킷을 어긋나게 읽음. 응답 6 개가 몰려 들어올 때 깨지고 송신이 멈춤 | PC 드라이버 | 커널 6.1 판 백포트로 교체 |
| 3 | 모든 모터가 같은 응답 ID `0x0FD` | **CAN 선 위** | 하나씩 보내기로 회피 (`24ef2a0`). 근본 해결은 안 함 |

- 2 번은 "응답이 몰려 올 때 PC 쪽이 못 받는" 문제였다. 사용자가 말한 어댑터 병목에 해당한다. 이것은 드라이버 교체로 사라졌다.

### 7-3. 3 번 (0xFD) 이 어댑터가 아니라 선 위의 문제인 근거

1. **어댑터만 따로 시험하면 문제가 없다.** 개발자가 통신선을 뺀 어댑터를 루프백 (자기가 보낸 것을 자기가 받음) 으로 시험했다. 초당 5,000 프레임 20,000 개, 그리고 10 ms 마다 6 개 묶음 5,916 개가 모두 돌아왔다. 오류 0 이었다.
2. **잃는 응답이 둘씩 짝으로 빠진다.** 몰아 보내기 696 주기 중 71 주기에서 6 개 중 정확히 2 개가 같이 빠졌다. 1 개만 빠진 주기는 1 번이었다. 두 모터가 같은 ID 로 부딪혀 둘 다 깨지는 모양과 맞는다. 어댑터가 넘쳐서 버리면 뒤쪽 프레임이 몇 개든 빠져야 하고 짝일 이유가 없다.
3. **버스 오류 프레임이 생긴다.** 몰아 보내기 1,367 / 1,314 개, 하나씩 보내기 4 / 4 개 (100 Hz, 5 초). 오류 프레임은 CAN 선 위에서 비트가 어긋날 때 생긴다. 어댑터가 받은 뒤 처리를 못 하면 오류 프레임이 아니라 수신 넘침 (`rx_over`, `missed`) 으로 나타난다.
4. **같은 어댑터·같은 프레임 수에서 보내는 시점만 바꿔도 사라진다.** 하나씩 보내기는 무응답 주기 0 %, 유실 0.2 % 였다.
5. **우리 벤치에서도 어댑터는 연달아 오는 응답을 받는다.** slcan 어댑터에 모터 1 개 응답 4 개가 0.12 ~ 0.35 ms 간격으로 붙어 왔다. 500 회 모두 4 개를 받았다 (응답 ID 는 같지만 한 모터가 차례로 보내므로 동시 시작이 없다).

→ **0xFD 충돌은 어댑터 병목이 아니다.** 두 모터가 같은 ID 로 동시에 보내기 시작해서 선 위에서 깨지는 문제다. 어댑터를 더 좋은 것으로 바꿔도 남는다.

### 7-4. 다만 "지금 주기를 정하는 병목" 은 어댑터 왕복이다 — 사용자 말이 맞는 부분

- 0xFD 충돌을 피하려고 하나씩 보내기를 쓴다. 그러면 한 주기에 모터 수만큼 왕복을 차례로 한다.
- 왕복 1 번 (HUPHY 실측, 왼다리, 토크 0): 중앙값 0.69 ms, 95 % 0.96 ms. 다리 하나 6 모터: 중앙값 4.33 ms, 95 % 5.27 ms.
- 왕복 1 번 중 선 시간은 요청 + 응답 2 프레임 = 0.22 ~ 0.27 ms 다. 나머지 약 0.4 ms 는 USB·드라이버·모터 처리 시간이다. 셋의 비율은 아직 가르지 않았다 (gs_usb 하드웨어 시각표 `candump -H` 로 가를 수 있다).
- 그래서 **지금 주기 상한은 "USB 어댑터 왕복 × 6"** 이다. 응답 ID 를 모터마다 나누면 몰아 보내기로 돌아갈 수 있다. 그러면 이 왕복 비용을 주기당 6 번이 아니라 1 번 정도만 낸다. 개발자 기록의 몰아 보내기 마지막 응답 도착은 약 3.5 ms 였다 (충돌로 8 % 유실된 상태). 응답 ID 를 나눈 뒤의 값은 실측하지 않았다.

## 8. "0xFD 를 병렬화하려면 스레드를 여러 개로 나눠야 한다" 검토 (2026-10-19)

> 사용자 전달 (개발자 의견): 0xFD 를 병렬화하려면 스레드를 여러 개 나눠야 한다. 처음부터 다시 검토하라.
> 근거 코드: HUPHY `biped` `2fdc139` — `src/huphy/robots/biped.py` `_seq_run` (416행~), `src/huphy/robots/leg.py` `_seq_send`/`_seq_wait` (782~792행), `src/huphy/motors/canbus.py` 수신 스레드 `start_reader` (기본 꺼짐, `reader=False`).

### 8-1. 지금 코드가 하는 일 (스레드 1 개)

```
라운드 i (i = 1..6):  왼다리 i 번째 모터에 보냄 → 오른다리 i 번째 모터에 보냄
                      → 왼쪽 응답 기다림 → 오른쪽 응답 기다림 (대개 이미 소켓 버퍼에 와 있음)
```

- 두 다리는 버스가 다르다 (`canl`, `canr`). 그래서 한 스레드로도 두 버스가 **이미 동시에** 일한다. 오른쪽 응답은 왼쪽을 기다리는 동안 커널 소켓 버퍼에 쌓인다. 잃지 않는다.
- 한 라운드 시간 ≈ 두 다리 왕복 중 더 긴 쪽. 6 라운드 ≈ 6 × 0.69 ms ≈ 4.3 ms (개발자 실측: 다리 6 모터 중앙값 4.33 ms, 95 % 5.27 ms).

### 8-2. 스레드를 나누면 무엇이 바뀌나

| 나누는 방법 | 0xFD 충돌 | 주기 | 판정 |
|---|---|---|---|
| **한 버스 안에서 모터마다 스레드** | **다시 생긴다.** 여러 스레드가 거의 동시에 보내면 몰아 보내기와 같다. 모터들이 동시에 응답을 시작해 선 위에서 부딪힌다 | 충돌 재전송으로 오히려 나빠짐. 스레드끼리 잠금으로 줄을 세우면 지금의 하나씩 보내기와 같아짐 | **효과 없음** |
| **다리 (버스) 마다 스레드 1 개** | 그대로 없음 (버스마다 하나씩 보내기 유지) | 중앙값은 거의 같다 (이미 두 버스가 동시에 일함). 이득은 **꼬리** 다: 지금은 라운드마다 두 다리가 서로를 기다린다. 한쪽 모터가 늦거나 무응답이면 (`--drain-ms` 4 ms) 다른 다리도 그만큼 멈춘다. 다리별 스레드면 그 다리만 멈춘다 | 작은 이득. 0xFD 문제를 푸는 것은 아님 |
| **수신 전용 스레드** (`reader=True`) | 그대로 | 받는 지연이 조금 줄 수 있다. 선 위 순서는 안 바뀐다 | 작은 이득 |

- 핵심: **0xFD 충돌은 PC 안의 실행 순서 문제가 아니다.** 모터 둘이 같은 ID 로 같은 순간에 선 위에 올라오는 문제다 (§1-4, §7-3). PC 의 스레드 수는 선 위에서 모터가 응답을 시작하는 시점을 바꾸지 못한다. 오히려 "한 버스에 동시에 여러 명령" 을 만들면 충돌을 부른다.
- 그래서 스레드로 얻는 병렬은 **버스 사이의 병렬** 뿐이다. 그것은 지금도 엇갈려 보내기로 대부분 얻고 있다.

### 8-3. 한 버스 안에서 진짜로 겹쳐 보내는 방법 (스레드와 무관)

| 방법 | 한 다리 통신 시간 (추정) | 근거·한계 |
|---|---|---|
| 지금: 하나씩 보내기 | 4.3 ms (실측 중앙값) | 왕복 0.69 ms × 6 |
| ① Host ID 를 모터마다 나누고 몰아 보내기 | **약 1.5 ~ 2.5 ms (추정, 미실측)** | 선 시간 = 프레임 12 개 × 111 ~ 135 µs = 1.33 ~ 1.62 ms + 어댑터·모터 지연. 우리 벤치에서 모터 1 개에 4 개 몰아 보내기의 마지막 응답 중앙값이 1.28 ms 였다 ([[177_slcan_vs_gs_usb_fact_check]] §3-2). 개발자 기록의 몰아 보내기 마지막 응답은 약 3.5 ms 였으나 이는 충돌·재전송이 섞인 값이다 |
| ② 버스를 늘림 (예: 다리마다 어댑터 2 개, 버스당 모터 3 개) | 약 2.1 ms (= 0.69 × 3, 추정) | 하나씩 보내기 그대로 써도 됨. 어댑터·배선 추가가 필요 |
| ③ 개인 프로토콜 (29 비트) 로 전환 | ①과 비슷 | 응답 ID 에 모터 ID 가 들어 있어 충돌이 없다. 프로토콜 전환 위험·코드 전면 수정 ([[reference-robstride-fcmd-byte]]) — 권하지 않음 |

- ① 에서도 버스마다 스레드는 필요 없다. 한 스레드가 두 버스에 몰아 보내고 두 버스에서 모으면 된다.
- ① 은 실측 전이다. 벤치 RS04 1 대로 Command 9 동작을 먼저 확인하고 (§6-1), 로봇 6 대 버스에서 몰아 보내기를 하나씩 보내기와 비교해야 확정된다.

## 9. "어댑터가 Host ID 로 걸러 차례로 받는 것뿐 아닌가, 어댑터 버퍼가 3 개라 이점이 없지 않나" 검토 (2026-10-19)

> 사용자 질문: USB 어댑터 입장에서는 버퍼에 쌓인 값에서 Host ID 만 걸러 차례로 받는 것 아닌가? 지금 코드와 차이가 없나? 재전송·버퍼 처리만 달라지나? USB-CAN 하드웨어 버퍼가 이미 3 개라 Host ID 를 바꿔도 성능 이점이 없지 않나?
> 근거 코드: candleLight_fw (`System_ID/firmware/candleLight_fw`, `64dc8dc`) `src/can/bxcan.c`, `src/can_common.c`, `src/main.c`, `include/config.h`.

### 9-1. 어댑터는 ID 로 거르지 않는다. 받는 것은 원래 차례대로다

- candleLight 의 기본 수신 거르기: 거르기 뱅크 0, 마스크 방식, 마스크 0 → **모든 ID 를 받는다** (`bxcan.c` `can_init`, 100 ~ 103 행). 전부 하드웨어 수신 FIFO 0 으로 간다.
- CAN 선 위에는 한 번에 한 프레임만 흐른다. 그래서 어댑터와 PC 는 Host ID 를 나누든 안 나누든 **언제나 한 개씩 차례로** 받는다.
- PC 가 어느 모터의 응답인지 아는 방법도 그대로다 (데이터 첫 바이트 = 모터 ID). 걸러 낼 필요가 없다.
- 따라서 Host ID 를 나눠서 달라지는 것은 "받는 방식" 이 아니다. **선 위에서 응답이 살아남는지** 다.

### 9-2. 지금 코드와 무엇이 다른가 — 기다림을 겹치는 것

```
지금 (하나씩, 응답 ID 공용):
  보냄1 ─[왕복 0.69]─ 받음1 · 보냄2 ─[0.69]─ 받음2 · ... · 보냄6 ─[0.69]─ 받음6     ≈ 4.3 ms (실측)

Host ID 를 나눈 뒤 (몰아 보내기):
  보냄1 보냄2 ... 보냄6 ─ 받음(ID 작은 순) 1 2 3 4 5 6                              ≈ 1.5 ~ 2.5 ms (추정)
```

- 왕복 1 번 0.69 ms 중 선 시간은 0.22 ~ 0.27 ms 다. 나머지 약 0.4 ms 는 USB·드라이버·모터 처리의 **고정 대기** 다 (§7-4).
- 지금은 이 고정 대기를 주기마다 **6 번 차례로** 낸다. 몰아 보내기는 6 개의 대기를 **겹쳐서 1 번 정도만** 낸다. 이것이 이득의 전부다.
- 지금 몰아 보내기를 못 쓰는 이유는 응답 ID 가 같아서 겹친 응답이 선 위에서 깨지기 때문이다 (§1-4). Host ID 를 나누면 겹친 응답이 중재로 줄을 서고 깨지지 않는다.
- 재전송은 결과다. 공용 ID 로 몰아 보내면 깨짐 → 오류 프레임 → 재전송이 생긴다 (개발자 실측 버스 오류 약 1,300). ID 를 나누면 이것이 없어진다.

### 9-3. "버퍼 3 개" 는 두 가지가 섞여 있다

| | 무엇 | 크기 | 몰아 보내기에 걸리나 |
|---|---|---|---|
| ① 모터 쪽 | 한 모터에 응답 전 보낼 수 있는 프레임 수 (2026-09-09 라즈베리파이 실측, [[174_findings_digest_bench_can_2026-10-17]] §3-1) | 3 | **안 걸린다.** 몰아 보내기도 모터마다 1 개 (전압 읽기를 더해도 2 개) 만 보낸다 |
| ② 어댑터 하드웨어 수신 FIFO | 로봇 어댑터 STM32F072 의 CAN 제어기 (bxCAN) 수신 FIFO 0. candleLight 는 FIFO 0 만 쓴다 | 3 단 | **실측상 안 걸린다** (아래) |
| ③ 어댑터 펌웨어 대기열 | ②에서 꺼낸 프레임을 USB 로 보내기 전에 쌓는 곳 (`config.h` `CAN_QUEUE_SIZE`) | 64 프레임 | 안 걸린다 |
| ④ PC 드라이버 | gs_usb 수신 요청 30 개, 송신 동시 10 개 ([[177_slcan_vs_gs_usb_fact_check]] §2-1) | 30 / 10 | 안 걸린다 |

- ②의 3 단은 "한 번에 3 개만 받는다" 는 뜻이 아니다. 펌웨어가 꺼내기 전까지 **쌓아 둘 수 있는 수** 다. candleLight 의 주 반복문 (`main.c` 96 행 `while (1)`) 이 돌 때마다 `CAN_ReceiveFrame` 이 FIFO 에서 1 개를 꺼내 ③으로 옮긴다 (`can_common.c` 273 행). 프레임은 선 위에서 최소 111 µs 간격으로 오므로, 3 단이면 펌웨어가 약 0.33 ms 안에 한 번만 돌면 넘치지 않는다.
- ②가 실제로 버티는 근거:
  1. 개발자의 어댑터 루프백 시험: 10 ms 마다 6 개 묶음 5,916 개, 초당 5,000 개 20,000 개가 모두 돌아왔다. 오류 0.
  2. 로봇에서 공용 ID 로 몰아 보낸 696 주기 중 622 주기는 응답 6 개를 모두 받았다. 빠진 주기는 대부분 정확히 2 개씩 빠졌다 (충돌 모양). FIFO 가 넘쳤다면 짝으로 빠질 이유가 없다.
  3. 우리 벤치 (CANable2, STM32G431, 수신 FIFO 3 단): 모터 1 개 응답 4 개가 0.12 ~ 0.35 ms 간격으로 붙어 왔고 500 회 모두 4 개를 받았다.
- 한계: FIFO 가 넘치는 경우는 펌웨어 반복문이 0.33 ms 넘게 멈출 때다 (예: USB 처리 지연). 그러면 수신 넘침 오류로 보인다. 개발자 기록의 오류 프레임은 비트·스터프 오류였고 수신 넘침이 아니었다. Host ID 를 나눈 뒤 F072 어댑터로 몰아 보내기를 한 실측은 아직 없다.
