## 2. slcan → gs_usb (candleLight) — 무엇이 좋아지나

- 지금 어댑터: CANable2, slcan 펌웨어. 2026-09-12 라즈베리파이 실측(`System_ID/FIRMWARE_RUNBOOK.md`): 모터 6개 한 주기 4.07 ms, 12개 6.28 ms. 그중 **응답 기다림 3.9 ms, 응답이 USB 로 1 ms 묶음 간격**으로 들어옴 — 선은 18 % 만 사용. 즉 병목은 선이 아니라 **slcan 의 USB 전달 방식**.
- candleLight(gs_usb): 프레임을 글자로 바꾸지 않고 USB 대량 전송으로 직접 전달, 커널 기본 드라이버, 하드웨어 시각표, 오류 계수 정상 보고, `slcand` 불필요(`ip link set can0 type can bitrate 1000000`). 기대 효과: 응답 대기의 1 ms 눈금이 사라져 한 주기가 **선 시간에 가까워진다** (실측 전이라 수치는 미확인).
- 펌웨어 교체는 BOOT 점퍼를 손으로 잡아야 함 — 준비물·절차는 `System_ID/FIRMWARE_RUNBOOK.md`, 파일은 `System_ID/firmware/`. 2026-09-12 에는 사용자가 원격이라 보류됐던 작업.

### "병렬화"의 정확한 뜻
- CAN 은 **한 줄에 한 번에 한 프레임**만 흐른다. 진짜 동시 전송은 **줄을 늘려야** 한다 (로봇은 이미 왼다리 can0 / 오른다리 can1 두 줄).
- 한 줄 안에서 가능한 것은 **겹치기(파이프라인)**: 6개 명령을 기다림 없이 연달아 보내고, 응답 6개를 한꺼번에 모은다. slcan 에서도 되지만(파이 실측: 모터 둘에 3개씩 동시 → 손실 0 %) USB 1 ms 묶음 때문에 이득이 작고, gs_usb 에서 이득이 크다.
- 제약 ① RobStride 수신 칸이 **모터당 3개** (2026-09-09 실측: 4번째는 버려짐) → 모터당 미응답 프레임 3개 이하. 제어 1 + 읽기 1 이면 여유.
- 제약 ② ★ **모든 모터가 같은 CAN 번호(0xFD)로 응답**한다(데이터 0번 바이트만 모터 번호). 두 모터가 정확히 같은 순간에 응답을 시작하면 표준상 충돌(비트 오류 → 재전송)이 날 수 있다. 명령이 130 µs 간격으로 한 줄로 도착하므로 보통은 저절로 엇갈리지만, 몰아 보낼 때는 **오류 계수(`ip -details -statistics link show can0` 의 bus-errors, 재전송)를 반드시 같이 잴 것**.

## 3. 1 Mbps 한 줄, 모터 6개 — 선 시간 예산

프레임 1개(표준 11비트 번호, 데이터 8바이트) = 111 비트(비트 채움 없음) ~ 135 비트(최악 채움) = **111 ~ 135 µs**.

| 주기마다 모터당 | 프레임/주기 (6개) | 선 시간 | 선 100 % 이론 최대 | **선 70 % (권장 상한)** |
|---|--:|--:|--:|--:|
| A. 제어 + 응답 | 12 | 1.33 ~ 1.62 ms | 617 ~ 751 Hz | **432 ~ 526 Hz** |
| B. A + 파라미터 1개 읽기 (전압 또는 전류) | 24 | 2.66 ~ 3.24 ms | 309 ~ 375 Hz | **216 ~ 263 Hz** |
| C. A + 전압·전류 둘 다 | 36 | 4.00 ~ 4.86 ms | 206 ~ 250 Hz | **144 ~ 175 Hz** |

- 선 70 % 를 상한으로 두는 이유: 재전송·오류 프레임·응답 시각 흔들림의 여유.
- 실제 상한은 선 시간 + 모터 처리 시간 + 어댑터 전달 시간. slcan(파이) 실측은 A 방식 6개에 4.07 ms ≈ **245 Hz** — 선 이론(526 Hz)의 절반. gs_usb 로 이 차이가 얼마나 줄어드는지는 **교체 후 실측**으로만 확정한다.
- 전압·전류를 매 주기 모든 모터에서 읽을 필요는 없다: 예) 제어는 매 주기, 전압은 모터를 돌아가며 한 주기에 한 개 → 프레임 12 + 2 = 14 개/주기, 70 % 에서 약 370 ~ 450 Hz.

## 5. 보충 (2026-10-16, 사용자 질문 후)

- **"모터당 3개" 의 출처**: 우리 코드의 설정이 아니라 2026-09-09 라즈베리파이 실측이다 (`System_ID/rs_direct_socket.py` 주석: 한 모터에 3개 연달아 2,864 회/초 손실 0, 4개 연달아 210 회/초·22 % 손실, 모터 둘에 3개씩 6개는 손실 0). 우리 코드(`exchange()`)는 그 실측을 근거로 4개 이상을 거부할 뿐이다. 모터 둘에 6개를 연달아 보내도 손실이 없었으므로 어댑터의 송신 칸이 원인은 아니다 — **모터 쪽 수신 버퍼(3칸) 가 원인이라는 것은 추정**(STM32 계열 CAN 수신 FIFO 가 3칸인 것과 맞음, 모터 내부는 확인 못 함). 모터는 자기 번호의 프레임만 받으므로 A~F 에 한 개씩 보내는 것은 이 제한과 무관하다.
- **응답 번호 0xFD 의 정체**: 매뉴얼 6.1 — 상태 응답의 11비트 번호는 **호스트 CAN ID**(파라미터 `CAN_MASTER` 0x200A, 기본 253 = 0xFD)이고 모터 번호는 데이터 0번 바이트에 있다. 그래서 **모터 CAN ID 를 바꿔도(Command 7) 응답 번호는 그대로 0xFD** 다. 모터마다 응답 번호를 다르게 하려면 **Command 9 (Modify Host CAN ID)** 로 모터별 호스트 ID 를 따로 줘야 한다: 11비트 번호 = 대상 모터 번호, 데이터 `FF FF FF FF FF FF <새 호스트 ID> 01` (매뉴얼 6.12, p.81). ★ 7번 바이트가 F_CMD 자리이므로 0xFF 가 아닌 값이 들어가는 것이 정상인 명령 — 보내기 전에 바이트를 눈으로 확인. 응답 번호가 낮을수록 충돌 시 우선권이 높다.
- 사용자: candleLight(gs_usb) 펌웨어 어댑터는 이미 준비됨 (2026-10-16 통보).

## 7. 보충 2 (2026-10-16) — 호스트 ID 저장, 버퍼, 주기 밀림

**호스트 ID 가 전원을 꺼도 남나 — 매뉴얼 확인 (RS04 User Manual 260713)**
- 파라미터 표: `0x200A CAN_MASTER` uint8, 읽기/쓰기, 기본 253 ("can host id"). `0x2009 CAN_ID` 바로 옆.
- 4.1.7 private Type 18 (단일 파라미터 쓰기): 제목 그대로 **"lost in power failure"** — 쓰기만 하면 전원을 끄면 사라짐.
- 4.1.9 private Type 22 (저장): "function code 0x20 으로 시작하는 파라미터를 저장" — 0x200A 가 여기에 해당.
- MIT 쪽 대응: Command 15 (파라미터 쓰기, RAM) + **Command 12 (Save motor data, `[모터ID] FF FF FF FF FF FF FF F8`)**, 둘 다 펌웨어 RS04 0.4.1.29 이상.
- Command 9 (Modify Host CAN ID) 자체의 저장 여부는 매뉴얼에 **적혀 있지 않음** (응답 형식만 있음). Command 7(모터 ID)도 MIT 표에는 없고 private Type 7 에 "effective immediately" 만 있음.
- 결론: Command 9 (또는 Command 15 로 0x200A 쓰기) → **Command 12 저장** → 전원 재투입 후 Command 14 로 0x200A 읽어 확인. 저장을 빼면 재투입 때 253 으로 돌아갈 수 있음(미확인이므로 저장을 넣는 쪽이 안전).

**응답 번호가 같으면 모터 버퍼가 낭비되나** — 아니다. 명령은 이미 모터마다 번호가 다르다(1~6). 0xFD 는 **모터 → 호스트 응답**의 번호다. 모터는 자기 번호의 프레임만 받는다(수신 필터; 하드웨어 필터인지 소프트웨어 걸러내기인지는 모터 내부라 미확인 — 모터 둘에 6개 연달아 손실 0 실측은 어느 쪽과도 맞음). 0xFD 공유의 문제는 버퍼가 아니라 **중재**다: 두 모터가 같은 순간 같은 번호로 응답을 시작하면 둘 다 중재에서 이겼다고 판단 → 데이터 구간에서 비트 충돌 → 오류 프레임 → 둘 다 자동 재전송. 호스트 ID 를 다르게 주면 번호가 낮은 쪽이 이기고 진 쪽은 오류 없이 바로 뒤에 보낸다.

**주기가 응답보다 빨라지면 (다음 주기에 이전 응답이 도착)**
- HUPHY 현재 동작: `drain(expect=6)` 은 **프레임 개수**만 센다. 직전 주기의 늦은 응답이 이번 주기 수거에 들어오면 그것도 1개로 세어 6개가 일찍 차고, 그 모터의 이번 응답은 다음 주기로 밀린다 → 한 번 늦으면 한 주기 밀림이 계속 이어질 수 있음 (오류 프레임에 대해 같은 현상을 코드 주석이 이미 적어 둠). 상태 값은 그대로 쓰이고 지연 기록기만 `late` 로 표시.
- 같은 모터에 응답이 오기 전 다음 명령을 계속 보내면 그 모터 앞에 미응답이 쌓임 → 3개를 넘으면 버려짐(§5). 즉 **모터 하나의 왕복 시간 + 그 버스 전체 선 시간 < 주기** 가 상한.
- 개선안: ① 개수 대신 **"이번 송신 이후 도착한 모터별 최신 응답"** 으로 완료 판정(도착 시각 < 송신 시각인 프레임은 late 로만 기록) ② 수신 스레드를 켜고 제어 루프는 기다리지 않고 **모터별 최신 상태**를 씀 — 지연이 0~1 주기로 고정되어, 학습의 관측 지연 무작위화(0~1 정책 주기)와 같은 꼴 ③ 모터별 호스트 ID 로 커널 필터(`CAN_RAW_FILTER`)를 걸어 짝짓기를 번호로 확정.
