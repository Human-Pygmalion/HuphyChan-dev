# 모델의 좌우 이름이 바뀌어 있었다 — 언제부터, 무엇을, 왜 고쳤나

2026-09-12 · 이 문서 하나만 읽으면 됩니다. 앞뒤 사정은 `docs/134`(실물에서 어떻게
드러났나)와 `docs/133`(통신 실측)에 있습니다.

---

## 1. 한 줄로

로봇 모델에서 **`L_` 이 붙은 다리가 물리적으로는 오른다리**였습니다. 프로젝트
**첫날(2026-06-21)부터** 그랬고, **2026-09-12** 에 바로잡았습니다. 시뮬레이터
안에서는 아무 해가 없었고(좌우 대칭이라 이름표만 바뀐 셈), **실물에 연결한 날**
왼 무릎에 오른 무릎 한계가 들어가 안전 클리핑이 무릎을 하드스톱으로 밀었습니다.

## 2. 무엇이 어떻게 틀렸나

    L_hip_pitch_link  pos = (0, **-0.1237**, 0)      <- -y 에 있었음
    R_hip_pitch_link  pos = (0, **+0.1237**, 0)      <- +y

**앞이 +x** 입니다. 기구로 확인했습니다 — 무릎을 60도 굽히면 발이 **-x 로 0.41 m,
+z 로 0.27 m** 움직입니다. 무릎은 뒤로 접히므로 발이 가는 쪽이 뒤, 즉 **+x 가
앞**입니다. z 가 위인 오른손 좌표계에서 **+y 는 왼쪽**입니다. 그러므로 -y 에 있던
`L_` 사슬은 **오른다리**입니다.

이 모델은 좌우가 **미러 부호**입니다 (왼 무릎 `[0,+120]` / 오른 무릎 `[-120,0]`).
그래서 이름이 뒤바뀌면 **부호가 뒤집힌 것과 똑같은 증상**이 납니다. 실제로 실물
무릎이 "세기를 20까지 올려도 0.00도" 로 나타났고, 저는 그것을 한동안 "모터 부호가
모델과 반대" 로 잘못 읽었습니다 (`docs/134` 의 취소선).

## 4. 왜 더 일찍 못 잡았나

세 가지가 겹쳤습니다.

1. **시뮬레이터 안에서는 무해합니다.** 두 다리가 거울상이라, 이름만 바뀐 로봇은
   물리적으로 똑같습니다. 학습은 정상으로 돌았고 지표도 정상이었습니다.
2. **미러 축이 증상을 가렸습니다.** 09-03 부터 좌우 범위가 서로 부호가 반대라,
   이름이 뒤바뀐 것과 부호가 뒤집힌 것이 **같은 모양**으로 보입니다. 저는 실제로
   후자로 잘못 읽었습니다.
3. **경고는 있었는데 끝까지 안 쫓았습니다.** 09-11 에 사용자가 두 번 짚었고
   (위 연표), 브리지 파일은 스스로 `side_mapping_verified: false` 를 달고
   있었습니다. "아직 안 쟀다" 는 표시는 있었지만 재지 않은 채 진행했습니다.

## 5. 오늘 바꾼 것 (2026-09-12)

**이름표와 그 참조만** 바꿨습니다. 위치·질량·관성·축·범위는 **한 글자도 안
건드렸습니다.**

| 무엇 | 어디 | 왜 |
|---|---|---|
| 모델 **67개** 파일의 `L_` ↔ `R_` 맞바꿈 | mjlab 자산 29개 · `assets/pygmalion_v2` 의 xml 19개·urdf 19개 | 이름이 물리와 맞게 |
| 바꾼 도구 | `tools/robot_model/swap_leg_names.py` (새로 만듦) | 되풀이 가능하게, 그리고 **전후 물리가 같은지 확인**까지 |
| 학습 기본자세의 좌우 값 두 쌍 맞바꿈 | `pygmalion_constants.py` 의 `L/R_hip_yaw_joint` (±0.165, ±0.113) | 이름이 바뀌었으니 값도 같이 바꿔야 **자세가 그대로** |
| 우리 한계 파일 다시 씀 | `System_ID/mjcf_limits.json`, `System_ID/sim_joint_conv.json` | 왼다리에 왼다리 한계가 가도록 |
| 검사 하네스 한계·기대값 | `tools/huphy_audit/e2e_live.py` (E24·E36·E37) | 무릎의 막힌 끝이 반대쪽이 됨 |

| 재발 방지 | `tools/robot_model/build_robot.py` 에 `assert_left_is_plus_y()` | 빌더가 다시 -y 에 왼다리를 놓으면 **파일을 못 쓰고 멈춤** |

**확인한 것**

* MuJoCo 로 전후를 불러 **바디 번호별 위치·질량·관성, 관절 번호별 축·범위·위치,
  geom 위치·크기** 가 전부 같음을 확인했습니다. 바뀐 것은 관절 이름 12개뿐입니다.
* 29개 모델 전부 다시 열리고, 전부 **왼다리가 +y** 입니다.
* 학습 쪽 사전 점검(`preflight_action_window.py`)이 **PASS** — 12관절 모두 명령
  가능하고, 기본자세 값은 이름만 좌우가 바뀐 채 크기가 같습니다
  (왼 무릎 −38.39도 / 오른 무릎 +38.39도).
* 실물 경로 전 구간 검사 62개: **지킴 59 · 주의 3 · 구멍 0.**

## 6. 안 바꾼 것 · 남은 것

| 무엇 | 왜 안 바꿨나 |
|---|---|
| **STL 파일 이름** | `<mesh name="L_thigh" file="R_thigh.stl">` 처럼 어긋나 보입니다. **자산 이름(name)이 기준**이고 파일 글자는 뜻이 없습니다. 파일까지 바꾸려면 메시 내보내기 단계를 같이 고쳐야 해서 오늘은 "이름 할당만" 으로 멈췄습니다 |
| **빌더의 좌우 배정 자체** | `sign = -1.0 if s == 'L'` 세 군데 + 크랭크 축 예외 두 군데 + ±15도 한 군데를 함께 뒤집어야 하고, 마지막이 메시 선택이라 위와 같은 이유로 미룸. 대신 **쓰기 직전 확인**을 넣어 조용한 재발을 막았습니다 |
| 옛 계통 `pygmalion_v1.xml`, `_scene_tmp.xml` | 다리가 y 가 아니라 **x 로 갈라지는 다른 좌표 규약**입니다. 손대면 오히려 틀어집니다. 되돌려 놨습니다 |
| 학습 다시 하기 | **필요 없습니다.** 관절 순서(모델 순서)와 물리가 그대로라, 이미 학습된 정책은 같은 관절을 같은 순서로 움직입니다. 바뀐 것은 사람이 읽는 이름뿐입니다 |
| 모터의 `sign`·`offset` 실측 | 아직입니다. 실측 단서는 있습니다 — 왼 무릎은 raw **+9.70도**가 하드스톱(곧게 폄)이라 `offset ≈ -9.70`, 오른 무릎은 raw ≈0 이라 `offset ≈ 0`. 정식으로는 `huphy-commission --limb <다리> sweep` 으로 사람이 끝에서 끝까지 움직여 재야 합니다 |
| **1~6번 모터가 왼다리라는 가정** | 이것도 아직 안 쟀습니다. 이번 일의 교훈이 그대로 적용됩니다 — **안 잰 가정은 표시해 두고, 실물에 닿기 전에 재야 합니다** |

## 7. 되돌리는 법

    python3 tools/robot_model/swap_leg_names.py --apply <파일...>

같은 도구를 한 번 더 돌리면 원래대로 돌아옵니다 (맞바꿈은 두 번 하면 제자리).
단, 머리말 주석이 있으면 건너뛰므로 먼저 그 주석을 지워야 합니다. 파이의 HUPHY
설정은 `config/calibration/*.json.bak_sidefix` 에 이전 파일이 있습니다.
