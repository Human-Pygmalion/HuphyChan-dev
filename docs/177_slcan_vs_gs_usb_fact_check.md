# 177. "gs_usb 는 slcan 보다 병렬화가 된다" — 사실 확인 (문헌 + RS04 실측, 2026-10-19)

> 사용자 질문 (2026-10-19): 이전에 gs_usb 를 쓰면 slcan 보다 병렬화가 가능하다고 들었다. 사실인가? 문헌 조사부터 하라.
> 원문 발췌 노트: [[research_raw/2026-10-19_slcan_vs_gs_usb_sources]] (출처 18 개, 판정표 19 행).
> 실측 결과 파일: `System_ID/can_link/results/probe_can0_slcan_rs04_{noparam,vbus}_20261019.json`, `burst_can0_slcan_rs04_20261019.json`.

## 0. 용어

| 용어 | 뜻 |
|---|---|
| slcan | CAN 프레임을 글자 (ASCII) 로 바꾸어 USB 직렬 포트로 보내는 방식. 리눅스 드라이버 `slcan`, 연결 프로그램 `slcand` 가 필요하다 |
| gs_usb | CAN 프레임을 이진 구조 그대로 USB 벌크 전송 (bulk transfer) 으로 보내는 방식. 리눅스 기본 드라이버. 어댑터 쪽 펌웨어는 candleLight |
| URB | USB Request Block. 리눅스가 USB 장치에 넘기는 전송 요청 1 개 |
| 왕복 시간 | 명령을 보내기 직전부터 그 응답을 커널이 받은 시각까지의 시간 |
| 몰아 보내기 | 여러 프레임을 응답을 기다리지 않고 연달아 보내는 것 (파이프라인, pipelining) |

## 1. 결론

**부분적으로만 맞다.**

- **맞는 부분**: gs_usb 는 컴퓨터와 어댑터 사이에서 프레임 여러 개를 동시에 넘긴다. 채널당 송신 URB 는 최대 10 개, 수신 URB 는 30 개다. slcan 드라이버는 프레임 1 개를 보낼 때마다 송신 대기열을 멈춘다. USB 전송이 끝난 뒤에야 다음 프레임을 받는다.
- **틀린 부분**: CAN 선 위에서는 어떤 어댑터로도 병렬이 안 된다. CAN 은 한 번에 프레임 1 개만 흐르는 직렬 버스다. 1 Mbit/s 에서 8 바이트 표준 프레임 1 개는 111 ~ 135 µs 다.
- **어댑터로 안 바뀌는 것**: ① 모든 모터 응답이 같은 CAN 번호 `0xFD` 를 쓰는 충돌 문제 ([[171_can_bus_budget_6motors]] §3). ② 모터 쪽 수신 칸 한도. ③ 선 시간.
- **오늘 실측 (3090, slcan)**: 응답이 1 ms 묶음으로 오지 않았다. 4 개를 몰아 보내면 마지막 응답 중앙값이 1.28 ms 다. 이는 선 시간 (프레임 8 개 = 0.89 ~ 1.08 ms) 에 가깝다. 그래서 이 기계에서는 gs_usb 로 바꿔도 **중앙값 이득은 작다**. 남은 문제는 꼬리 지연 (99 백분위수 3.7 ~ 5.7 ms) 이다. gs_usb 가 꼬리를 줄이는지는 gs_usb 어댑터로 같은 시험을 해야 안다.

## 2. 문헌 근거 (1 차 출처는 직접 확인)

| 주장 | 판정 | 출처 |
|---|---|---|
| gs_usb 송신 URB 최대 10 개, 수신 URB 30 개 | 참 | 리눅스 `drivers/net/can/usb/gs_usb.c` `#define GS_MAX_TX_URBS 10`, `GS_MAX_RX_URBS 30` (2026-10-19 master 직접 확인) |
| slcan 은 프레임마다 송신 대기열을 멈춘다 | 참 | 리눅스 `drivers/net/can/slcan/slcan-core.c` `slcan_xmit()` 의 `netif_stop_queue`, 쓰기 완료 후 `netif_wake_queue` (직접 확인) |
| slcan 에는 송신 에코·하드웨어 시각표·오류 계수 보고가 없다 | 참 (드라이버 기준) | 같은 파일. canable2 slcan 펌웨어 소스에서도 오류 프레임 송출 코드를 찾지 못했다 (조사 노트 S6) |
| gs_usb 는 1 µs 하드웨어 시각표·오류 보고·다채널을 지원한다 | 참 (펌웨어가 기능을 알릴 때) | `gs_usb.c` |
| candleLight 는 USB 패킷 1 개에 CAN 프레임 여러 개를 묶어 보낸다 | **거짓 (메인라인)** | `System_ID/firmware/candleLight_fw/src/usbd_gs_can.c` `USBD_GS_CAN_SendFrame()` 는 프레임 1 개를 전송 1 개로 보낸다 (직접 확인). 장치 대기열은 채널당 64 프레임 (`include/config.h` `CAN_QUEUE_SIZE`). 묶음 전송은 Elmue 의 별도 확장 프로토콜뿐이다 |
| 메인라인 candleLight 가 CANable 2.0 (STM32G431) 에서 돈다 | **거짓** | candleLight_fw README: "STM32G431-based devices (e.g. CANable-MKS 2.0) are not supported by this project yet." (직접 확인) |
| USB 풀스피드 프레임은 1 ms 이고 벌크 전송은 지연 보장이 없다 | 참 | Infineon AN57294 (조사 노트 S9) |
| slcan 과 gs_usb 의 왕복 시간을 직접 비교한 측정 | **찾지 못함** | 논문 (Sojka·Píša 2011 은 USB 어댑터 미포함), linux-can, ODrive, mjbots, RobStride 포럼 모두 없음. 유일한 단서는 CANine 블로그 (slcan 1.5 ~ 2.0 ms, gs_usb 아닌 자체 펌웨어 1 ms, 방법 미공개) |
| gs_usb 로 바꾸면 같은 번호 응답 충돌이 없어진다 | **거짓** | 충돌은 CAN 중재 단계의 문제다. 리눅스 CAN 문서: CAN 번호는 버스에서 유일해야 한다 |

## 3. 실측 — RS04 1 개, 3090 가상 머신, CANable2 slcan, 1 Mbit/s (2026-10-19 11:10 ~ 11:25)

- 모터는 토크 꺼짐 상태 (Reset) 였다. 힘 0 MIT 프레임과 Command 14 읽기만 보냈다.
- 도구는 `System_ID/can_link/bus_probe.py` 와 `burst_timing.py` 다.

### 3-1. 주기 시험 (`bus_probe.py`, 각 5 s)

| 방식 | 주기 목표 | 이룬 주기 | 제때 응답 | 손실 | 왕복 중앙값 / 99 % / 최대 |
|---|---|---|---|---|---|
| 하나씩 보내기, 제어만 | 200 Hz | 199.0 Hz | 100 % | 0 % | 0.53 / 3.73 / 4.73 ms |
| 하나씩 보내기, 제어만 | 1000 Hz | 845.6 Hz | 100 % | 0 % | 0.48 / 3.79 / 3.99 ms |
| 몰아 보내기, 제어만 | 1000 Hz | 932.4 Hz | 89.6 % | 0 % | 0.48 / 3.78 / 7.07 ms |
| 하나씩 보내기, 제어 + VBUS | 200 Hz | 194.0 Hz | 100 % | 0 % | 0.54 / 3.88 / 5.50 ms |
| 하나씩 보내기, 제어 + VBUS | 500 Hz | 422.6 Hz | 100 % | 0 % | 0.48 / 3.82 / 9.41 ms |
| 몰아 보내기, 제어 + VBUS | 500 Hz | 489.8 Hz | 92.7 % | 0 % | 0.58 / 3.80 / 5.89 ms |

- 모든 시험에서 손실 0, 커널 버스 오류 0, 오류 프레임 0 이다.
- "제때 응답" 이 100 % 아래인 것은 응답이 다음 주기 송신 뒤에 온 경우다 (늦은 응답). 손실은 아니다.

### 3-2. 몰아 보낸 응답이 언제 오나 (`burst_timing.py`, 50 Hz, k 개씩 500 회)

k 개 = 힘 0 MIT 프레임 1 개 + Command 14 읽기 (k − 1) 개를 연달아 보낸다.

| k | 응답 수 / 보낸 수 | j 번째 응답 도착 중앙값 (ms) | 응답 사이 간격 중앙값 (ms) | 첫 응답이 1 ms 넘게 걸린 비율 |
|---|---|---|---|---|
| 1 | 500 회 모두 1 / 1 | 0.56 | — | 18.8 % |
| 2 | 500 회 모두 2 / 2 | 0.57, 0.79 | 0.23 | 23.2 % |
| 3 | 500 회 모두 3 / 3 | 0.56, 0.90, 1.03 | 0.35, 0.12 | 19.4 % |
| 4 | 500 회 모두 4 / 4 | 0.57, 0.89, 1.05, 1.28 | 0.32, 0.12, 0.24 | 17.6 % |

- 응답 사이 간격은 0.1 ~ 0.35 ms 에 몰린다. 선 시간 규모다. 1 ms 묶음 무늬는 없다.
- 간격 0.0 ~ 0.1 ms 칸도 20 ~ 30 % 있다. 응답 2 개가 USB 전송 1 번에 함께 온 경우로 본다 (slcan 글자 프레임 약 22 바이트, USB 패킷 64 바이트).
- 꼬리: 첫 응답의 약 18 ~ 23 % 가 1 ms 를 넘는다. 99 백분위수는 3.9 ms 다. 원인은 이 시험으로 가르지 못했다 (가상 머신 USB 전달, slcand 일정, 모터 처리 중 어느 것인지 미확인).

### 3-3. 이 실측이 바꾸는 이전 기록

- **모터 수신 칸 3 개 한도**: 오늘 4 개를 몰아 보내도 500 회 모두 4 개가 돌아왔다. 2026-09-09 실측 ("4 번째는 버려짐") 과 다르다. slcan 은 프레임을 1 개씩 내보내므로 선 위에서 프레임 사이가 벌어진다. 그 사이 모터가 앞 프레임을 처리했을 수 있다. 따라서 3 개 한도는 **프레임이 선에 붙어서 들어올 때** 의 값으로 본다. gs_usb 는 프레임을 더 촘촘히 내보낼 수 있으므로 이 한도에 더 쉽게 닿을 수 있다. 미확인이다.
- **"1 ms 묶음"**: 2026-09-12 라즈베리파이 실측의 무늬다. 오늘 3090 (x86) 에서는 보이지 않았다. 라즈베리파이 USB 제어기 탓일 수 있다. 가설이며 검증하지 않았다.
- **"선은 18 % 만 사용"** (`System_ID/FIRMWARE_RUNBOOK.md`, [[171_can_bus_budget_6motors]] §2): 데이터 바이트만 센 값으로 보인다. 12 프레임 × 64 비트 / 4.07 ms = 19 % 다. 프레임 전체 (111 ~ 135 비트) 로 세면 12 × 111 ~ 135 µs / 4.07 ms = **33 ~ 40 %** 다.

## 4. 어댑터 사정

| 어댑터 | 칩 | 지금 펌웨어 | 메인라인 candleLight |
|---|---|---|---|
| 벤치 (3090, `can0`) | CANable2, STM32G431 | slcan (`normaldotcom/canable2`, b158aa7) | 지원 안 함 |
| 로봇 (2026-09 기록, `Protofusion_Labs_CANable_9fddea4`) | CANable 1, STM32F042C6 | slcan (`canable-fw`) 였다 | 지원 (`canable_fw` 대상) |

- 사용자는 candleLight 어댑터를 따로 준비했다 (2026-10-16 통보). 그 어댑터의 칩과 펌웨어 판은 아직 확인하지 않았다.

## 5. 남은 일

1. candleLight 어댑터를 3090 벤치에 꽂고 같은 두 도구를 그대로 돌린다. 같은 RS04 로 slcan 과 비교한다.
   ```
   python3 bus_probe.py --channel <gs채널> --ids 4 --model RS04 --mode both --rates 100,200,300,500,1000 --duration 5 --param none
   python3 burst_timing.py --channel <gs채널> --id 4 --model RS04 --kmax 4 --reps 500 --rate 50
   ```
   gs_usb 는 `candump -H` 로 어댑터 하드웨어 시각표도 볼 수 있다. 이것으로 꼬리 지연이 USB 쪽인지 모터 쪽인지 가른다.
2. 모터 6 개 버스에서 몰아 보내기를 쓰려면 먼저 호스트 ID 를 모터마다 나눠야 한다 ([[174_findings_digest_bench_can_2026-10-17]] §3). 어댑터 교체는 이 문제를 풀지 않는다.
