# 모터 12개가 통신에 전혀 응답하지 않는다 (2026-09-14) — **2026-09-15 해결**

> SPEC-TABLES: 해당 없음 — 실물 통신 점검 기록이다.

## §0 ★ 해결 (2026-09-15) — **48 V 전원이었고, 어댑터 번호도 바뀌어 있었다**

사용자가 전원을 넣은 뒤 다시 확인했습니다. **12개 전부 응답합니다.**

```
left_leg  can0  hip_pitch id=1 응답 · hip_roll id=2 응답 · hip_yaw id=3 응답
                knee id=4 응답 · ankle_a id=5 응답 · ankle_b id=6 응답   전부 응답함.
right_leg can1  hip_pitch id=7 응답 · … · ankle_b id=12 응답            전부 응답함.
```

실제 각도·토크·온도도 들어옵니다 (관찰 모드라 토크는 전부 0.03 N·m 이하):

```
left_leg/hip_pitch  +1.15도  -0.03 N·m  30도   right_leg/hip_pitch  -4.10도  -0.03 N·m  29도
left_leg/knee       +7.53도  -0.03 N·m  28도   right_leg/hip_yaw   +15.40도  -0.01 N·m  27도
지연 28~34 ms
```

**버스 배정도 확인됐습니다** — 모터 1~6 이 `can0`, 7~12 가 `can1` 에서 답했습니다.
설정(`left_leg: can0`)과 일치합니다.

### §0-1 전원 말고도 걸려 있던 것 셋

| # | 무엇 | 어떻게 됐나 |
|---|---|---|
| 1 | **전원을 넣자 어댑터 번호가 바뀜** — `ttyACM0/1` → **`ttyACM2/3`**. `can_up.sh` 가 번호를 박아 둬서 "어댑터가 안 꽂혔습니다" 로 멎음 | **일련번호(`/dev/serial/by-id`)로 찾도록 고쳐** 로봇에 배포. 카메라 프로그램이 같은 이유로 이미 by-id 를 쓰고 있었음 |
| 2 | **지운 도구의 프로세스가 아직 떠 있었음** — 2026-09-14 에 `live_monitor.py` 를 파일만 지우고 프로세스를 안 죽여, 텔레메트리 포트(9871)를 붙잡고 꾸러미를 가로채고 있었음 | 종료. **지울 때 도는 것도 같이 죽일 것** |
| 3 | **3차원 뷰어가 읽는 꾸러미 모양이 달랐음** — 뷰어(`bridge/huphy_udp.py` `parse_fast`)는 `left_leg/hip_pitch/pos` 같은 **납작한 열쇠 세 토막**만 읽는데, 관찰 모드는 `{"motors": {...}}` 로 보내고 있었음. **한 줄도 안 읽히고 조용히 버려짐** | `StateSender` 가 같은 값을 **두 모양으로** 보내게 고침. 실제 꾸러미를 파서에 먹여 관절 12개가 나오는 것 확인 |

### §0-2 아직 안 된 것 — 3차원에 실제로 비추기

`huphy_viser` 는 받은 값을 **"실물 채널"에만** 넣고 시뮬 관절로 옮기지 않습니다. 그 일을
하는 것은 정식 뷰어의 **`real_replay` 모드**이고(`modes.py:20` — *"received q drives the
sim joints kinematically"*), 넣어 주는 도구도 이미 있습니다(`bridge/huphy_udp_forward.py`).
정식 뷰어 + 전달기 + `real_replay` 로 물리면 됩니다. 아직 안 했습니다.

## §1 증상

두 통신선 모두 **보내기만 되고 받는 것이 0** 이다.

```
can0   TX 59,514 프레임   RX 0   오류 0   arbit-lost 0   bus-off 0
can1   TX 44,106 프레임   RX 0   오류 0   arbit-lost 0   bus-off 0
```

HUPHY 자체 점검(`huphy.scripts.commission ... scan`)도 같다. 관찰 루프를 끄고 단독으로
돌렸으므로 **두 프로그램이 서로 응답을 가로챈 것이 아니다.**

```
left_leg  can0  응답 없음: hip_pitch hip_roll hip_yaw knee ankle_a ankle_b
right_leg can1  응답 없음: hip_pitch hip_roll hip_yaw knee ankle_a ankle_b
```

## §2 여기까지는 정상이다

| 무엇 | 상태 |
|---|---|
| 어댑터 두 개 | `/dev/ttyACM0`, `/dev/ttyACM1` 둘 다 있음 |
| 통신선 올리기 | `can_up.sh` 성공, 초당 100만 비트, can0·can1 UP |
| 관찰 모드 | 초당 20.0회로 정확히 돌고, 20초에 783번 읽음 |
| 텔레메트리 | 12개 모터가 다 실려 나감. **한계값도 정확** |
| 한계값 대조 | 로봇 설정과 최종 MJCF 가 **여유 3도만큼만** 다름 (예: 왼 무릎 로봇 −117~−3 / 모형 −120~0) |

즉 **소프트웨어 경로는 끝까지 살아 있다.** 각도·토크·온도가 전부 0인 것은 모터가
답을 안 하기 때문이다.

## §3 원인 후보 (확인 순서)

1. **48 V 전원이 안 들어와 있다.** 가장 유력하고 가장 싸게 확인된다.
2. 모터 쪽 통신선 커넥터 또는 종단저항.
3. **통신 프로토콜이 바뀌어 있다.** RobStride 명령의 `data[6]` 자리에 `0xFD` 가
   들어가면 끄기가 아니라 **통신 프로토콜 변경**이고 **전원을 다시 넣을 때 적용**된다
   ([[reference-robstride-fcmd-byte]]). 이것이 걸려 있으면 지금 프로토콜로는 영영
   대답하지 않는다. 전원이 확실한데도 응답이 0이면 이쪽을 봐야 한다.

**오류 계수가 전부 0인 것을 근거로 1번을 배제하면 안 된다** — 이 어댑터(CANable,
글자 방식 slcan)가 무응답을 커널 오류 계수로 올려 주는지 확인하지 않았다.
