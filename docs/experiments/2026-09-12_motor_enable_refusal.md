# 2026-09-12 · 열두 모터 중 일곱이 "힘 켜기"를 거부합니다 — 펌웨어가 두 갈래입니다

> 한 줄: **켜지는 다섯은 파라미터 읽기에 답하고, 안 켜지는 일곱은 답하지 않습니다.**
> 두 증상이 정확히 같은 5 대 7 로 갈립니다. 우리 명령 문제도, 전원 문제도 아닙니다.

## 무엇이 보였나

화면에서 "전부 0도로" 를 눌렀을 때 열둘 중 **다섯만** 힘이 들어갔습니다. 누를 때마다
**같은 일곱 개**가 안 켜졌습니다.

| | 모터 번호 | 모델 |
|---|---|---|
| 켜짐 | 1, 2, 4, 7, 10 | 전부 **RS04** |
| 안 켜짐 | 3, 5, 6, 9, 11, 12 | 전부 **RS03** |
| 안 켜짐 | 8 | **RS04** (RS04 중 유일) |

즉 **RS03 여섯 개 전부 + RS04 한 개(8번)** 입니다.

## 어떻게 갈랐나

### 1. 제 코드가 "켰다고 믿기만" 하던 것 — 이건 진짜 결함이었고 고쳤습니다

가드가 켜기 프레임을 **한 번 보내고 끝**이었습니다. 그 한 장이 흘려지거나 모터가
거부해도 아무도 몰랐고, 가드는 열둘 전부 "힘 켜짐" 이라고 **믿은 채** 꺼진 모터에
계속 명령을 보냈습니다.

이제 **모터가 보고하는 동작 상태를 보고 맞춥니다** — 켜졌다고 믿는데 모터가 꺼졌다고
하면 0.4초마다 다시 켭니다. 고친 뒤 `reenabled` 가 **154회**로 올라갔습니다. 즉 다시
켜기는 제대로 나가고 있고, **그래도 안 켜집니다.**

### 2. 고장 표시 — 없음

`can_probe.py` (고장값 조회, `ff ff ff ff ff ff 00 fb`) 로 열둘 전부 물었습니다.
**열두 개 모두 "고장 없음"** 입니다. 고장 클리어(`ff ... ff fb`)를 보낸 뒤 켜기를
보내도 그대로였습니다.

### 3. 한 개만 떼어 놓고 바이트를 봤습니다

`System_ID/enable_probe.py` 로 3번(RS03)과 4번(RS04)을 같은 순서로 다뤘습니다.

```
3번 (RS03)
  켜기 FF..FC     03 80 3d 80 a7 ff 01 22   mode=0 꺼짐
  켠 뒤 1..6      ...                       mode=0 꺼짐  (6/6 꺼짐)

4번 (RS04)
  켜기 FF..FC     04 81 1f 80 27 ff 81 2c   mode=2 켜짐
  켠 뒤 1..6      ...                       mode=2 켜짐  (6/6 켜짐)
```

일곱 번째 바이트가 갈립니다 — 4번은 켜자마자 `01` → **`81`** 로 바뀌고(위 두 비트가
동작 상태), 3번은 **끝까지 `01`** 입니다. 즉 3번은 켜기를 받고도 들어가지 않습니다.

같은 방법으로 5번(RS03)·8번(RS04)은 **0/5**, 7번(RS04)은 **5/5** 였습니다.

### 4. 결정적: 로봇 프로그램도 못 켭니다

`huphy-test --limb left_leg zero` 를 그대로 돌린 뒤 상태를 읽었습니다.

| 모터 | 결과 |
|---|---|
| 1, 2, 4 (RS04) | 힘 켜짐 |
| 3, 5, 6 (RS03) | **힘 꺼짐** |

HUPHY 가 보내는 켜기 프레임은 제 것과 **바이트까지 같습니다**
(`data[0:6]=0xFF, data[6]=0xFF, data[7]=0xFC` — `motors/robstride/bus.py:178`).
그러므로 **보내는 쪽의 문제가 아닙니다.**

## 추가로 더 가른 것 (2026-09-12 늦게)

### 고장 비트 — 원시 바이트로 다시 확인, 진짜로 전부 0

우리 `can_probe.py` 의 고장 비트 표가 HUPHY 표와 일부 다릅니다(5·6·7번 자리). 그래서
해석을 빼고 **응답 바이트를 그대로** 찍어 봤습니다.

```
  1  ID 0x000000FD  01 00 00 00 00 00 00 00  word=0x00000000
  ...
 12  ID 0x000000FD  0c 00 00 00 00 00 00 00  word=0x00000000
```

첫 바이트가 모터 번호이고 나머지가 전부 0 입니다. **열두 개 다 고장 비트가 하나도
안 섰습니다.** 저전압(비트 2)도 안 섰습니다. 다만 이것이 "전원이 정상" 이라는 뜻은
아닙니다 — 구동 전원이 **아예 없으면** 모터가 시도조차 안 해서 저전압 표시를 안 세울
수 있습니다.

### 제어모드 — MIT 로 맞춰도 안 켜짐

HUPHY 의 커미셔닝이 쓰는 것과 같은 명령(`0xFC` + F_CMD=0, 제어모드를 MIT 로)을 3번에
걸고 켜 봤습니다. **0/5.** 모드 문제가 아닙니다.

### 온도는 열두 개가 전부, 각자, 살아서 옵니다

사용자 질문: *"온도 리포트는 하나씩 다 오는지 검토해봐. 만약 된다면, 제어명령 넣는
쪽이나 모터 폴트 문제 아닌가?"*

여섯 번 연속 읽었습니다. **열두 개 전부 6/6 응답**이고 값이 서로 다릅니다(28~31도).
그러므로 열두 개 모두 **살아서 개별로 말하고 있습니다.**

### ★★ 결정적: 켜지는 다섯과 안 켜지는 일곱이 **다른 명령 집합**을 씁니다

파라미터 읽기(선택자 명령, HUPHY `tables.py:205-221` 이 매뉴얼 6.13~6.18절 인용)를
열두 개에 걸어 봤습니다.

| 번호 | 상태 프레임 | 파라미터 읽기 | 힘 켜기 |
|---:|---|---|---|
| 1, 2, 4, 7, 10 | 답함 | **답함** (run_mode 0, 프로토콜 0) | **켜짐** |
| 3, 5, 6, 8, 9, 11, 12 | 답함 | **무응답** | **안 켜짐** |

**두 증상이 정확히 같은 5 대 7 로 갈립니다.** 우연이 아닙니다.

HUPHY 표에 이유가 적혀 있습니다 — `tables.py:223-232`:

> `PARAM_CMD_FIRMWARE` … 선택자 명령을 쓰려면 이 펌웨어 이상이어야 함.
> **구형이면 응답이 없음.**

즉 **일곱 개는 다섯 개와 다른(더 오래된) 펌웨어**를 쓰고 있습니다.

29비트 확장 프레임(PRIVATE 프로토콜)으로도 걸어 봤는데 **열두 개 전부 무응답**입니다.
그러므로 프로토콜이 갈린 것은 아니고, 열두 개 다 MIT 로 말합니다.

### 세 번째 구현으로도 같은 결과 — 원본 `leg_control` 코드

사용자 지적: *"애초에 HUPHY 레포 코드에서 양다리 움직이는 걸 테스트했었고, 12개 모터 다
움직이는 걸 봤었어. 그때 테스트 코드 찾아봐."*

찾았습니다. `leg_control/` 이 `src/huphy` 로 정리되기 전의 **원본 코드**입니다
(`single_leg_controller.py`, `move_motor10.py`, `robot_constant.py`). 켜는 자리는
`single_leg_controller.py:349 enable()` → `:1187 _send_cmd_ff()` 이고, 만드는 바이트는

```python
data = [0xFF] * 8
data[7] = int(cmd)          # cmd = CAN_CMD_ENABLE = 0xFC
```

**우리 것·`src/huphy` 것과 완전히 같습니다.** 그 코드를 그대로 파이에서 돌렸습니다.

```
can0 · 원본 leg_control 방식
   1  mode=2   2  mode=2   3  mode=0
   4  mode=2   5  mode=0   6  mode=0
  (0.3초 뒤 다시 켜기) 1·2·4 는 2, 3·5·6 은 0
```

**세 구현이 모두 같은 프레임을 보내고 모두 같은 결과를 냅니다.** 보내는 쪽에서 더
찾을 것이 없습니다.

★ `move_motor10.py` 머리말에 *"50Hz 로 계속 재전송한다 (급격한 위치 점프 방지 +
**MIT 명령 타임아웃 방지**)"* 라고 적혀 있어 "명령이 끊기면 모터가 스스로 꺼진다" 는
성질을 원저자도 알고 있었음이 확인됩니다. 다만 지금 문제는 **켜졌다가 꺼지는 것이
아니라 처음부터 안 켜지는 것**이라 이 성질로는 설명되지 않습니다.

**아직 확인 못 한 것**: 펌웨어 **버전 숫자**. HUPHY 는 버전 읽기가 PRIVATE 프로토콜
전용이라 적어 두었고(`tables.py:228-232`) 이 저장소에 구현이 없습니다. PRIVATE 에
아무도 답하지 않으므로 **통신만으로는 버전을 못 읽습니다.**

**사람이 할 것**

1. **일곱 개와 다섯 개가 실제로 다른 물건인지 확인** — 제조 시기, 라벨, 최근에
   교체하거나 펌웨어를 올린 것이 있는지. 다섯 개(엉덩이앞뒤 2, 엉덩이좌우 왼쪽,
   무릎 2)만 새 펌웨어라면 그 경위가 답입니다.
2. 다르다면 **일곱 개를 같은 펌웨어로 맞추는 것**이 해법입니다.
3. 그동안 실물에서 쓸 수 있는 관절은 **1·2·4·7·10 (다섯 개)** 입니다.

## ★ 이 조사 중에 제가 낸 사고 — 끄기 명령을 프로토콜 변경으로 잘못 보냄

힘을 빼는 도구(`System_ID/can_off.py`)를 새로 쓰면서 일곱 번째 바이트를 `0x00` 으로
적었습니다. 같은 명령 바이트가 그 자리 값에 따라 뜻이 완전히 달라집니다.

```
FF FF FF FF FF FF FF FD    힘 빼기
FF FF FF FF FF FF 00 FD    통신 프로토콜을 0(PRIVATE)으로 바꿈   <- 제가 보낸 것
```

**열두 개 전부에 세 번씩 나갔습니다.** 이 설정은 *전원을 다시 넣을 때* 적용되므로 당장
증상이 없었고, 알아챈 것은 **모터 하나가 안 꺼져서** 였습니다. 그대로 두고 전원을
껐다 켰으면 열두 개가 전부 다른 방식으로 말하기 시작해 **아무것도 안 붙었을 것**입니다.

되돌렸습니다 — 통신 방식을 MIT(2)로 다시 못 박고(`--restore-protocol`) 제대로 된
끄기를 보냈습니다. 열두 개 전부 **힘 꺼짐** 확인했습니다.

같은 구조가 다른 명령에도 있습니다. 이 자리는 눈으로 반드시 확인해야 합니다.

| 명령 | 일곱째 `0xFF` | 일곱째가 다른 값 |
|---|---|---|
| `0xFC` | 힘 켜기 | **제어모드 변경** |
| `0xFD` | 힘 빼기 | **통신 프로토콜 변경** |
| `0xFB` | 고장 클리어 | 고장값 조회 |
