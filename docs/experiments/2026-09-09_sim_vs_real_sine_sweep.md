> 이 문서는 처음 보는 사람도 읽을 수 있게 씁니다. 줄임말을 쓰지 않고, 숫자에는 단위를 붙이고,
> 어떤 조건에서 잰 값인지 함께 적습니다.

## 왜 했는가

사용자 관찰: **"화면 속 모형(Sim)은 다리가 달려 있는데도 실물보다 더 튀어 오르고(오버슛),
실물은 시킨 위치를 따라가지 못한다."** 상식과 반대입니다. 무거운 다리가 달린 쪽이 더 굼떠야
합니다. 그래서 **양쪽에 같은 이득(kp/kd)을 주고 같은 사인파 명령을 넣어** 주파수별로 응답을
견주었습니다.

## 한 줄 결론

**두 가지가 겹쳐 있었습니다.**

1. **실물에 도착하는 이득이 화면이 쓰는 값의 1/7 이었습니다.** 화면은 무릎에 kp=220 을 쓰는데
   실물에는 kp=30 만 도착합니다. 중간에 두 번 잘립니다.
2. **명령이 실물에 80 밀리초 늦게 도착합니다.** 화면 속 모형은 5 밀리초입니다. 16배 차이입니다.

그리고 **이득을 같게 맞춰 놓고 보면 관찰이 뒤집힙니다** — 실물이 화면 속 모형보다 **더 잘**
따라갑니다. 즉 "실물이 못 따라간다"는 것은 실물의 문제가 아니라 **실물에 약한 이득이
도착하고 있었기 때문**이었습니다.

덤으로, 왜 지금 이득 상한이 30 인지도 설명이 됩니다(아래 §6).

## 1. 이득이 어디서 잘리는가

| 단계 | 무릎 kp | 무릎 kd | 어디 |
|---|---|---|---|
| 화면 속 모형이 쓰는 값(학습 때 쓴 값) | **220.0** | **6.0** | `GET /gains` |
| 화면 쪽 전송 상한 | 30 | 1.5 | 뷰어 실행 환경변수 |
| 로봇 쪽 수신 상한 | 50 | 2.5 | 로봇 브리지 실행 인자 |
| **실제 모터에 도착** | **30.0** | **1.5** | 패킷 기록에서 확인 |

즉 **7.3배 약한 용수철**과 **4배 약한 damper**가 실물에 걸립니다. 두 상한 모두 벤치 첫
실험 때 안전을 위해 일부러 넣은 값이고, 그 뒤로 아무도 내리지 않았습니다. 버그가 아니라
**남아 있는 안전장치**입니다. 다만 화면 어디에도 "지금 7배 깎여서 나가는 중"이라고 적혀
있지 않았습니다.

덧붙여 **damping 비율도 달라집니다.** 감쇠는 대략 kd÷√kp 에 비례하는데,
화면 6÷√220 = 0.40 대 실물 1.5÷√30 = 0.27 이므로 **실물 쪽이 덜 감쇠된 설정**입니다.
아래 Run A/B 에서 오버슛이 오히려 커지는 것이 이 때문입니다.

## 2. 공정한 비교를 위해 고친 것

처음 잰 값은 비교가 성립하지 않았습니다. **화면 속 로봇의 발이 바닥에 닿아 있어서 무릎이
체중을 받고 있었습니다** — 그 상태의 무릎 토크는 23 뉴턴미터였습니다. 반면 벤치의 실물
모터는 **축에 아무것도 달리지 않은 맨 모터**입니다. 하중이 걸린 쪽과 무부하를 견준 셈입니다.

화면 속 로봇을 1.35 미터 높이에 매달아 발을 띄우자 무릎 토크가 **23 → 4.8 뉴턴미터**(정강이
무게만)로 떨어졌습니다. 이후 모든 측정은 이 조건입니다.

## 3. 실험 설계

한 관절(왼쪽 무릎)에 사인파 목표를 주고, 주파수를 0.2 → 3.2 헤르츠까지 7단계로 올립니다.
각 단계는 6주기 머물고 **앞 2주기는 버린 뒤** 잽니다(아직 안정되지 않은 구간을 그 주파수의
답으로 착각하지 않기 위해). 진폭은 ±8도입니다.

| 실험 | 무엇을 | 이득 | 실물 |
|---|---|---|---|
| A | 화면 속 모형만, 발 뜬 상태 | kp=220 kd=6 (모형의 원래 값) | 없음 |
| B | 화면 속 모형만, 발 뜬 상태 | kp=30 kd=1.5 (실물이 받는 값) | 없음 |
| C | **둘 동시**, 발 뜬 상태 | **kp=30 kd=1.5 (양쪽 같게)** | 있음 |

"따라감"은 실제로 움직인 폭 ÷ 시킨 폭입니다. 1.0이면 시킨 만큼 갔고, **1.0을 넘으면
오버슛**입니다. "늦음"은 목표보다 얼마나 뒤처져 따라오는지를 각도로 나타낸 것입니다.

## 4. 결과

### Run A — 화면 속 모형, 원래 이득 (kp=220 kd=6)

| 주파수 | 따라감 | 늦음 |
|---|---|---|
| 0.2 Hz | 0.958 | 2.2° |
| 0.8 Hz | 0.995 | 7.1° |
| **1.2 Hz** | **1.096** | 14.4° |
| 1.6 Hz | 0.878 | 31.3° |
| 3.2 Hz | 0.849 | 31.0° |

**1.2 헤르츠에서 오버슛(1.096)이 나옵니다.** 사용자가 본 "Sim이 튄다"가 이것입니다.

### Run B — 같은 모형, 이득만 실물 값으로 (kp=30 kd=1.5)

| 주파수 | 따라감 | 늦음 |
|---|---|---|
| 0.2 Hz | **0.740** | 7.2° |
| 0.8 Hz | 0.986 | 18.6° |
| **1.2 Hz** | **1.257** | 79.9° |
| 1.6 Hz | 0.324 | 67.2° |
| 3.2 Hz | 0.428 | 69.3° |

두 가지가 눈에 띕니다. **거의 정지 상태인 0.2 헤르츠에서도 74%밖에 못 따라갑니다** — 약한
용수철이 정강이 무게(4.8 뉴턴미터)를 못 이깁니다. 그리고 **오버슛이 1.096 → 1.257로 더
커졌습니다** — §1에서 말한 감쇠 비율 때문입니다.

### Run C — 둘 동시, 양쪽 같은 이득 (kp=30 kd=1.5) ★

| 주파수 | 모형 따라감 | 모형 늦음 | **실물 따라감** | **실물 늦음** |
|---|---|---|---|---|
| 0.2 Hz | 0.751 | 7.2° | **0.883** | 24.7° |
| 0.4 Hz | 0.788 | 9.8° | **0.912** | 32.6° |
| 0.8 Hz | 1.004 | 18.9° | **0.945** | 51.8° |
| 1.2 Hz | **1.314** | 79.4° | 1.041 | 74.9° |
| 1.6 Hz | **0.327** | 70.5° | **1.036** | 98.2° |
| 2.4 Hz | 0.402 | 57.6° | **1.002** | 142.3° |
| 3.2 Hz | 0.434 | 74.1° | 0.855 | 194.3° |

**이득을 같게 하면 관찰이 뒤집힙니다.** 실물은 0.88~1.04로 **모든 주파수에서 고르게**
따라가고, 화면 속 모형이 1.2 헤르츠에서 1.314로 튀었다가 1.6 헤르츠에서 0.327로 무너집니다.

실물이 못 따라간 것이 아니라, **실물에만 약한 이득이 가고 있었던 것**입니다.

## 5. 실물의 늦음은 순수한 "늦게 도착함"이다

실물의 늦음을 주파수에 대해 직선으로 맞춰 보면

```
늦음(도) = 9.1 + 56.7 × 주파수(헤르츠)      잔차 최대 4.3도 (16배 주파수 범위에서)
```

기울기가 곧 **시간 지연 157 밀리초**입니다. 따라가는 폭은 1.0 근처를 유지하는데 위상만
비례해서 늦는 것 — 전형적인 **순수 지연**의 모습입니다.

이것을 계단 입력으로 직접 갈라 재면:

| | 명령을 준 뒤 움직이기 시작할 때까지 |
|---|---|
| 화면 속 모형 | **5 밀리초** (제어 한 틱) |
| 실물 | **79~80 밀리초** |

즉 157 밀리초 중 **80 밀리초가 순수한 사구간(명령이 도착하기까지 아무 일도 안 일어나는
시간)**이고, 나머지는 모터 자체의 응답 지연입니다.

**관측 경로는 범인이 아닙니다.** 로봇이 잰 시각과 우리가 받은 시각의 차이가 0.31 ± 0.16
밀리초이고, 관측은 초당 311번 들어옵니다. 늦는 것은 **명령이 가는 방향**입니다.

80 밀리초의 내역 중 설명되는 부분:

| 구간 | 예상 |
|---|---|
| 화면이 초당 50번 보냄 → 다음 패킷까지 기다림 | 평균 10 ms |
| 통신 왕복 18 ms 의 절반 | 9 ms |
| 로봇이 초당 100번 도는 제어 루프 | 평균 5 ms |
| 관측이 돌아오는 길 | 약 12 ms |
| **합계** | **약 36~44 ms** |

**나머지 약 36~44 밀리초는 아직 설명되지 않았습니다.** 이걸 가르려면 로봇이 "언제 명령을
받아 언제 모터에 썼는지"를 스스로 기록해야 하고, 그건 로봇 쪽 코드 수정입니다 → §7.

## 6. 왜 지금 상한이 30 인지가 설명된다

명령이 80 밀리초 늦게 도착하면, 제어 이론상 **1÷(2×0.08) = 6.25 헤르츠**에서 위상이 180도
뒤집힙니다. 그 주파수에서 되먹임 크기가 1을 넘으면 발진합니다. 맨 모터의 회전자 관성을
0.0163 킬로그램제곱미터로 놓고 계산하면 그 한계 이득은

```
kp = 0.0163 × (2π × 6.25)² ≈ 25
```

**현재 쓰고 있는 상한 30과 거의 같습니다.** 이 30은 예전에 벤치에서 손으로 더듬어 찾은
값인데(5는 정지 마찰도 못 이겨서 무릎 5도 명령에 0.04도만 움직였음), 그 값이 우연이 아니라
**80 밀리초 지연이 정하는 한계**였던 것으로 보입니다.

**따라서 "상한을 220까지 올리면 된다"는 해법은 위험합니다.** 지연을 먼저 줄이지 않고 이득만
올리면 발진합니다. 순서는 **지연 줄이기 → 그 다음 이득 올리기**입니다.
(이 수치는 감쇠 항이 주는 위상 앞섬을 무시한 어림이므로, 실제 한계는 실험으로 확인해야
합니다 — §7.)

## 7. 아직 확인하지 못한 것

* **설명되지 않은 36~44 밀리초가 어디인지.** 로봇이 명령을 받은 시각과 모터에 쓴 시각을
  스스로 남기게 해야 가릅니다. 로봇 쪽 코드 수정이라 별도 가지에서 하고 장부에 남깁니다
  (`docs/128_huphy_change_ledger.md`).
* **모터 파라미터(회전자 관성·damping)가 맞는지.** 화면 속 모형은 무릎 armature 0.01633,
  damping 0.0095, 정지마찰 0.2695 뉴턴미터를 씁니다. 맨 모터의 계단 응답에서 실제 값을
  역산해 대조해야 합니다. 이번 실험은 이 항목을 아직 건드리지 않았습니다.
* **이득을 올렸을 때 실제 한계.** §6의 25는 계산값입니다. 30 → 40 → 50 식으로 조금씩 올리며
  발진이 시작되는 지점을 실측해야 합니다. 지연을 줄이기 전에는 권하지 않습니다.
* **엉덩이 회전 관절**은 아직 안 쟀습니다(무릎만).

## 이 숫자로 할 수 없는 말

* 이번 측정은 **무릎 하나**, **±8도**, **발 뜬 상태**입니다. 걷는 중의 부하나 다른 진폭에서
  같은 결과가 나온다는 보장은 없습니다.
* 실물 쪽 "따라감"은 **맨 모터**의 값입니다. 다리를 달면 관성이 붙어 달라집니다.
* 80 밀리초는 **왕복**(명령이 가고 관측이 돌아오는 것까지)입니다. 편도 명령 지연만 따로 잰
  것이 아닙니다.

## 설정 명세

자동 채움 도구는 이 노트를 학습 런으로 보고 "원본 설정 소실"이라 적었는데, **사실이 아니라
바로잡습니다.** 이것은 학습 런이 아니라 **벤치 측정**입니다. 학습 런 디렉토리가 없는 것이
맞고(애초에 학습을 하지 않았으므로), 이 측정을 지배한 설정은 전부 아래에 있습니다.

### §1b-2 액추에이터 (왼무릎, 측정 대상)

| 항목 | 화면 속 모형 | 실물 벤치 |
|---|---|---|
| 모터 | RS04 | RS04 (맨 모터, 축에 부착물 없음) |
| 토크 한계 | ±120 뉴턴미터 (실측 사용 구간 −23.4~+10.2) | 로봇 설정값 |
| 회전자 관성(armature) | 0.01633 | 미측정 — 대조 예정(§7) |
| 관절 damping | 0.0095 | 미측정 |
| 정지 마찰 | 0.2695 뉴턴미터 | 미측정 |
| 액추에이터 방식 | 토크 지령 + 소프트웨어 PD | MIT 모드 (kp/kd 전송) |

실효 이득 확인: 기록의 토크를 `토크 ≈ kp×오차 − kd×각속도`로 회귀하면
**kp 219.96 / kd 4.88, 결정계수 1.0000** — 설정한 220 이 그대로 적용되고 있으며 포화도
아닙니다(한계의 20% 이내에서만 움직임).
