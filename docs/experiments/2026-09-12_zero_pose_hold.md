# 2026-09-12 · 다리 12관절을 0도로 되돌리고 유지 — 첫 전관절 구동

> 실물 로봇의 다리(관절 12개)를 **로봇 프로그램(HUPHY) 자신의 기능으로** 처음 전부
> 움직였습니다. 그전까지는 제가 따로 짠 코드로 관절 두세 개만 돌렸습니다.

## 왜 했나

관절마다 기울어진 정도가 제각각이라 **어느 관절이 얼마나 어긋났는지 눈으로 볼 수가
없었습니다.** 12개를 전부 0도에 모으면 어긋남이 바로 보입니다. 그리고 이 자세가
앞으로 관절 영점을 실측할 때의 출발선이 됩니다.

사용자 지시로 **15초에 걸쳐 천천히** 옮겼고, 영상을 남겼습니다.

## 무엇을 어떻게

| 항목 | 값 |
|---|---|
| 돌린 프로그램 | `huphy-test --robot zero --approach 15 --allow-uncalibrated` |
| 어디서 | 다리가 달린 라즈베리파이 (`~/HUPHY`, 가지 `biped` 커밋 `eb8541e` 의 사본) |
| 통신 | `can0` = 왼다리(모터 1~6), `can1` = 오른다리(모터 7~12) |
| 목표 제어 주기 | 초당 100회 |
| 한 주기 최대 이동량 | 12.0도 (모터 무부하 최고속도 초당 1200도 ÷ 초당 100회) |
| 한계 안쪽 여유 | 3.0도 |
| 영상 | `docs/assets/hw/2026-09-12_zero_pose_hold.mp4` (274.9초, 실시간 속도) |

**미리 보여준 것**(사용자 승인 전): 무릎 둘은 **±3.00도로 잘립니다**. 무릎은 0도가
하드스톱이고 여유가 3도이기 때문입니다. 나머지 10개는 정확히 0.00도로 갑니다.

**첫 주기에 실제로 들어간 보정량**: 왼 엉덩이회전 1.40도, 오른 엉덩이회전 1.49도,
오른 무릎 5.63도 (0.98 뉴턴미터). 셋 다 한 주기 상한 12.0도 안입니다.

## 결과 — 자세는 맞았고, 통신이 못 따라왔습니다

### 자세

끝난 뒤 12개 관절 전부 **힘 꺼짐** 상태에서 읽은 값입니다 (세기 0 · 감쇠 0 · 토크 0
프레임만 보내는 읽기 전용 조회).

| 번호 | 관절 | 각도(도) | 온도(도) |
|---:|---|---:|---:|
| 1 | 왼 엉덩이앞뒤 | 0.05 | 31.0 |
| 2 | 왼 엉덩이좌우 | 2.52 | 30.0 |
| 3 | 왼 엉덩이회전 | 1.29 | 27.0 |
| 4 | 왼 무릎 | 4.47 | 28.0 |
| 5 | 왼 발목 A | −0.76 | 28.0 |
| 6 | 왼 발목 B | −2.01 | 28.0 |
| 7 | 오른 엉덩이앞뒤 | −3.07 | 30.0 |
| 8 | 오른 엉덩이좌우 | −1.20 | 28.0 |
| 9 | 오른 엉덩이회전 | −2.30 | 28.0 |
| 10 | 오른 무릎 | 0.80 | 28.0 |
| 11 | 오른 발목 A | −1.31 | 28.0 |
| 12 | 오른 발목 B | 0.08 | 28.0 |

전부 0도에서 4.5도 안입니다. 온도는 27~31도로 실온 수준 — 힘을 거의 안 쓰고 버텼다는
뜻입니다.

**이 숫자로 할 수 없는 말**: 이건 **모터가 켜진 순간을 0으로 본 각도**이지, 관절이
실제로 0도라는 뜻이 아닙니다. 관절 영점은 아직 안 쟀습니다. 왼 무릎 4.47도와 오른 무릎
0.80도의 차이도 "왼쪽이 더 굽었다"가 아니라 "두 모터의 영점이 서로 다른 자리에 있다"
일 수 있습니다.

### 안전장치가 실제로 막은 것

| 무엇 | 횟수 |
|---|---:|
| 관절 한계를 넘는 명령을 한계 안쪽으로 자름 | 48,762 |
| 한 주기 이동량(12.0도)을 넘는 명령을 자름 | 11 |
| 상태값이 없어 명령 자체를 거부 | 2 |

한계 자르기가 4만 8천 번인 것은 **무릎 둘이 내내 잘리고 있었기 때문**입니다 — 0도를
달라는 명령이 매 주기 3.00도로 잘렸습니다. 이것이 의도한 동작입니다.

### 통신이 못 따라왔습니다 — 그리고 그게 끝을 맺었습니다

```
huphy 종료: 24540주기 296.5초 (평균 82.8Hz / 목표 100Hz), 밀림 548회,
            최악 23.8ms, 무응답 주기 23858회
통신 두절로 멈춤: ['left_leg/knee'] 가 5주기째 응답 없음. 자세를 붙잡고 토크를 끊음
```

| 무엇 | 숫자 | 뜻 |
|---|---|---|
| 제어 주기 | 평균 초당 82.8회 (목표 100회) | 17퍼센트 느립니다. 밀림 548회, 최악 23.8밀리초. |
| 수거 대기 | 다리당 2밀리초 × 2 = 최악 4밀리초 | 10밀리초 주기의 40퍼센트를 모터 응답 기다리는 데 씁니다. |
| 무응답 주기 | 23,858회 / 24,540회 = **97.2퍼센트** | 거의 매 주기, 모터 하나 이상이 그 주기 안에 답을 못 했습니다. |

**오른다리(can1)가 왼다리(can0)보다 고르게 더 나쁩니다.** 그리고 송신 실패·수신 실패는
양쪽 모두 **0회**이고, 대기 초과만 can0 5,411회 · can1 6,350회입니다. 즉 **신호가 깨져서
못 받은 게 아니라, 정해진 시간 안에 안 온 것**입니다.

끝을 맺은 것은 사람이 아니라 로봇 프로그램 자신입니다. 왼 무릎이 다섯 주기 연속으로
답이 없자 *"자세를 붙잡고 토크를 끊음"* 경로를 탔습니다. 이 장치는 의도대로 동작했습니다.

## 다음에 할 일

1. **응답이 빠지는 원인 가르기.** 처리 속도(파이가 벅참)인지 배선인지. 가장 싼 갈림길은
   **다리 하나만 돌려 보는 것**입니다 — 모터 6개면 주기 부담이 절반이므로, 그래도
   빠지면 배선 쪽입니다.
2. 관절 영점 실측 (지금 자세가 출발선).
3. 관절별 부호(`sign`) 확정 — 아직 12개 전부 미실측입니다.

## 되짚을 거리

- **영상을 움직임이 시작된 뒤에 켰습니다.** 첫 몇 초가 빠졌습니다. 순서를 바꿔야 합니다:
  녹화가 도는 것을 확인한 다음에 명령.
- 이 실험 전에 **제가 따로 짠 코드로 무릎을 열었다가 하드스톱을 넘길 뻔했습니다.**
  로봇 프로그램을 그대로 쓰면 한계 자르기가 자동으로 걸립니다 — 실제로 이번에 4만 8천 번
  걸렸습니다. 앞으로 실물 구동은 로봇 프로그램 경로로만 합니다.
