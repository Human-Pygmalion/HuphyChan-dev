# 2026-09-12 · 발목 두 모터를 모터 공간에서 안전하게 자르기

> 한 줄: **기구학은 아무것도 못 거릅니다.** 다듬은 크랭크 사각형이 100% 풀립니다.
> 거르는 일을 하는 것은 **발판 자세 한계** 하나뿐입니다.

## 왜 이 문제가 생기는가

발목은 모터 두 개가 로드 두 개로 발판 하나를 미는 **닫힌 기구**입니다. 그래서 두
각도를 따로 자르면 모자랍니다 — 각각은 범위 안이어도 **그 조합이 발판을 한계 밖으로**
보낼 수 있습니다.

로봇 프로그램(HUPHY)은 **발판 공간**(`ankle_pitch`/`ankle_roll`)으로 명령을 주면
역기구학으로 조합을 봅니다. 그런데 우리는 **모터 공간**(`ankle_a`/`ankle_b`)으로
줍니다 — 사용자 결정(2026-09-12): *"AB. HUPHY 지금 구현체도, 실제 Policy 도 그 공간으로
돌잖아."* 맞는 말이고, 학습된 정책이 내는 것이 그 두 숫자입니다.

**모터 공간에서는 HUPHY 가 A·B 를 따로따로 자르고 조합은 아무도 안 봅니다.**

## 실측한 구멍

크랭크 한계는 시뮬레이터 모델에서 ±68.75도이고, 운용은 양쪽 15도 안으로 줄여
±53.75도입니다. 그 사각형 안에서:

| 조합 | 발판이 가는 자세 |
|---|---|
| A **+53.8** / B **−53.8** | **숙임 67.4도** — 한계 30도를 37도 넘김 |
| A **+53.8** / B **+53.8** | **기울임 45.2도** — 한계 20도를 25도 넘김 |

각각은 범위 안입니다. 조합이 문제입니다.

## ★ 기구학은 필터가 아닙니다

"갈 수 없는 조합은 기구학이 막아 준다" 고 생각하기 쉽지만, 재 보니 **아니었습니다.**

HUPHY 의 발목 기구학(`kinematics/ankle.py`)으로 A·B 격자를 전수로 풀었습니다.

| | 결과 |
|---|---|
| 격자 | 81 × 81 = **6,561칸**, 양발 각각 |
| `solve_fk` 가 푼 칸 | **6,561칸 (100.0%)** |
| 못 푼 칸 | **0칸** |

**운용 범위 안에서 기구학이 실패하는 자리가 하나도 없습니다.** 그러므로 "기구학이
막아 줄 것" 은 안전 근거가 못 됩니다. 거르는 일을 하는 것은 **발판 자세 한계**뿐입니다.

## 발판 한계의 출처 — 시뮬레이터 모델

사용자 지시: *"rp 모드 mjcf / urdf 확인해봐. 그거 돌려보면 나올탠데."* 그대로 했습니다.

```xml
<joint name="L_ankle_pitch_joint" range="-0.872665 0.523599"/>   <!-- -50.00 ~ +30.00도 -->
<joint name="L_ankle_roll_joint"  range="-0.349066 0.349066"/>   <!-- -20.00 ~ +20.00도 -->
```

지금 쓰는 모델 전부가 같은 값이고 **양발이 같습니다.**

★ **제 추측이 틀렸던 자리**: 방향을 몰라 "두 해석의 교집합인 숙임 ±30" 으로 잡아
두었는데, 실제로는 **한쪽 50도 · 다른 쪽 30도로 치우쳐** 있습니다. 제 추측대로 갔으면
한쪽에서 20도를 버릴 뻔했습니다.

옛 세대 모델 다섯 종(`pygmalion_v1`·`pygmalion.xml`·`cant20`·`cant30`·`rolloff30`)은
숙임 상한이 **+40도**로 다릅니다. 6~7월 파일이고 파이썬 어디에서도 참조하지 않는 것을
확인했습니다. 한 폴더에 세대가 섞여 있으니 **대조할 때 반드시 갈라야 합니다.**

## 걸어 둔 것 — 두 겹을 **AND** 로

사용자 지시: *"양쪽 다 걸고, and 문으로 클리핑해."*

```
1) 축마다      |A| <= 22.75도  그리고  |B| <= 22.75도
2) 조합으로    solve_fk(A, B) 가 숙임 -50~+30 · 기울임 -20~+20 안
```

**둘 다 만족해야** 통과합니다. 하나라도 어긋나면 **두 모터가 같이** 직전에 받아들인
자리 쪽으로 물러납니다(반씩 좁히기 12회). 거부하지 않고 자르는 이유, 그리고 한쪽만
자르지 않는 이유는 같습니다 — **한쪽 로드만 요구가 바뀌면 기구가 비틉니다.**

**22.75도는 계산해 낸 값입니다.** 네 귀퉁이가 전부 ROM 안에 드는 가장 큰 정사각형을
ROM 에서 찾은 것이고, 양발이 같습니다. ROM 을 바꾸면 이 값도 바뀌어야 하므로,
검사(E27)가 **매 실행마다 다시 계산해 상수와 대조**합니다.

구현: `System_ID/huphy_live.py` 의 `AnklePairGuard`.

## 검사

`tools/huphy_audit/e2e_live.py` E25~E29. 전부 가짜 모터 위에서 돕니다.

| | 무엇 | 결과 |
|---|---|---|
| E25 | 축마다 자르기 | A 90도를 넣으면 22.75도로 나감 |
| E26 | 조합이 ROM 밖이면 물러나는가 | 축 한계 안에서는 **벗어나는 자리가 아예 없음**(61×61 전수) — 축 한 겹으로 이미 닫혀 있고 조합 검사는 덧대는 것 |
| E27 | 축 한계가 ROM 과 아직 맞는가 | 다시 계산해 대조 |
| E28 | ROM 이 지금 쓰는 모델과 같은가 | **첫 실행에서 옛 모델 다섯 종의 +40도를 잡아냄** |
| E29 | 물러날 때 두 모터가 같이 가는가 | 같은 비율로 물러남 |

## 남은 질문 — 시뮬에도 클리핑이 필요한가

사용자 질문: *"Sim 의 출력은 클리핑 안된, ROM 밖 출력도 들어가지 않나?"*

확인한 사실:

* 시뮬 모델은 크랭크 관절에 **±68.75도 범위**를 갖고 있습니다.
* 발판 관절에도 −50~+30 / ±20 이 걸려 있습니다.
* `<equality connect>` 로 **닫힌 고리가 실제로 물려 있습니다** — 로드가 물려 있으니
  갈 수 없는 조합은 시뮬에서도 못 갑니다.

그러므로 **조합 제한은 시뮬에도 이미 있습니다.** 실물과 다른 것은 **한계에 부딪혔을
때**입니다 — 시뮬에서는 구속조건이라 공짜이고, 실물에서는 쇠입니다.

**따라서 진짜 물어야 할 것은 "정책이 한계를 밀고 있는가" 입니다.** 안 밀고 있으면
시뮬 클리핑은 필요 없고, 밀고 있으면 그건 클리핑 이전에 보상 설계 문제입니다 —
예전에 무릎이 멈춤턱을 상시 21.8 뉴턴미터로 밀던 것과 같은 종류입니다.

이건 **학습 쪽 일**이라 이 세션에서 하지 않습니다 (사용자 지시 2026-09-12:
*"이 세션에서는 학습관련해서 아무것도 안한다"*). **포크된 세션에 넘길 항목**입니다.
