## §5 여쭐 것 넷

### §5-1 게인을 어느 쪽에 맞출까요 — **이것이 제일 중요합니다**

| | 지금 값 |
|---|---|
| 실기 (`robot.yaml`) | `kp 10 · kd 1` (12개 전부) |
| 시뮬 (학습) | 엉덩이 150 · 무릎 220 · 발목 28.5 · 크랭크 22.27, `kd 6 / 1.81 / 1.414` |

**이대로 같은 명령을 주면 "모형이 실물과 다른가" 가 아니라 "게인이 다른가" 를 재게
됩니다.** 고를 수 있는 것:

| 안 | 내용 | 걱정 |
|---|---|---|
| **가** | 실기를 시뮬 값(150/220)으로 올림 | 실기에서 그 세기를 써 본 적 없음. 벤치 상한은 30이었음 |
| **나** | 시뮬을 실기 값(10/1)으로 내림 | 안전하지만 **학습이 쓰는 조건이 아님** |
| **다** | 양쪽을 중간(예: 20/2)으로 맞춤 | 벤치에서 검증된 영역. 다만 둘 다 실사용 조건이 아님 |

벤치 기록: `kp=5` 는 정지마찰을 못 이겨 5도 명령에 0.04도밖에 안 움직였고, 풀리는 값이
무릎 20 · 엉덩이회전 10 이었습니다.

### §5-2 영점을 먼저 넣을까요

HUPHY 보정 파일의 `offset_deg` 가 12줄 전부 `0.0` 입니다(할 일 #14). 앞선 측정에서
**왼 무릎이 9.4도**까지 어긋나 있었습니다. 이걸 안 넣으면 "같은 명령" 이 **다른 자세**를
뜻합니다. 지금 넣고 시작할까요, 아니면 그대로 재고 나중에 빼서 보정할까요?

### §5-3 어떤 명령을, 어떤 관절에, 어떤 자세로

* **관절**: 한 번에 하나(벤치에서 하던 방식, 해석이 깨끗함) vs 12개 동시
* **명령 모양**: 계단 / 처프 / 사인 — 벤치 도구가 이미 셋 다 있습니다
* **자세**: 크레인에 매달아 발을 띄운 채 vs 발을 바닥에 붙이고
* **시뮬 쪽 받침대**: 매단 상태를 흉내내려면 `string` 또는 `fixed` 가 맞고, `free` 면 넘어집니다

권합니다: **왼 무릎 하나, 계단 입력, 크레인에 매달아 발 띄움, 시뮬은 `fixed`.**
가장 단순하고 벤치 자료와 바로 비교됩니다.

### §5-4 `test_tx_wiring` 의 가짜 값을 고쳐도 될까요

§4 의 왼 무릎 `+22.9도` 입니다. 모델 범위가 `[−120, 0]` 이니 부호만 뒤집으면 범위 안에
들어옵니다. **시험 파일만 고치는 일**이고 제품 코드는 안 건드립니다.

### §8-2 막힌 시험 9개 — **제품 코드는 멀쩡하고, 시험 쪽 값이 낡았습니다**

9개를 전부 끝까지 따라가 보니 **버그가 하나도 없었습니다.** 두 무리입니다.

**(가) `test_rom_clip` 2개 — 2026-09-04 규칙을 아직 검사하고 있음**

`sim_core.py` 는 2026-09-15 에 사용자 지시로 **자르기를 그만두고 세기만** 하도록 바뀌었습니다.
그 근거가 코드 안에 그대로 적혀 있습니다:

```python
# sim_core.py:874  (docstring)
#   ROM: **the received value is never altered** (2026-09-15, replacing the 2026-09-04
#   clip). The user's rule is that nothing between the robot and the model may set a
#   direction or a range limit - doing so erases the very mismatch this view exists to
#   show. The left knee reached 9.7 deg past its model bound and the old clip drew it
#   pinned at the bound, which read as "fine".
```

시험은 아직 옛 보장(`assert lo <= q <= hi`)을 검사합니다. **제품이 옳고 시험이 낡았습니다.**
그리고 이것은 제가 §3 에서 `rom_deg` 를 `null` 로 되돌린 판단과 **같은 규칙**입니다.

**(나) `test_tx_wiring` 6개 + `test_remote_motion` 1개 — 2026-09-12 이전 부호**

가짜 값이 왼 무릎을 `+0.4 rad = +22.9도` 로 줍니다. 지금 모형에서 왼 무릎은 `[−120, 0]도`

텔레메트리가 정확히 **`−6.0`** 을 돌려주었습니다:

```
L_knee_joint   model_range=[-120.00,   0.00]   safe_clip=[-114.00,  -6.00] deg
시험 기대:  pkt["left_leg/knee/pos"] > 5.0
실제 결과:  -6.0        ← safe_clip 의 위쪽 끝과 소수점까지 일치
```

`test_tx_wiring` 6개는 그 43도 벌어짐을 **무장 관문이 `409` 로 막아서** 납니다.
**안전장치가 제 일을 한 것이고, 이것이 우리가 모터를 만지기 전에 확인하고 싶었던 바로 그 동작입니다.**

**틀린 절반 — 그래도 12개 다 무응답입니다.** 그리고 원래 고장(11:16)의 원인도 아닙니다:

* 11:22 부터 12:12 까지 **USB 사건이 하나도 없습니다** — 번호가 바뀐 적이 없습니다.
* 무엇보다 **11:03 에 바로 이 CANable2 두 개로 12개가 전부 답했습니다.** 어댑터 종류가
  근본적으로 안 맞는 것이라면 그때도 안 됐어야 합니다.

**지금 계측값**: 조회를 3개 보내면 `TX packets 6 → 9` 로 정확히 늘고, `RX packets 0`,
오류·드롭·bus-off 전부 0. **나가기는 나가고, 아무도 답하지 않습니다.**

### §11-7 남은 후보 두 개와, 각각을 가르는 방법

| 후보 | 왜 그럴듯한가 | 어떻게 가르나 |
|---|---|---|
| **모터 전원이 안 나감** | 두 버스가 동시에 죽었고, 공통은 전원뿐 | 전원공급기 **전압·전류 실제 수치**를 눈으로. 조회를 보내는 동안 전류가 조금이라도 움직이면 살아 있는 것 |
| **종단 저항(120옴)** | CANable v1 은 납땜 점퍼, CANable2 는 설정이 다를 수 있음. 종단이 없으면 **한 번은 되고 그다음엔 안 되는** 식으로 애매하게 동작함 | 새 어댑터의 종단 설정 확인. 또는 옛 CANable 을 잠깐 도로 꽂아 조회 |

**옛 어댑터를 도로 꽂아 `can_probe.py` 를 돌려 보는 것이 가장 빠른 판정입니다** —
답하면 어댑터 문제이고, 그래도 안 답하면 전원·배선입니다.

#### 되돌리는 도구가 이미 있습니다

```python
# System_ID/can_off.py:46
SET_PROTOCOL_MIT = bytes([0xFF] * 6 + [0x02, 0xFD])
"""통신 프로토콜을 MIT(2) 로 되돌린다. --restore-protocol 일 때만 보낸다."""
```

```
can_off.py --channel can0 --ids 1 2 3 4 5 6 --restore-protocol
```

**다만 이것도 "전원 재투입 후 적용" 입니다** — 보낸 뒤 모터 전원을 한 번 껐다 켜야 합니다.
그리고 모터에 **영구 저장되는 설정**이므로 사용자 확인 없이는 보내지 않습니다.

**또 하나 바로잡습니다**: 제가 §11-3 에서 *"상태 조회에 12개 다 무응답 = 힘이 꺼져 있다는 뜻"*
이라고 적었는데, `docs/124` 에 **그 해석을 실측으로 철회한 기록**이 있습니다 —
*"꺼진 모터도 정상적으로 답합니다. `disable_torque()` 뒤 0.5/1.0/2.0초에 물어도 무응답
모터 없음. 응답 여부로는 전원 상태를 알 수 없습니다."* 즉 **무응답은 정상이 아니라 고장
신호**였습니다.
