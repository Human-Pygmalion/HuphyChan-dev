# 통신 건강을 어떻게 판정할 것인가 — 설계안

> 2026-09-12. 사용자 제안: *"카운터를 달고 보낸 명령에 대해 대답이 오면 0으로, 안 오면
> 1씩 올리고, 5를 넘으면 응답없음으로 치는 건 어때? 반례나 이걸로 못 잡는 통신문제가
> 있나?"* → *"1,2 좀 더 구체적으로. 중요한 부분이라 엄밀하게 설계해야 해."*

이 문서는 **아직 고치기 전**입니다. 승인받고 손댑니다. HUPHY 는 우리 저장소가
아니므로 가지에서만 작업하고 `docs/128_huphy_change_ledger.md` 에 적습니다.


## 0. 지금 어떻게 돌고 있나 (읽고 확인한 것)

제안하신 방식이 **이미 구현되어 있습니다.**

| 자리 | 하는 일 |
|---|---|
| `robots/leg.py:730` `_note_link` | 응답 오면 `_miss_streak[모터] = 0`, 없으면 `+= 1` |
| `safety/link.py:44` | `DEFAULT_MAX_MISS_CYCLES = 5` |
| `safety/link.py:100` | `miss >= 5` 인 모터가 하나라도 있으면 두절 판정 |
| `control/loop.py:274` | 두절이면 자세를 붙잡고 토크를 끊음 |

"응답이 왔다" 의 판정은 `motors/robstride/bus.py:232 collect()` 에 있습니다 —
**이번에 꺼낸 프레임 묶음 안에 그 모터 번호가 있었는가.**


## 1. 무엇이 문제인가 — "왔다" 의 정의

`collect()` 는 프레임이 **언제 도착한 것인지 안 봅니다.** 큐에서 꺼낸 묶음에 그
모터 번호가 있으면 "왔다" 입니다. 여기서 두 가지가 갈라집니다.

### (가) 한 주기 늦게 오는 응답을 "이번 것" 으로 셈

응답 대기창을 0으로 두면 이번 주기 응답을 안 기다리고 **직전 주기 것**을 집습니다.
그래도 카운터는 0으로 초기화됩니다. **모든 값이 한 박자 뒤인데 건강해 보입니다.**

### (나) 반대로, 멀쩡한데 두절로 판정함

큐가 마침 비어 있으면 "없음" 으로 셉니다. 응답은 30밀리초 뒤에 멀쩡히 도착하는데도요.
2026-09-12 실측에서 대기창 0으로 양다리를 돌렸더니 **왼 무릎이 5주기째 무응답으로
찍혀 루프가 멈췄습니다.** 통신은 멀쩡했습니다.

즉 지금 카운터는 통신 건강이 아니라 **"우리가 꺼낸 순간과 응답이 도착한 순간의
위상차"** 를 재고 있습니다.


## 2. 제안 — 연속 횟수가 아니라 **밀린 개수**를 센다

    지금:  응답 오면 0, 없으면 +1,  5 이상이면 두절
    제안:  보낼 때 +1, 응답 오면 -1,  밀린 개수가 5 이상이면 두절

모터마다 `outstanding`(답을 못 받은 명령 수)을 듭니다.

### 왜 이게 나은가

| 상황 | 지금 (연속 무응답) | 제안 (밀린 개수) |
|---|---|---|
| 응답이 늘 한 주기 늦음 | 0 (건강해 보임) 또는 5 (헛 두절) — **위상 따라 뒤집힘** | **계속 1** — 늦는다는 사실이 그대로 보임 |
| 정말 죽은 모터 | 1,2,3,4,5 → 두절 | 1,2,3,4,5 → 두절 (같음) |
| 다섯 중 한 번만 답함 | **영영 안 걸림** (매번 초기화) | 5주기마다 +4 → **곧 걸림** |
| 응답이 몰려서 두 개씩 옴 | 한 주기 0, 다음 1 | 0 유지 |

**세 번째 줄이 핵심입니다.** 문턱 아래로 새는 모터는 지금 방식으로 절대 안 잡힙니다.

### 구현이 작습니다

재료가 이미 다 있습니다.

* `CanFrame.stamp` — **받는 순간**의 `time.monotonic()` (`canbus.py:326`, `:470`).
  수신 스레드가 큐에 넣을 때 찍으므로 진짜 도착 시각입니다.
* `Leg._awaiting` — 이번 주기에 명령한 모터 (`leg.py:711`).
* `Leg._miss_streak` — 자리만 바꾸면 됩니다.

고칠 곳은 `_note_link` 하나입니다.

```
    for motor_id in self._awaiting:
        self._asked[motor_id] += 1
        self._outstanding[motor_id] += 1          # 보냈다
    for motor_id in answered:                      # 이번에 도착한 응답
        self._outstanding[motor_id] = max(0, self._outstanding[motor_id] - 1)
```

`answered` 는 `bus.collect()` 가 이미 돌려주는 "본 모터" 의 여집합입니다.

### 엄밀히 따질 점 넷

1. **부르지 않은 응답이 섞이면 안 됩니다.** 고장 조회(`0xFB`) 응답은 상태 프레임과
   **CAN ID 가 같습니다**. 그걸 답으로 세면 밀린 개수가 잘못 줄어 문제를 가립니다.
   → 고장 조회 전에 큐를 비우는 `flush_rx` 가 이미 있고(`canbus.py:426`), 제어
   루프에서는 고장 조회를 안 합니다. **제어 중에는 고장 조회를 하지 않는다** 를
   규칙으로 못 박습니다.
2. **0 아래로 안 내려가게** 묶습니다. 한 주기에 두 개가 오면(직전 것 + 이번 것)
   음수가 되고, 그러면 그 뒤 진짜 무응답을 그만큼 못 셉니다.
3. **명령하지 않은 모터는 안 셉니다.** 지금 코드가 이미 `_awaiting` 으로 가립니다.
   여는 관절만 열 때 나머지가 두절로 찍히면 안 됩니다.
4. **문턱값**. 한 주기 늦는 운용에서는 밀린 개수가 **1에 머뭅니다.** 5는 여유가
   넉넉합니다. 다만 대기창을 0으로 두면 정상값이 1이므로, 문턱을 5로 두면 실제
   여유는 4주기(40밀리초)입니다. 그대로 둘지 6으로 올릴지는 실측으로 정합니다.

### 이 제안도 **못 잡는** 것

* **답은 하는데 값이 안 바뀌는 경우**(엔코더 굳음) — 프레임은 오므로 0입니다.
  → 3장에서 다룹니다.
* **답은 하는데 명령을 안 듣는 경우** — 오늘 제가 몇 시간 헤맨 그것입니다.
  밀린 개수는 0입니다. → 목표와 측정의 차이가 안 줄어드는 것으로 봐야 합니다.
  별도 항목으로 남깁니다.
* **같은 CAN 번호를 쓰는 모터가 둘** — 한쪽 응답이 양쪽을 줄입니다. 이건 어떤
  카운터로도 못 잡고, 연결할 때 번호를 확인하는 수밖에 없습니다(`can_up.py` 가 함).
* **송신 실패** — 밀린 개수는 늘어나므로 **걸리기는 합니다.** 다만 원인이
  "모터가 죽음" 인지 "우리가 못 보냄" 인지는 `can/tx_errors` 를 같이 봐야 갈립니다.


## 3. 고장 비트를 제어 경로에서 살리기

### 지금 상태

* 해독기 `codec/mit.py:168 decode_flags` 가 **있습니다.** 모드·고장·경고 세 비트를
  뽑고, 인코딩 범위와 무관해 항상 맞습니다.
* **부르는 곳이 시험 파일뿐입니다.** `bus.py:249` 의 `collect()` 는
  `decode_state` 로 다섯 물리량만 뽑고 **Byte6 의 비트를 버립니다.**
* `MotorState`(`motors/base.py:123`)에 담을 칸이 없습니다. 다만 **얼린 클래스가
  아니라** 칸을 넣을 수 있습니다.

즉 로봇이 "나 고장" 이라고 말해도 제어 루프는 **듣지 않습니다.**

### 제안

**① 담기** — `MotorState` 에 세 칸을 넣고 `collect()` 에서 채웁니다.

```
    mode: Optional[int] = None      # 0 꺼짐 / 1 보정중 / 2 켜짐
    fault: bool = False
    warning: bool = False
```

★ `mode` 는 **판단에 쓰지 않습니다.** RS03 은 힘이 들어가도 0으로 보고합니다
(2026-09-12 실측, 6543주기 중 0회가 2). 화면에 "모름" 으로 적는 용도입니다.
이걸 "꺼짐" 으로 읽었다가 멀쩡한 모터 일곱 개를 고장으로 몰았습니다.

**② 내보내기** — `Leg.link_status()` 와 관찰에 `fault`/`warning` 을 실어 화면과
텔레메트리까지 보냅니다.

**③ 판정** — 고장 비트가 **연속 N주기** 서면 두절과 같은 경로로 멈춥니다.

한 번에 멈추지 않는 이유: 2026-09-11 에 **초당 420건의 가짜 고장**을 본 적이
있습니다. 한 프레임만 보고 로봇을 세우면 멀쩡한 로봇이 계속 섭니다. 연속 조건이
그걸 거릅니다.

**④ 자세한 원인은 멈춘 뒤에** — 상태 프레임의 고장 비트는 **한 비트**라 "뭔가
잘못" 까지만 압니다. 어떤 고장인지는 고장 조회(`0xFB`)로 11비트 낱말을 받아야
합니다(`tables.py:249 FAULT_BITS`). 그건 **왕복이 한 번 더 드니 제어 중에는 하지
않고**, 멈춘 뒤에 한 번 물어 사람에게 보여 줍니다. 2장 1번 항목(고장 조회 응답이
상태 프레임과 ID가 같음)과도 맞물립니다.

### 이걸로 잡히는 것 / 안 잡히는 것

잡힘: 과열·저전압·과전압·상 과전류·스톨/과부하·엔코더 미보정·위치 초기화 실패 —
`FAULT_BITS` 의 11가지. **엔코더가 굳어도 그 비트가 서면 잡힙니다.**

안 잡힘: 비트가 안 서는 종류의 이상(기구가 걸림, 부하가 과함인데 모터는 정상 판단).
그건 **목표와 측정의 차이**로 봐야 합니다.


## 4. 어떻게 확인할 것인가

전부 가짜 통신선(`tools/huphy_audit/fake_can.py`) 위에서, **실물 전에** 봅니다.

| 검사 | 만들 상황 | 기대 |
|---|---|---|
| L1 | 응답이 늘 한 주기 늦게 옴 | 밀린 개수가 **1에 머묾**, 두절 아님 |
| L2 | 모터 하나가 완전히 죽음 | 5주기째 두절 판정 |
| L3 | 다섯 중 한 번만 답함 | **두절 판정됨** (지금 방식은 못 잡음) |
| L4 | 한 주기에 응답 두 개가 몰려 옴 | 밀린 개수가 **음수로 안 감** |
| L5 | 명령 안 한 모터 | 밀린 개수 안 늘어남 |
| L6 | 고장 비트가 한 주기만 섬 | **안 멈춤** (가짜 고장) |
| L7 | 고장 비트가 연속 N주기 섬 | 멈춤, 사람에게 무엇이 섰는지 보임 |
| L8 | RS03 이 mode 0 을 보고하며 정상 동작 | **고장으로 판정하지 않음** |

L3 과 L8 이 이번 설계의 핵심입니다 — 각각 "지금 못 잡는 것" 과 "오늘 잘못 잡았던 것".
