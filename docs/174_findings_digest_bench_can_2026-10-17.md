## 0. 용어

| 용어 | 정의 |
|---|---|
| 모터 ID | RobStride 모터의 CAN 주소 (파라미터 `0x2009 CAN_ID`, 1 ~ 127). 호스트가 모터에 명령을 보낼 때 11비트 번호로 쓴다 |
| 호스트 ID | 모터가 상태 응답을 보낼 때 쓰는 11비트 번호 (파라미터 `0x200A CAN_MASTER`, 공장값 253 = `0xFD`). 모터 ID 는 응답 데이터 0번 바이트에 들어간다 |
| F_CMD 바이트 | 특수 명령 프레임의 7번째 바이트 (`data[6]`). `0xFF` 가 아니면 명령의 뜻이 바뀐다 ([[reference-robstride-fcmd-byte]] 메모) |
| 몰아 보내기 (burst) | 한 버스의 모터 명령을 응답을 기다리지 않고 연달아 보내고, 응답을 나중에 한꺼번에 모으는 방식 |
| 하나씩 보내기 (seq) | 모터 하나에 보내고 그 응답을 받은 뒤 다음 모터에 보내는 방식 |
| 한 주기 밀림 | 이번 주기의 응답이 다음 주기에 처리되어, 상태 값이 한 주기 묵은 채 정상으로 보이는 상태 |
| VBUS | 모터 펌웨어가 잰 버스 전압 [V] (파라미터 `0x701C`) |
| iqf | 모터 펌웨어가 걸러 낸 q축 전류 [A] (파라미터 `0x701A`) |

## 1. v11a 권장안 묶음 시험 (`rough_box_trial_v11a`, 2026-10-14 ~ 15)

원본: [[experiments/2026-10-14_rough_box_trial_v11a]], 계획 [[168_v11a_improvement_plan]].

- 기준선은 실물 배포 정책 `rough_box_main_v11a` 의 설정이다.
- 시험은 다섯 가지를 한꺼번에 바꿨다. 명령 지연 0 ~ 1 정책 주기, 게인 무작위화 (Kp ×0.8 ~ 1.2, Kd ×0.7 ~ 1.3), 밀기 완화 (8 ~ 15 s 간격, 수평 ±0.5 m/s 만), 엔코더 치우침 ±0.05 rad, 발목 크랭크 게인 55 / 2.5.
- 같은 씨앗 43, 12,000 회, 원격 RTX 3090.

| 학습 마지막 200 회 넘어짐 종료 | 0.0021 | 0.0094 | 불합격 (시험은 더 어려운 무작위화 아래에서 잼) |

- 판정: 채택하지 않는다.
- 실기 실패 쪽 내성(낮은 게인·지연)은 크게 좋아졌다.
- 명령 추종(회전·진행 방향·서기)은 나빠졌다. 걷기 진행 방향 틀어짐은 8.6° → 33.1° 이다.
- 묶음 시험이라 원인을 나눌 수 없다.
- 가설 1: 게인 0.5 배 생존은 크랭크 55 덕이다 (0.5 배여도 27.5 > 기준선 22.3).
- 가설 2: 회전 퇴보는 지연·게인 무작위화 때문이다 (무작위화가 최대에 가까워진 6,000 회 이후에 시작).
- 후속 분리 비교는 다른 세션이 진행 중이다 (할 일 #151, #158, #159).

### 2-2. 확인한 사실

- VBUS·iqf 는 제어 응답에 없다. MIT Command 14 (파라미터 읽기) 로 따로 묻는다.
- Command 14 요청은 CAN 번호 `0x304` (= 3 << 8 | 모터 ID 4), 데이터 0 ~ 1 바이트 = 파라미터 번호 (작은 자리 먼저) 이다.
- 응답은 매뉴얼 표와 달리 **호스트 ID `0xFD`** 로 온다. 데이터 0 ~ 1 바이트 = 파라미터 번호, 4 ~ 7 바이트 = 32비트 실수 (작은 자리 먼저) 이다. 실측 예: `0x0FD 1C 70 00 00 71 BD 42 42` = VBUS 48.685 V.
- Command 14 는 펌웨어 RS04 0.4.1.29 이상이 필요하다. 이 모터는 응답한다. 새 매뉴얼은 `Motor_Spec/manuals/RS04_User_Manual_260713.pdf`, `RS03_User_Manual_261013.pdf` 에 있다.
- 정지 상태 VBUS 는 48.69 V 이다.

#### 2-2a. MIT 모드에서 Command 14 가 동작하는가 → 동작한다 (2026-10-19 확인)

사용자 질문 (2026-10-19): 모터가 MIT 모드인데도 파라미터를 묻는 Command 14 가 동작하나?

- VBUS 는 초당 약 100 번 읽는다 (전압 집중 측정을 켜면 약 200 번). 1 ms 안팎의 스파이크 최고값은 오실로스코프로만 볼 수 있다.

## 3. CAN 통신 (RobStride MIT, HUPHY `biped`)

원본: [[171_can_bus_budget_6motors]] §2 ~ §7, `System_ID/can_link/README.md`, HUPHY `docs/can_communication.md` (`origin/biped` `2fdc139`).

### 3-1. 프로토콜 사실 (매뉴얼 RS04 260713)

- 명령의 11비트 번호는 모터 ID 이다. 모터는 자기 번호의 프레임만 받는다.
- 상태 응답의 11비트 번호는 호스트 ID 이다. 모든 모터의 공장값은 `0xFD` 이다.
- 호스트 ID 는 Command 9 로 바꾼다. 프레임은 `[모터 ID] FF FF FF FF FF FF <새 호스트 ID> 01` 이다. F_CMD 자리에 새 값이 들어가는 명령이므로, 보내기 전에 바이트를 확인한다.
- private Type 18 (파라미터 쓰기) 은 전원이 꺼지면 사라진다 ("lost in power failure").
- `0x20xx` 파라미터는 저장 대상이다. MIT 저장 명령은 Command 12 (`FF FF FF FF FF FF FF F8`, 펌웨어 0.4.1.29 이상) 이다.
- Command 9 자체가 저장까지 하는지는 매뉴얼에 없다. 그래서 Command 9 → Command 12 → 전원 재투입 → `0x200A` 읽기로 확인한다.
- 같은 모터에 응답 전 프레임을 4 개 이상 연달아 보내면 버려진다. 3 개까지는 손실이 0 이었다 (2026-09-09 라즈베리파이 실측, `System_ID/rs_direct_socket.py` 주석). 원인은 모터 수신 버퍼(3 칸) 로 추정한다. 모터 내부는 확인하지 않았다.

### 3-2. 선 시간 예산 (1 Mbit/s, 한 버스 모터 6 개)

프레임 하나는 111 ~ 135 µs 이다.

| 모터당 주기마다 보내는 것 | 프레임/주기 | 선 70 % 기준 최대 주기 |
|---|--:|--:|
| 제어 + 응답 | 12 | 432 ~ 526 Hz |
| + 파라미터 1 개 읽기 | 24 | 216 ~ 263 Hz |
| + 전압·전류 둘 다 | 36 | 144 ~ 175 Hz |

- 2026-09-12 라즈베리파이 slcan 실측은 모터 6 개 한 주기 4.07 ms 였다. 병목은 선이 아니라 slcan 의 USB 1 ms 묶음이었다.

### 3-3. HUPHY `biped` 의 경과

- `a1b67b1` (2026-10-13) 까지: 몰아 보내기, 수거는 응답 **개수** 로 끝냄, 호스트 ID 설정 없음 (12 개 모두 `0xFD`).
- 그 시점 로봇 기록 분석 (`System_ID/can_link/results/`): 유실 2.2 ~ 3.5 %. 한 사건 뒤 오른다리 6 관절이 59 ~ 71 주기 연속으로 늦었다 (한 주기 밀림의 지속).
- `2fdc139` (2026-10-16 17:22) 에서 개발자가 고쳤다.
  - 응답 번호 충돌을 실측으로 확인했다 (양다리, 토크 0, 100 Hz). 몰아 보내기: 무응답 주기 39 ~ 43 %, 유실 5 ~ 6 %, 버스 오류 약 1,300. 하나씩 보내기: 무응답 0 %, 유실 0.2 %, 버스 오류 4. 주기는 89 → 95 Hz.
  - `--send-mode` 기본값을 `seq` 로 바꿨다.
  - 송신보다 먼저 도착한 응답을 그 주기의 무응답으로 세게 바꿨다 (`6535181`).
- **호스트 ID 분리는 `2fdc139` 기준으로 하지 않았다.** 근거: HUPHY `docs/can_communication.md` 313행 "지금은 안 함", 479행 체크하지 않은 할 일 "(선택) 모터마다 호스트 id 를 다르게". 그 뒤 실물에서 설정만 바꿨는지는 저장소로 알 수 없다. 로봇에서 `timeout 1 candump canr | awk '{print $2}' | sort | uniq -c` 로 응답 번호를 보면 판정된다.
- 호스트 ID 를 모터마다 다르게 주면 중재가 정상 동작한다. 그러면 몰아 보내기로 돌아가 하나씩 보내기보다 높은 주기를 낼 수 있다. 이 주장은 아직 실측하지 않았다.

### 3-4. 우리 작업공간 `System_ID/can_link/` (커밋 `3fa891d`)

- 시험 도구: `bus_probe.py` (힘 0 프레임만, 순차·몰아 보내기 비교, 오류 계수), `host_id_tool.py` (읽기 기본, 변경은 한 모터씩·확인 플래그 필수), `analyze_huphy_latency.py` (로봇 지연 기록 분석).
- 개선판 `huphy_patch/` 는 `a1b67b1` 기준이다. **`2fdc139` 에는 더 이상 적용되지 않는다** (`robstride/bus.py` 충돌). 갱신은 할 일 #157 이다.
- 개발자 전달 문서는 `System_ID/can_link/README.md` 와 [[124_huphy_handoff_findings]] 항목 1-3a 이다.
- HUPHY 저장소에는 커밋하지 않는다 (사용자 지시).

## 5. 함정 (다시 밟지 말 것)

- F_CMD 바이트: 특수 명령의 7번째 바이트가 `0xFF` 가 아니면 다른 명령이다. 2026-09-12 에 모터 12 개의 통신 방식을 바꿀 뻔했다.
- slcan 어댑터는 USB 가 다시 잡히면 장치 번호가 바뀐다. 항상 `/dev/serial/by-id/...` 경로로 연다.
- 3090 가상 머신에는 sudo 권한이 없다. CAN 을 올리는 명령은 사용자가 친다.
- 상태 확인으로 `pkill -f <패턴>` 을 쓰면 자기 셸을 죽일 수 있다. `pgrep -af "[b]ench_server"` 처럼 쓴다.
- 벤치 서버 재시작은 토크를 끈다. 사용 중이면 먼저 묻는다.
- HUPHY 로컬 저장소(`/home/syaro/external_repos/HUPHY`) 는 다른 가지에 체크아웃되어 있다. `git show origin/biped:<경로>` 로만 읽는다.
