## 왜 하는가 (한 문단)

지금 벤치의 통신 어댑터는 **초당 230~240개의 프레임**밖에 못 보냅니다. 그런데 프레임 하나를
주고받는 시간은 **0.93 밀리초**로 빠릅니다. 데이터를 0바이트로 줄여도 초당 프레임 수가 그대로
였으므로(240 대 230), 막는 것은 **글자 수가 아니라 프레임 하나당 드는 고정 비용**입니다.
프레임당 4.3 밀리초가 드는데, 이 어댑터가 붙은 USB 저속 구간의 한 칸이 1 밀리초이니
**한 프레임에 USB 칸 네 개**를 쓰는 셈입니다.

새 펌웨어(candleLight)는 **여러 프레임을 USB 패킷 하나에 묶어** 보냅니다. 즉 우리가 실측으로
확인한 바로 그 지점을 겨냥합니다. 글자 수를 줄이는 방향은 아무 소용이 없다는 것도 같은
측정으로 확인했습니다.

## 실행 가능한지 — 확인 끝난 것

| 확인 항목 | 결과 |
|---|---|
| 어댑터의 마이크로컨트롤러 | **STM32F042C6** (지금 펌웨어 소스의 링커 파일이 `STM32F042C6_FLASH.ld`) |
| 새 펌웨어에 맞는 대상 이름 | **`canable_fw`** (candleLight 의 STM32F042C6 대상) |
| 새 펌웨어 빌드 | ✅ 성공. 23,596 바이트 = 32 KB 중 71.8% |
| **되돌릴 펌웨어** | ✅ **지금 올라간 것과 같은 커밋(`9fddea4`)에서 빌드 성공**, 29,888 바이트 |
| 로봇 커널의 `gs_usb` | ✅ 이미 있음 — 새 펌웨어를 올리면 바로 잡힘 |
| `dfu-util` | 로봇에 없음 → 설치 파일을 옮겨 뒀습니다 |
| 파일 위치 (로봇) | `/home/syaro/System_ID/fw/` |

**되돌릴 수 없게 되는 경우는 하나뿐입니다** — BOOT 점퍼에 손이 닿지 않는 경우. STM32 의 DFU
부트로더는 **지울 수 없는 ROM 에** 있어서, 잘못된 펌웨어를 올려도 부트로더는 그대로 남습니다.
즉 **BOOT 점퍼로 다시 들어갈 수만 있으면 몇 번이든 되돌릴 수 있습니다.**

## 사용자가 먼저 확인해 주실 것 (여기서 막히면 진행 불가)

1. **어댑터에 BOOT 점퍼나 버튼이 있는지.** 케이스를 열어야 보일 수 있습니다. 사진에서 보이는
   점퍼는 종단저항(120 Ω)이라 다른 것입니다.
2. **여분 어댑터가 있는지.** 지금 이것이 유일한 통로입니다.

읽기 잠금이 걸려 있으면 실패합니다. 실패해도 괜찮습니다 — 같은 커밋에서 빌드한 파일이 이미
있습니다(`canable-9fddea4.bin`). 성공하면 그 둘을 비교해 볼 수 있어 더 확실합니다.

### 4단계 — 어떤 칩인지 눈으로 확인 (사람)

```bash

```

**128 KB(128*001Kg)로 나오면 멈추세요** — 그건 STM32F072 이고 다른 파일이 필요합니다.
(저에게 알려 주시면 그 대상으로 다시 빌드하겠습니다.)

# 딸린 시험 — 가상머신이 얼마나 먹는가

**이건 위 펌웨어 교체가 기대만큼 안 될 때만 하시면 됩니다.** 새 펌웨어로 초당 1000회가
넘게 나오면 가상머신은 애초에 문제가 아니었던 것이므로 이 시험이 필요 없습니다.

## 왜 하는가

로봇은 가상머신입니다(QEMU, 가상 CPU 4개, virtio 랜 = Proxmox 계열로 보임). USB 장치가
가상머신으로 넘어갈 때 매 전송이 하이퍼바이저를 왕복하는데, 이것이 프레임당 4.3 밀리초의
큰 몫일 수 있습니다. **같은 어댑터를 호스트에서 직접 재면 그 몫이 갈립니다.**

## 호스트에서 치실 명령

```bash
# 1. 가상머신에서 USB 어댑터를 뗀다 (웹 화면: VM → 하드웨어 → USB 장치 → 제거)
#    또는 명령으로 (VMID 는 로봇 가상머신 번호):
qm set <VMID> --delete usb0

# 2. 호스트에 도구가 있는지
which slcand cangen || apt install -y can-utils

# 3. 호스트에서 어댑터를 CAN 으로 올린다 (지금 로봇에서 하던 것과 같은 방식)
modprobe can slcan
slcand -o -c -s8 /dev/ttyACM0 can0
ip link set can0 up

# 4. 던지기 시험 — 모터가 쓰지 않는 번호(0x123)로만 보낸다.
#    다른 노드가 확인응답은 해주므로 버스 오류가 안 나고, 번호가 달라 모터는 무시한다.
#    모터 토크는 지금 꺼져 있다.
time cangen can0 -g 0 -n 2000 -I 123 -L 8
```

마지막 줄의 **걸린 시간을 알려 주시면** 제가 초당 몇 개인지 계산해 비교하겠습니다.
지금 가상머신 안에서 잰 값은 **초당 230.5개**(같은 8바이트 프레임)입니다.

* 호스트에서도 230 근처면 → **어댑터/펌웨어 문제**, 가상머신은 무죄
* 호스트에서 훨씬 빠르면 → **가상머신 통과가 범인**, 제어를 실물 기판으로 옮기는 것이 답

## 끝나면 되돌리기

## 나중에 — 라즈베리파이 전용 기판

사용자가 "나중에 로봇 전용으로 라즈베리파이를 셋업하겠다"고 하셨습니다. 그때 바뀌는 것:

* 가상머신 통과가 사라집니다 (위 시험의 답이 무엇이든 이 몫은 없어짐)
* **SPI 연결 CAN 이 그때부터 가능해집니다** — 가상머신에는 SPI 버스가 없어서 지금은 불가
### 이미 가지고 있는 8 MHz MCP2515 로 할 수 있는가 — 계산과 답

앞서 "최소 8조각"이라고 적었던 것을 **정정합니다. 하드웨어 최소는 5조각**입니다. 결론(1 Mbps
불가)은 그대로지만 숫자를 바로잡습니다.

MCP2515 는 시간조각 하나가 `2 x (BRP+1) / 크리스털` 이고, 비트 하나는
`1(동기) + 전파(1~8) + 위상1(1~8) + 위상2(2~8)` = **최소 5조각, 최대 25조각**입니다.

| 크리스털 | 가장 짧은 조각 | 5조각(이론 최소) | **8조각(표준)** | 1 Mbps 에 필요한 조각 |
|---|---|---|---|---|
| **8 MHz** | 250 ns | 800 kbps | **500 kbps** | **4개 → 불가** |
| 16 MHz | 125 ns | 1600 kbps | 1000 kbps | 8개 → 가능 |
| 20 MHz | 100 ns | 2000 kbps | 1250 kbps | 10개 → 가능 |

**8 MHz 로 1 Mbps 는 성립하지 않습니다.** 4조각이 필요한데 하드웨어 최소가 5조각입니다.
800 kbps 는 이론상 되지만 조각이 5개뿐이라 표본 지점을 제대로 놓을 여유가 없습니다.
**쓸 수 있는 답은 500 kbps** 입니다(8조각, 표본 지점 87.5%, 여유 정상).

### 그런데 500 kbps 로 낮춰도 우리는 아무것도 잃지 않습니다

지금 1 Mbps 에서 **선의 6% 만 쓰고 있습니다**(초당 230회 × 왕복 2프레임). 막던 것은 선이
아니라 어댑터였기 때문입니다.

| 통신 속도 | 프레임 하나(8바이트, 채움 포함 약 130비트) | 왕복 한 번 | 선이 낼 수 있는 초당 왕복 |
|---|---|---|---|
| 1 Mbps | 0.13 ms | 0.26 ms | 약 3,800회 |
| **500 kbps** | 0.26 ms | 0.52 ms | **약 1,900회** |

목표가 초당 1,000회이므로 **500 kbps 에서도 두 배 가까운 여유**가 있습니다.

### 모터 통신 속도는 공식적으로 바꿀 수 있습니다

RS04 매뉴얼 24쪽, **통신 종류 23 "모터 통신속도 변경 프레임(전원 재투입 시 적용)"**:

* 29비트 확장 프레임(= 개별 규약). `Bit28~24 = 0x17`, `bit23~8 = 주 CAN 번호`,
  `bit7~0 = 대상 모터 번호`
* 8바이트 자료의 **F_CMD 자리**가 속도 선택: **`01`=1M, `02`=500K, `03`=250K, `04`=125K**
* **전원을 껐다 켜야 적용됩니다**

HUPHY 에는 아직 이 명령이 없습니다(개별 규약 전환 `set_protocol` 과 파라미터 읽기·쓰기는
있음). 필요해지면 새 가지에서 추가하고 장부에 남깁니다.

**바꿀 때 주의할 것**

* 모터를 바꾸면 어댑터도 같이 바꿔야 합니다. 안 그러면 그 순간 통신이 끊깁니다.
* 모터 한 대는 바뀌고 다른 한 대는 안 바뀌면 **버스가 갈라집니다.** 한 대씩 바꾸고 매번
  확인하세요.
* 되찾는 법은 속도를 하나씩 시도해 보는 것입니다(1M → 500K → 250K → 125K).

### 정리 — 순서

1. **USB 어댑터 펌웨어 교체** (이미 준비 완료, 비용 0원). 이것으로 초당 1,000회가 나오면
   **SPI 보드가 아예 필요 없습니다.**
2. 라즈베리파이로 옮기기 — 가상머신 통과가 사라집니다. 이 단계에서도 USB 어댑터로 충분할
   가능성이 높습니다.
3. 그래도 모자랄 때만 SPI 보드. 가진 8 MHz 품을 쓰려면 **버스 전체를 500 kbps 로** 내리면
   됩니다(위 계산상 손해 없음). 새로 산다면 16 MHz 이상 또는 **MCP2518FD**.
4. 크리스털만 8 → 16 MHz 로 바꾸는 것도 방법입니다(부품값은 싸지만 표면실장 납땜).

# USB 대 SPI — 어느 쪽이 유리한가 (2026-09-09)

사용자 질문: "USB(펌웨어 수정이 될 수도 안 될 수도 있음)와 SPI(8 MHz 판) 중 어느 게 유리한가?
어느 쪽이 데이터가 더 안정한가?"

## 결론

**우리 목적(모터 파라미터 측정)에는 USB + 새 펌웨어가 낫습니다.** 특히 **자료의 질**에서
차이가 큽니다. SPI 의 장점은 8 MHz 판에서는 대부분 사라집니다.

다만 **완성된 로봇의 상시 제어**라면 이야기가 다릅니다 — 아래 마지막 항목.

## 1. 시각 정확도 — 여기서 승부가 갈립니다

파라미터를 알아내는 일은 "언제 얼마나 움직였나"를 재는 일입니다. **몇 시에 재었는지가
흔들리면 그만큼 값이 틀어집니다.** 30 헤르츠 성분에서 0.5 밀리초는 위상 5.4도에 해당합니다.

| 방식 | 시각을 누가 찍나 | 흔들림(표준편차) |
|---|---|---|
| **지금(문자열 방식)** | 컴퓨터가 받은 뒤 | **113 µs** |
| **USB + 새 펌웨어** | **어댑터가 프레임을 받는 순간** | **6.8 µs** |
| SPI (MCP2515) | 컴퓨터가 인터럽트 처리 후 SPI 로 읽은 뒤 | 컴퓨터 쪽이므로 위 113 µs 와 같은 성격 |

새 펌웨어는 **어댑터 안에서** 시각을 찍습니다(받기 인터럽트 안). 컴퓨터까지 오는 길의
흔들림이 시각에 섞이지 않습니다. 반면 MCP2515 는 시각을 찍는 곳이 결국 컴퓨터라, 인터럽트
지연과 SPI 읽기 시간이 그대로 시각에 실립니다.

**즉 자료의 안정성만 놓고 보면 USB + 새 펌웨어가 SPI 보다 낫습니다.** 직관과 반대이지만,
시각을 어디서 찍느냐가 연결 방식보다 중요하기 때문입니다.

## 2. 선 점유율 — 8 MHz 는 500 kbps 를 강제하고, 그게 발목을 잡습니다

8 MHz 크리스털은 1 Mbps 가 불가능하므로 **버스 전체를 500 kbps 로** 내려야 합니다. 그러면
프레임 하나가 두 배로 길어집니다(240 → 480 마이크로초는 왕복 기준).

| 상황 | 1 Mbps | 500 kbps |
|---|---|---|
| 모터 1대, 초당 1000회 (**지금 측정에 필요**) | 24~27% | 48~54% |
| 모터 2대, 초당 1000회 | 48~54% | **96~108% ← 불가** |
| 모터 12대, 초당 100회 (완성 로봇) | 29~32% | **58~65% ← 빠듯** |

**모터 한 대를 재는 지금 일에는 500 kbps 로도 됩니다.** 그러나 **두 대를 함께 초당 1000회로
돌리는 것은 500 kbps 에서 성립하지 않고**, 완성된 12관절 로봇에서도 선 점유가 60% 대로 올라
여유가 없습니다.

## 3. 나머지 항목

| 항목 | USB + 새 펌웨어 | SPI (8 MHz MCP2515) |
|---|---|---|
| 왕복 시간 | 지금 0.93 ms. 새 펌웨어로 줄 여지 있으나 **USB 저속 구간의 1 ms 칸이 바닥** | 약 0.6~0.7 ms (500 kbps 기준). 조금 낫다 |
| 초당 처리량 | 묶어 보내기로 크게 개선 예상, 다만 **주고받기 방식에서는 왕복 시간이 상한**(약 1000회) | 라즈베리파이에서 초당 3400개 보고. 선이 1900회로 먼저 막힘 |
| 받기 버퍼 | STM32 안에서 여러 개 + USB 묶음 | **2개뿐** — 몰리면 넘침(오류로 표시되긴 함) |
| 컴퓨터 부담 | 낮음 | 드라이버 인터럽트가 코어 하나의 71.5% 까지 쓴 사례 있음 |
| 지금 쓸 수 있나 | **준비 끝. BOOT 점퍼만 확인되면 오늘** | **아니오** — 가상머신엔 SPI 가 없어 라즈베리파이 이후 |
| 되돌리기 | 파일 하나로 원상복구 | 배선·설정 되돌리기 |
| 모터 설정 변경 | 불필요 | **필요**(전 모터 500 kbps, 전원 재투입, 한 대만 바뀌면 버스 갈라짐) |

## 4. 그래도 SPI 가 나은 경우

**완성된 로봇을 상시 제어할 때**입니다. USB 는 "최선을 다하는" 방식이라 시간을 보장하지
않습니다 — 컴퓨터가 바쁘거나 다른 USB 장치가 붐비면 늦어집니다. SPI 는 전용 선이라 그런
간섭이 없습니다.

다만 그때도 **8 MHz 판은 권하지 않습니다.** 12관절을 500 kbps 로 돌리면 선 점유가 60% 대이고,
CAN 은 보통 그 아래로 유지합니다. 그 단계에서는 **16 MHz 이상 또는 MCP2518FD**, 또는 기판에
내장된 CAN 을 쓰는 것이 맞습니다.

## 5. 그래서 순서

1. **USB + 새 펌웨어를 먼저.** 준비 끝났고, 되돌리기 쉽고, **자료의 질이 가장 좋아집니다.**
2. 라즈베리파이로 옮기기. 가상머신 통과가 사라집니다.
3. 그래도 모자라면 SPI — 그때 **16 MHz 이상**을 구합니다. 가진 8 MHz 판은 급할 때
   모터 한 대 재는 용도로는 쓸 수 있습니다.

**아직 확인 안 된 것**: 새 펌웨어가 실제로 얼마나 빨라지는지는 **우리 장비에서 재 봐야
압니다.** 위 6.8 µs 와 묶어 보내기는 만든 쪽이 밝힌 값이고, 우리 조건(가상머신 통과 포함)
에서의 결과는 다를 수 있습니다.
