# HUPHY 개발자에게 — 통신선(CAN) 수신·송신 계층에서 찾은 것과, 그대로 복사해 쓸 수 있는 개선판

> **읽는 분:** HUPHY `biped` 가지를 만드시는 분
> **쓴 사람:** Human-Pygmalion 저장소 (실제 모터·로봇 기록을 분석한 쪽)
> **날짜:** 2026-10-16
> **기준:** `origin/biped` = `a1b67b1` (파일·줄 번호는 전부 이 커밋 기준)
> **HUPHY 저장소는 건드리지 않았습니다.** 개선판은 이 폴더(`System_ID/can_link/huphy_patch/`)에만 있고,
> 파일 두 개를 복사하시거나 `PATCH.diff` 를 적용하시면 됩니다.
>
> 쉬운 말로 씁니다. 처음 나오는 줄임말은 풀어 씁니다.
> - **중재(arbitration)**: 두 장치가 동시에 말하기 시작했을 때 11비트 번호가 **작은 쪽이 이기는** 규칙. 번호가 같으면 가릴 수 없습니다.
> - **응답 번호 = 호스트 번호(host id)**: 모터가 상태 응답에 실어 보내는 11비트 번호. 모터의 파라미터 `0x200A CAN_MASTER`, 공장값 253(`0xFD`).
> - **한 주기 밀림(one-cycle slip)**: 이번 주기에 와야 할 응답이 다음 주기에 처리되어, 값이 한 주기 묵은 채로 "정상"으로 보이는 상태.
> - **커널 도착 시각(kernel timestamp)**: 리눅스 커널이 프레임을 받은 순간의 시각. 파이썬이 나중에 꺼낸 시각이 아닙니다.

## 0. 요약 (세 줄)

1. **수거(`collect`)가 "프레임 몇 개 왔나"로 끝나서, 응답이 한 번만 늦어도 한 주기 밀림이 끝없이 이어집니다** — 가짜 버스에서 재현했고(54주기 중 54주기가 계속 밀림), 실물 기록에서도 한 번의 사건 뒤에 59~71주기 연속으로 늦는 구간이 보입니다. 개선판은 다음 주기에 바로 복구됩니다(54주기 중 0주기).
2. **모터 12개가 전부 같은 응답 번호 `0xFD` 로 답합니다**(호스트 번호를 바꾸는 코드·절차가 없음). 같은 번호끼리는 중재로 가려지지 않아 충돌(비트 오류) 가능성이 있고, 실물 기록의 손실 2.2~3.5 % 가 모터 1개짜리 벤치(0.009 %)보다 훨씬 큰 것과 맞지만 **아직 로봇에서 재 보지 못한 가설**입니다. 재는 도구와 한 번에 한 모터씩 바꾸는 절차를 같이 드립니다.
3. **파일 두 개(`canbus.py`, `robstride/bus.py`)를 복사해도 기본 동작은 HUPHY 자체 시험을 그대로 통과합니다**(아래 6-3). 모터별 완료 판정과 커널 도착 시각은 기본으로 들어가고, 수신 스레드·미응답 한도·모터별 응답 번호는 **켜는 항목**입니다 — 켜는 순서와 근거는 3-4절 "권장 설정"에 있습니다.

## 2. 발견 상세

### 2-1. ★★★ 수거가 프레임 개수로 끝나서, 한 번 늦은 응답이 한 주기 밀림을 영구히 남깁니다

**무엇이**

`RobStrideBus.collect()` 가 `canbus.drain(expect=N)` 을 부르고, `N` 개가 차면 끝냅니다. 어느 모터의 응답인지는 보지 않습니다.
직전 주기의 늦은 응답이 큐에 남아 있으면 그것도 한 개로 세어져서, 이번 주기의 **마지막 응답 하나가 큐에 남습니다**. 다음 주기에도 똑같이 반복됩니다.

```python
# src/huphy/motors/robstride/bus.py:286-310  (a1b67b1)
frames = self.bus.drain(expect=expect, timeout_s=wait)     # N개 차면 끝 -- 누구 것인지 안 봄
seen = set()
...
for f in frames:
    ...
    self._states[mid] = MotorState(..., stamp=now)         # 304: 도착 시각이 아니라 수거 시각
    seen.add(mid)
return [mid for mid in self.motor_ids if mid not in seen]  # 310: 누가 왔나만 봄, 언제 왔나는 안 봄
```
`robots/leg.py:721` 이 `expect=len(self._awaiting)` 을 넘기고, `canbus.py:440`(`len(out) >= expect`)과 `:487-499`(`_drain_queue`)가 개수로 끝냅니다.

**왜 문제인가**

- 한 번 늦으면 **그 뒤 모든 주기**에서 보내는 순서가 가장 늦은 모터(오른다리면 `ankle_b`)의 관절 값이 **한 주기(100 Hz 에서 10 ms) 묵은 값**입니다. 그런데 `collect()` 의 반환값(응답 없는 모터 목록)은 비어 있어서 **정상으로 보입니다.**
- 저절로 풀리지 않습니다. 응답 하나가 진짜로 사라지면 그때 풀립니다.
- 지연 기록기는 이 응답들을 `late` 로 표시하지만 원인을 알려 주지 않습니다.

**재현 (가짜 버스, 시계 가상, 하드웨어 없음)** — `tests/test_collect_slip.py`

모터 6개(번호 7~12), 100 Hz, 수거 창 4 ms. 9번 모터의 응답이 5번째 주기에서 **딱 한 번** 3 ms 늦음(창을 3 ms 넘김).

| | 원본 `a1b67b1` | 개선판 |
|---|---|---|
| 그 뒤 54주기 중 값이 묵은 주기 | **54** (끝까지) | **0** |
| 복구되는 주기 | 안 풀림 | 바로 다음 주기 |
| 묵은 값을 가진 모터 | 12번(보낸 순서 꼴찌) 54주기 | 없음 |
| 늦게 온 모터를 바꿔 6번 반복 | 6번 모두 54/54 | 6번 모두 0/54 |

**실물 기록에서 (HUPHY `archivedlogs`, `analyze_huphy_latency.py` 결과)**

"늦음(late)이 이어진 길이"는 같은 관절에서 **연속된 수거 주기마다** 늦음 행이 있는 횟수입니다. 서로 무관한 늦음이면 1~2 에서 끝나야 합니다.

| 기록 | 조건 | 다리별 가장 긴 연속 늦음 (주기) | 늦음 행 중 응답이 4 ms 창 안에 온 것 |
|---|---|---|---|
| `test_zerolatency(gscan r).csv` | 200 Hz, 창 4 ms | 오른 **21**, 왼 11 | 오른다리 46~58 % |
| `005054msgscan(r)latency.csv` | 100 Hz, 창 4 ms | 오른 **49**, 왼 **82** | 오른다리 38~45 % |
| `00503latency4ms.csv` | 50 Hz, 창 4 ms | 오른 **59~71** (여섯 관절 전부, 첫 주기부터 같은 사건) | 오른다리 43~86 % |

마지막 줄이 가장 깔끔합니다. 오른다리 여섯 관절이 **첫 주기에서 함께 밀리기 시작해 1.2~1.4초(59~71주기) 동안 연속으로 늦었고**, 그 늦은 행의 지연은 1~4 ms 입니다(오른다리 `hip_pitch` 의 60주기 연속 늦음 구간 지연 앞쪽 값: 2.2, 1.1, 1.7, 1.0, 1.1, 1.4 ms ...). 응답이 느려서 창을 넘긴 것이 아니라, **개수가 먼저 차서 남겨진** 것입니다.
"늦음 행의 약 40~60 % 가 창(4 ms) 안에 도착"한 것도 같은 방향의 증거입니다. 나머지 늦음(창을 실제로 넘긴 것)은 이 방식으로 설명되지 않으니, **모든 늦음이 이 원인이라고는 주장하지 않습니다.**

또 하나: 늦음의 비율이 **보내는 순서를 따라 단조롭게 늘어납니다**(오른다리 200 Hz: `hip_pitch` 0.9 % → `ankle_b` 3.9 %; 100 Hz: 2.8 % → 22.2 %). 개수로 끝나면 남겨지는 것은 항상 순서상 뒤쪽 모터이므로 이 모양과 맞습니다.
그리고 응답이 한 수거에서 빠진 관절은 **다음 주기에 늦음으로 나타납니다**(오른다리에서 빠진 주기의 다음 주기에 늦음이 나타날 확률: 13~33 % (200 Hz), 46~64 % (100 Hz). 같은 관절의 평소 늦음 비율은 0.9~3.9 % (200 Hz), 2.8~22 % (100 Hz)). 사라진 것이 아니라 한 주기 뒤에 처리된 것입니다.

**어떻게 고치나** — 완료를 모터별로 판정합니다 (`huphy_patch/robstride/bus.py`).

```python
# 모터는 "이번 송신 시각 이후에 도착한 응답(커널 도착 시각)"을 받았을 때 끝난 것.
# 송신 이전에 도착한 프레임은 상태에 반영하되 late 로만 기록 -- 끝 판정에 안 씀.
if sent is not None and stamp >= sent:
    fresh[mid] = stamp
else:
    late[mid] = ...          # last_collect.late, 나이는 last_collect.late_age_s
...
pending = {m for m in awaited if m not in fresh}
if not pending: break         # 전부 새 응답이면 즉시 종료 (정상 주기는 창을 다 쓰지 않음)
```
반환값은 그대로(응답이 없는 모터 번호 목록)이고, 자세한 것은 새 속성 `bus.last_collect` 에 있습니다(`awaited / fresh / missing / late / late_age_s / fresh_age_s / skipped / waited_s / timed_out`).
한 모터의 응답이 여러 개면 **가장 늦게 도착한 것**을 상태로 씁니다. 상태는 시간을 거슬러 가지 않습니다.

> **한계 (정직하게):** MIT 응답에는 순번이 없어서, 왕복이 주기보다 길면(응답이 다음 송신 뒤에 도착) 직전 명령의 응답을 이번 것으로 오인합니다. 이것은 원본도, 개선판도 못 가립니다. 정상 왕복은 1~4 ms 라 100 Hz(10 ms)에서는 드뭅니다.

### 2-2. ★★ 모든 모터가 같은 응답 번호 `0xFD` 로 답합니다

**무엇이**

매뉴얼(RS04 User Manual 260713, 6.1)의 상태 응답은 11비트 번호가 **호스트 번호**이고, 모터 번호는 데이터 0번 바이트에 들어 있습니다. 호스트 번호는 파라미터 `0x200A CAN_MASTER`(공장값 253 = `0xFD`)입니다.
HUPHY 에는 이것을 바꾸는 코드가 없습니다.

```python
# src/huphy/motors/robstride/tables.py:197
CMD_SET_HOST_ID = 0x01   # Command 9. F_CMD = 새 호스트 ID (응답 프레임의 11비트 ID)
# 호출부 0.  commissioning.py 에도, docs/motor_setup.md 에도 없음 (모터 번호 변경·프로토콜·영점만 있음)
```
그래서 한 버스에 모터 6개가 같은 번호 `0xFD` 로 답하고, 모터 번호는 `bus.py:320` 에서 `data[0]` 으로만 구분합니다.

**왜 문제인가**

- 번호가 같은 두 프레임은 **중재로 가려지지 않습니다.** 둘이 정확히 같은 순간에 말하기 시작하면 데이터 구간에서 비트가 어긋나 오류 프레임이 나고 둘 다 다시 보냅니다(표준 동작).
- 호스트의 명령(번호 1~12)은 응답(`0xFD`)보다 번호가 작아서 **항상 이깁니다.** 6개 명령을 연달아 보내면 응답 6개가 모두 "명령이 끝나기를 기다리다가" 마지막 명령이 끝나는 순간 **같이** 말하기 시작할 조건이 됩니다.
- 이 폴더의 가짜 버스에서 "같은 번호가 동시에 시작하면 충돌"이라는 **보정 안 한 장난감 모델**을 돌리면 손실이 36~47 % 로 나오는데, 실물은 2~4 % 입니다. 즉 실물에서는 모터마다 처리 시간이 달라 대부분 엇갈릴 가능성이 큽니다. **충돌이 있는지, 얼마나인지는 로봇에서 재야 압니다.**

**지금 있는 수치**

| | 값 | 출처 |
|---|---|---|
| 모터 1개 벤치(응답 번호 충돌 불가), 200 Hz, 제어 1 + 전압 읽기 1, 74,837주기 | 상태 응답 손실 **0.009 %** (7건) | `docs/171` 1절 |
| 로봇 오른다리 6개, 200 Hz, 창 4 ms | 손실 **3.52 %**, 왼다리 2.76 % | 아래 6절 |
| 로봇 오른다리 6개, 100 Hz, 창 4 ms | 손실 **3.40 %**, 왼다리 2.16 % | 아래 6절 |

로그만으로는 충돌 때문인지 가려지지 않습니다. 이유 두 가지: ① 손실(`lost`) 행에는 **시각이 없어서**(파일 끝에 개수만큼 적힘) 어느 주기에서 났는지 모릅니다. ② 늦음은 2-1 의 개수 판정으로 설명되는 부분이 큽니다.
다만 **양다리에서 같은 주기에 같이 늦는 경향**이 있습니다(오른·왼 동시 늦음 36회 vs 서로 무관하다면 5.0회, 200 Hz). 서로 다른 선에서 동시에 일어나므로 이 부분은 **선 위의 충돌이 아니라 컴퓨터 쪽 일시 정지**(스케줄링)입니다.

**어디**: `tables.py:197`(상수만), `commissioning.py`(호출부 없음), `docs/motor_setup.md`(없음), `bus.py:320`(`data[0]` 으로만 구분).

**어떻게 고치나**

1. 모터마다 호스트 번호를 따로 줍니다(5절). 번호가 작은 쪽이 이기고, 진 쪽은 오류 없이 바로 뒤에 보냅니다.
   *원본 코드는 이 변경과 무관하게 그대로 동작합니다* — 모터 번호를 `data[0]` 으로 구분하므로 응답 번호가 바뀌어도 읽힙니다.
2. 개선판은 `reply_ids={모터번호: 호스트번호}` 를 받아 **번호로 모터를 확정**하고(`data[0]` 과 어긋나면 버리고 `bus.link.id_mismatch` 로 셈), 옵션으로 커널 필터(`kernel_filter=True`)를 겁니다.

```python
bus = RobStrideBus(
    CanBus("canr", reader=True),
    motors,
    drain_s=0.004,
    reply_ids={7: 0x70, 8: 0x71, 9: 0x72, 10: 0x73, 11: 0x74, 12: 0x75},
    kernel_filter=True,       # 아직 안 바꾼 모터가 있으면 0xFD 도 자동으로 열어 둠
)
```
응답 번호가 **다른 모터의 명령 번호와 같으면 거부**합니다(`ValueError`). 그 번호로 온 프레임을 그 모터가 명령으로 받아들일 수 있기 때문입니다.

### 2-3. ★★ 모터 하나에 응답 없는 명령이 3개를 넘으면 모터가 버리는데, 호스트가 한도를 모릅니다

**무엇이**: 2026-09-09 실측(`System_ID/rs_direct_socket.py` 주석): 한 모터에 3개 연달아 보내면 손실 0, **4개 연달아는 22 % 를 잃음**, 모터 둘에 3개씩 6개는 손실 0. 모터 쪽 수신 칸이 3개라는 추정입니다(모터 내부는 확인 못 함).
`send_mit` 는 응답을 못 받은 명령이 몇 개 쌓였는지 보지 않습니다(`bus.py:207-238`).

**왜 문제인가**: 모터가 느려지거나 응답이 계속 늦으면 매 주기 1개씩 쌓여 4번째부터 버려집니다. 버려진 명령은 아무 표시 없이 사라집니다.

**재현** (모터 1개의 응답이 35 ms = 3.5주기 늦음, 100 Hz, 60주기) — `tests/test_collect_slip.py`

| | 원본 | 개선판(`max_outstanding=2`) | 개선판(기본, 꺼짐) |
|---|---|---|---|
| 모터에 쌓인 미응답 최대 | **3** | **2** (`max_outstanding=2`) | 3 (기본) |
| 모터 수신 칸이 버린 명령 | **15 / 60** | **0** | 15 |
| 그 모터에 보낸 명령 | 60 | **24** (36 건너뜀) | 60 |
| 나머지 5개 모터 | 항상 응답 | 항상 응답 | 항상 응답 |

**어떻게 고치나**: `max_outstanding`(**기본 꺼짐**, 켤 때 권장 2, 최대 3) 개의 미응답이 쌓인 모터에는 **이번 주기 명령을 보내지 않고 셉니다**(`bus.link.skipped_commands`, `last_collect.skipped`).
**동작이 바뀌는 곳입니다:** 건너뛴 주기에는 그 모터에 새 목표값이 전달되지 않습니다. 모터는 마지막으로 받은 MIT 명령(목표각·게인·토크)을 유지하므로 토크가 갑자기 0 이 되지는 않습니다.
기록은 `outstanding_ttl_s`(기본 50 ms)가 지나면 버려져서, 죽은 모터에도 주기적으로 다시 시도합니다. `enable/disable/clear_fault` 는 이 한도를 **받지 않습니다**(끄는 명령은 항상 나감 — 시험으로 확인). 켜기: `max_outstanding=2` (기본은 꺼짐 = 원본 동작).
부수 효과: 죽은 모터가 있어도 매 주기 창을 통째로 기다리지 않습니다(보내지 않았으니 기다리지 않음. 무응답 보고는 그대로).

### 2-4. ★★ 프레임 도착 시각이 커널 시각이 아니라 파이썬이 꺼낸 시각입니다

**무엇이**: `CanFrame.stamp` 는 `_frame_of` 안의 `time.monotonic()`(`canbus.py:509`)입니다. python-can 이 주는 커널 도착 시각(`msg.timestamp`)은 버려집니다. 수신 스레드는 기본 꺼짐(`canbus.py:200`)이라, 켜지 않으면 `stamp` 는 **수거를 부른 시각**입니다(`bringup.py:184` 는 양다리 모드에서 `reader=True` 로 켭니다).

**왜 문제인가**: 도착 시각이 "읽은 시각"이면 "이번 송신 이후에 왔나"를 가릴 수 없어서 2-1 의 고침이 성립하지 않습니다. 스레드가 켜져 있어도 스레드가 늦게 깨어나면(파이썬 전역 잠금, 스케줄러) 지연이 부풀려 보입니다.

**재현** — 프레임이 도착한 뒤 30 ms 동안 아무도 읽지 않다가 읽음:

| | `stamp` − 송신 시각 |
|---|---|
| 원본 | **30.2 ms** (읽은 시각) |
| 개선판 | **0.64 ms** (도착 시각) |

**어떻게 고치나**: `msg.timestamp`(커널 벽시계)를 `time.monotonic()` 기준으로 옮깁니다. 커널 시각이 없거나 터무니없으면 읽은 시각을 쓰고 `counters.stamp_fallbacks` 로 셉니다(0 이어야 정상).

```python
cand = ts - (time.time() - now)               # 벽시계 -> 단조시계
stamp = min(cand, now) if now - 5.0 <= cand <= now + 0.001 else now   # 아니면 읽은 시각 + 셈
```
도착 시각은 수신 스레드 유무와 무관하게 커널 시각입니다. 수신 스레드(`reader=True`)는 **기본 꺼짐**(원본과 같음)이고 켜는 것을 권장합니다(3-4절). 양다리 모드(`bringup.py:184`)는 원래 켜져 있습니다.

### 2-5. ★ 상태의 `stamp` 가 수거한 시각입니다

`bus.py:304` 가 `MotorState(..., stamp=now)` 로 넣는데 `now` 는 수거 시작 시각(`:289`)입니다. 응답이 5 ms 전에 도착했어도 나이가 0 으로 보입니다. `MotorState.age()` 와 `leg.py:787`(`link_status`)이 이 값을 씁니다.
개선판은 **프레임의 도착 시각**을 넣습니다(`MotorState.stamp` 의 문서 "`time.monotonic()`" 과 같은 기준).

### 2-6. ★ 오류 프레임을 합계로만 셉니다

`canbus.py:157,357,451` 은 `error_frames += 1` 만 합니다(큐에 안 넣는 것은 맞습니다 — 응답으로 오인되기 때문). 어떤 오류인지 모르면 충돌 가설을 확인할 수 없습니다.
개선판은 `counters.error_classes` 에 종류별로 셉니다: `bus_error`(선 위 비트·채움·형식 오류, 충돌이면 여기), `lost_arbitration`(송신 중 중재에서 짐), `controller`(수신 넘침·경고·패시브 등 세부 포함), `protocol`(세부: `bit`, `form`, `stuff`, `bit0`, `bit1`), `bus_off`, `no_ack` 등.
소켓에 `CAN_RAW_ERR_FILTER = CAN_ERR_MASK` 를 직접 걸어 python-can 버전과 무관하게 받습니다.
`as_fields()` 는 **원본 그대로** 두었고(키 집합을 고정하는 시험이 있습니다), 새 항목은 `error_fields()` 에 있습니다. 텔레메트리에 싣으시려면 `{**c.as_fields(), **c.error_fields()}` 로 합치십시오.
참고: 오류 프레임은 gs_usb(candleLight)에서만 나오고 slcan 은 만들지 않습니다(원본 주석과 같음). 커널 쪽 누적은 `ip -details -statistics link show <채널>` 의 `bus-errors / arbit-lost / error-warn / error-pass / bus-off / re-started` 에 있습니다 — `bus_probe.py` 가 전후 차이를 같이 기록합니다.

관절별 제때/늦음/유실 %, 지연 백분위수, **연속 늦음 길이**, 같은 주기에 여러 관절이 같이 늦는 정도(독립일 때의 기대값·순환 이동 순열 검정), 두 다리의 동시 늦음, 보내는 순서별 비율을 냅니다. 결과는 `results/analysis_*.json|txt`, 나머지 네 기록은 `results/supplementary/`.

### 4-2. 버스 측정 — `bus_probe.py`

보내는 프레임은 **영 이득 MIT 프레임**(kp = kd = 토크 = 0, 보내기 전에 비트 단위로 검사)과 **Command 14 읽기**뿐입니다. 활성화·정지·영점·번호·프로토콜 프레임은 이 파일에 없습니다(시험이 소스 구문 수준으로 확인).
주의: **활성화된(토크 켜진) 모터에 영 이득 프레임을 보내면 힘이 빠집니다.** 첫 단계에서 모터마다 한 번 물어 `Motor mode` 로 답하면 중단합니다(`--allow-enabled` 로만 무시).

```bash
# 하드웨어 없이 형식 확인 (가짜 버스; 숫자는 측정이 아님)
python3 bus_probe.py --fake --ids 7,8,9,10,11,12 --rates 100,200,300,500 --duration 2 --param vbus

# [로봇] 한 다리 (HUPHY 를 먼저 멈추고 토크를 끈 상태에서. 같은 선을 동시에 쓰면 서로 방해함)
python3 bus_probe.py --channel canr --ids 7,8,9,10,11,12 --model-map 9:RS03,11:RS03,12:RS03 \
       --mode both --rates 100,200,300,500 --duration 10 --param vbus
python3 bus_probe.py --channel canl --ids 1,2,3,4,5,6 --model-map 3:RS03,5:RS03,6:RS03 --mode pipelined --rates 100,200 --duration 10
```
- `sequential`: 하나 보내고 그 응답을 기다린 뒤 다음 모터 / `pipelined`: 전부 연달아 보내고 모았다가 다음 주기(HUPHY 방식).
- 모터별: 왕복 시간 중앙값·99번째 백분위수·최대(송신 직전 `time.time()` → 커널 도착 시각), **제때**(같은 모터에 다음 송신이 나가기 전에 도착) / **늦음**(다음 송신 뒤에 도착) / **유실**(50 ms 안에 안 옴), 응답 번호별 횟수(`reply_id_histogram` — 전부 `0xFD` 면 `shared_reply_id: true`), 오류 프레임 종류별, 커널 오류 카운터의 전후 차이(`ip -details -statistics` 와 `/sys/class/net/<채널>/statistics`).
- 모터 하나당 미응답 3개를 넘기지 않습니다(`--max-outstanding`, 최대 3). 못 보낸 횟수는 `skipped_by_outstanding_limit`.
- `--param vbus` 는 모터마다 주기당 Command 14 읽기를 하나 더 보냅니다(`vbus,iqf,mechpos,mechvel` 가능).
- 결과 JSON: `results/probe_<채널>_<시각>.json`, 레이트마다 한 줄 요약.

**해석표** (로봇에서 번호가 같은 상태와 모터별 번호 상태를 각각 재서 비교):

| 관찰 | 뜻 |
|---|---|
| 번호를 바꾸면 `bus-errors`·`error_frames.bus_error` 와 유실이 함께 줄어듦 | 같은 번호 충돌이 원인 → 2-2 확정 |
| 번호를 바꿔도 변화 없음, 오류 카운터 0 | 충돌이 아님 → 2-1 수정과 컴퓨터 쪽 일시 정지를 먼저 의심 |
| `sequential` 은 깨끗하고 `pipelined` 에서만 유실·늦음 | 연달아 보내기(수신 칸 3개·어댑터 큐·충돌) 문제 |
| `pipelined` 에서 `skipped_by_outstanding_limit` 이 큼 | 그 레이트에서 모터 응답이 주기를 못 따라감 |
| `lost_arbitration` 이 있음 | 송신 중 졌다는 뜻 — 정상 동작에서도 나옴, `bus_error` 와 구분해서 볼 것 |

## 5. 호스트 번호 바꾸기 절차 (모터 하나씩)

### 5-1. 권장 번호표와 이유

| 다리 | 모터 번호 | 응답 번호(호스트 번호) | 보내는 프레임 (`id`  `데이터`) |
|---|---|---|---|
| 왼다리 | 1, 2, 3, 4, 5, 6 | `0x60`, `0x61`, `0x62`, `0x63`, `0x64`, `0x65` | `0x001  FF FF FF FF FF FF 60 01` … `0x006  FF FF FF FF FF FF 65 01` |
| 오른다리 | 7, 8, 9, 10, 11, 12 | `0x70`, `0x71`, `0x72`, `0x73`, `0x74`, `0x75` | `0x007  FF FF FF FF FF FF 70 01` … `0x00C  FF FF FF FF FF FF 75 01` |

- **번호가 작은 쪽이 중재에서 이깁니다.** 호스트의 명령(1~12)이 가장 작아 항상 먼저 나가고, 그 뒤에 응답들이 번호 순서(`0x70` → `0x75`)로 나옵니다. 둘이 동시에 시작해도 번호가 작은 쪽이 이기고 진 쪽은 **오류 없이** 바로 뒤에 보냅니다(지금은 같은 번호라 이 규칙이 작동하지 않음).
- 번호 순서는 보내는 순서(1→6, 7→12)와 맞춰 두었습니다. 응답이 어차피 그 순서로 오므로 가장 자연스럽습니다.
- `0x60`/`0x70` 대역을 쓴 이유: **모터 번호(1~12)나 선택자 영역과 겹치지 않기 위해서**입니다. 응답 번호가 어떤 모터의 번호와 같으면 그 모터가 응답 프레임을 *명령으로* 받을 수 있습니다(상태 바이트가 이득·토크로 해석됨). 도구와 `RobStrideBus(reply_ids=…)` 가 둘 다 거부합니다.
- 왼·오 다리는 다른 선이라 서로 만나지 않지만, 한 파일에 섞여 기록될 때 구분되도록 다르게 두었습니다.
- 매뉴얼은 호스트 번호를 1바이트로 둡니다(`F_CMD` 칸). 공장값 `0xFD` 로 되돌리는 것은 허용됩니다(`--host 0xFD`).

### 5-2. 프레임 읽는 법 — 반드시 보고 보내십시오

```
11비트 번호 : 0x007                          (= 대상 모터 7 의 번호)
데이터      : FF FF FF FF FF FF 70 01
              ^^^^^^^^^^^^^^^^^ 0~5번 바이트 = FF 여섯 개
                                 ^^ 6번 바이트 = F_CMD 자리 = 새 호스트 번호 (여기서는 0x70)
                                    ^^ 7번 바이트 = 01 (명령 9)
```
**6번 바이트는 `F_CMD` 자리입니다.** 활성화(`FC`)·정지(`FD`)·고장 해제(`FB`) 같은 명령에서는 이 자리가 반드시 `FF` 여야 하고, 다른 값이면 **다른 명령**이 됩니다 (`FD` + `F_CMD=2` 는 통신 프로토콜 전환이고 전원을 다시 넣어야 적용되어, 한때 모터 12개를 잃을 뻔했습니다).
명령 9 에서만 이 자리가 `FF` 가 아니라 **바꾸려는 값**입니다. 그래서 도구는 `--i-understand-f-cmd` 가 없으면 **프레임을 출력만 하고 보내지 않습니다**(드라이런이 기본).

### 5-3. 절차 (한 모터씩, 이 순서)

사전 조건 **[로봇]**: 로봇을 받침대에 올리고 **토크를 끈 상태**, HUPHY 를 멈춘 상태, 한 번에 한 다리, 펌웨어 `0.4.1.29` 이상(Command 12·14·15 필요 — `read` 가 응답하면 충족).

1. **기준 측정**: `host_id_tool.py read --channel canr --ids 7,8,9,10,11,12` 로 전부 `0xFD` 인지 확인, `bus_probe.py` 로 기준 JSON 저장(4-2).
2. **드라이런**: `host_id_tool.py set --channel canr --motor 7 --host 0x70` → 프레임을 눈으로 확인.
3. **전송**: `... --motor 7 --host 0x70 --i-understand-f-cmd`. 도구는 먼저 그 모터의 `0x200A` 를 읽어 **읽히지 않는 모터는 건드리지 않고**, 보낸 뒤 **모든 번호를 들으며** 300 ms 동안 나온 프레임을 전부 찍고, `0x200A` 를 다시 읽어 응답이 새 번호로 오는지 봅니다.
4. **저장**: 읽기가 `0x70` 이면 `host_id_tool.py save --channel canr --motor 7 --i-understand-flash-write`(Command 12, `7 FF FF FF FF FF FF FF F8`). `set` 에 `--save` 를 붙이면 3과 4를 이어서 합니다. **저장을 빼면 전원을 껐다 켰을 때 `0xFD` 로 돌아갈 수 있습니다**(매뉴얼 4.1.7: 단일 파라미터 쓰기는 "전원 꺼지면 사라짐"; 명령 9 자체의 저장 여부는 매뉴얼에 적혀 있지 않음 — **미확인**).
5. **전원 재투입 확인**: 그 모터의 48 V 를 5초 이상 끊었다 켜고 3초 뒤 `read` → `0x200A = 0x70`, 응답이 `0x070` 번호로 왔는지 확인. 다시 `0xFD` 면 저장이 안 된 것이니 4로 돌아가고, 그래도 안 되면 `Command 15`(파라미터 쓰기)로 `0x200A` 를 쓰고 `Command 12` 로 저장하는 길을 확인해야 합니다(도구에 아직 없음).
6. **버스 확인**: `bus_probe.py` 의 `reply_id_histogram` 에서 그 모터는 `0x70`, 아직 안 바꾼 모터는 `0xFD` 인지.
7. 다음 모터로. 종이에 모터→번호 표를 적어 두십시오.
8. 끝나면 `bus_probe.py` 를 같은 조건(레이트 표, `--param vbus` 유무)으로 다시 돌려 1의 기준과 비교(4-2 해석표).

**되돌리기**: `set --motor 7 --host 0xFD --i-understand-f-cmd --save`.
**HUPHY 쪽**: 원본 코드는 그대로 읽습니다(`data[0]`). 개선판은 `reply_ids=` 로 번호를 확정하고, 일부만 바꾼 중간 상태에서도 동작합니다(바뀌지 않은 모터는 `data[0]`).
**이 도구는 이 문서를 쓰는 시점에 실물에서 실행하지 못했습니다**(7절).

## 7. 아직 확인 못 한 것

1. **같은 응답 번호 충돌이 실제로 일어나는지.** 로그로는 가려지지 않습니다(손실 행에 시각 없음, 늦음은 2-1 로 설명되는 부분이 큼). 로봇에서 `bus_probe.py` 를 번호 같음/다름 두 상태로 재서 `bus-errors` 와 유실을 비교해야 합니다(4-2 해석표).
2. **Command 9 가 호스트 번호를 실제로 바꾸는지, 저장되는지, 응답 형식이 무엇인지.** 매뉴얼은 응답을 "Response Command 2"(모터 번호 + 64비트 식별자)로 적을 뿐이고 저장 여부는 없습니다. 가짜 모터의 동작은 이 가정으로 만든 것이라 증거가 아닙니다. 벤치 모터 1개로 먼저 확인하는 것이 안전합니다(모터 전원 복구 필요).
3. **개선판을 실제 `python-can` 위에서.** 이 컴퓨터에는 `python-can` 이 없어 `can.Message` / `can.interface.Bus` 를 흉내 낸 대역으로 시험했습니다. 쓰는 속성은 `msg.timestamp`(소켓 기반 인터페이스에서 커널 벽시계), `bus.socket`(없으면 오류 필터 설정을 조용히 건너뜀), `bus.set_filters` 입니다. 실제 버전에서의 `msg.timestamp` 값과 `stamp_fallbacks == 0` 을 로봇에서 한 번 보셔야 합니다.
4. **실제 로봇에서 개선판의 효과.** 위 숫자는 가짜 버스입니다. 실물에서 `late` 비율과 연속 늦음이 줄어드는지는 로봇에서 같은 조건으로 `latency_log` 를 다시 떠 비교해야 합니다.
5. **왕복이 주기보다 긴 경우의 오인**(2-1 한계)과, 모터 수신 칸이 3개라는 **내부 원인**(실측은 있으나 모터 내부는 못 봄).
6. **켜는 항목 세 개(`reader=True`, `max_outstanding=2`, `reply_ids`)를 켠 상태의 HUPHY 시험.** 기본값에서는 통과를 확인했지만(6-3), 켠 상태로는 돌리지 않았습니다. 켜면 스레드를 가정하지 않는 원본 시험과 부딪힙니다(HUPHY 는 건드리지 않아 고치지 않음).
7. **어댑터 차이.** 오류 프레임은 gs_usb 에서만 나옵니다. 왼다리·오른다리 어댑터가 각각 slcan 인지 gs_usb 인지는 기록 파일만으로는 모릅니다.
