# 역기전력 흡수 시험 벤치 (모터 한 개, 웹 화면)

2026-10-15. 사용자 요청: "실물 셋업에서 역기전력 흡수 테스트를 하려 한다. 3090 머신에 달린
CAN 어댑터에서 연결된 모터를 확인하고, 그 모터에 내가 임의의 각도값을 줄 수 있는 웹 화면을
만들어 달라. Kp·Kd 와 위치를 조정하고, 전류·전압·위치를 실시간 그래프로 본다."

> **이 문서를 쓴 시점에 모터는 연결되어 있지 않았습니다.** 아래의 모든 "확인했다"는 **시뮬레이션
> 모터**(`--fake`)에서 한 것입니다. 실물에서 처음 켜는 날 확인할 항목은 6절 끝의 "실물에서 아직
> 확인되지 않은 것"에 따로 모았습니다.

## 1. 무엇을 하는가

모터 한 개가 **발전기처럼** 일하는 순간(빠르게 돌다가 급하게 멈추는 순간)에는 전기를 전원 쪽으로
되밀어 넣어 전원 전압이 올라갑니다(역기전력, 영어로 back-EMF). 사용자는 이 전압을 흡수·배출하는
장치를 붙였고, 그 장치가 일하는지 보려고 합니다. 이 벤치는

* 모터에 **원하는 각도**를 주고(목표 위치), **Kp·Kd**(아래 설명)를 화면에서 바꾸고,
* 위치·속도·토크·**q축 전류**(모터를 돌리는 힘을 만드는 전류)·**전원선 전압**·**되먹임 전력**을
  실시간 그래프로 보여 주며,
* 원하면 모든 값을 CSV 파일로 기록합니다.

Kp(위치 이득, 단위 N·m/rad)는 "목표 각도에서 1 라디안 벗어나면 몇 N·m 로 되돌릴 것인가"이고,
Kd(속도 이득, 단위 N·m·s/rad)는 "속도에 비례해 얼마나 브레이크를 걸 것인가"입니다. 모터 안쪽
펌웨어가 `토크 = Kp×(목표각−현재각) + Kd×(목표속도−현재속도)` 를 계산합니다(목표속도는 0).

## 3. 실행

```bash
# 시뮬레이션 모터 (하드웨어 없이 화면을 시험)
python3 bench_server.py --fake --port 8099

# 실물 (CAN 이 올라와 있어야 함, 4절)
python3 bench_server.py --channel can0 --id 4 --model RS04 --port 8099

# 모터 번호를 모를 때: 1..127 번을 읽기 전용으로 훑는다 (5절)
python3 bench_server.py --channel can0 --model RS04 --scan
```

시작하면 접속 주소(3090 머신이면 `http://10.8.0.14:8099/`, `http://192.168.0.16:8099/`)가 출력됩니다.
다른 PC 의 브라우저로 여십시오. 포트는 `--port` 로 바꿉니다(3090 머신에서 8095~8098, 8081 은
이미 쓰는 중). 제어 주기는 `--rate`(기본 200 Hz). 3090 머신에는 파이썬 3.10 표준 라이브러리만
있으면 됩니다(`python-can`, `fastapi` 불필요).

3090 머신에 올리기: `./sync_to_3090.sh` (`emf_bench/` 와 `System_ID/rs_direct_socket.py` 를 `~/System_ID/`
아래로 복사합니다. 후자는 원격에 없어서 함께 보냅니다).

## 4. 3090 머신에서 CAN 올리기

2026-10-15 점검: 3090 머신에는 `can0` 가 **없고**(`/sys/class/net` 에 `enp6s18`, `lo`, `wg0` 뿐), CAN 커널
모듈도 올라와 있지 않습니다. `slcand`, `candump`, `cansend` 는 설치되어 있습니다. 이 머신은 가상
머신이라 **USB 어댑터를 가상머신에 넘겨(패스스루) 주어야** 보입니다. `sudo` 는 사용자의 비밀번호가
필요합니다(에이전트는 하지 않음). 어댑터 종류를 아직 모르므로 두 경우를 적습니다.

어댑터를 꽂은 뒤 `lsusb` 와 `dmesg | tail` 로 확인하십시오.

**(가) candleLight / gs_usb 계열** (`lsusb` 에 "OpenMoko / candleLight" 또는 gs_usb 로 보임)

```bash
sudo modprobe can can_raw gs_usb
sudo ip link set can0 up type can bitrate 1000000
ip -details link show can0        # state UP, bitrate 1000000 확인
```

**(나) CANable / slcan(시리얼) 계열** (`/dev/serial/by-id/...` 로 보임, 꽂는 순서에 따라 ttyACM 번호가
바뀌므로 **고유 이름**으로 엽니다 — `System_ID/can_up.py` 와 같은 이유)

```bash
sudo modprobe can can_raw slcan
sudo slcand -o -c -s8 /dev/serial/by-id/usb-XXXX can0     # -s8 = 초당 100만 비트
sudo ip link set can0 up
```

옛 `slcand` 가 붙잡고 있으면 `Input/output error` 가 납니다(`sudo pkill -x slcand` 후 재시도).
모터 쪽 통신 속도는 기본 1 Mbps 입니다(매뉴얼 MIT 통신 설명).

내리기: `sudo ip link set can0 down` (slcan 이면 `sudo pkill -x slcand` 도).

## 5. 처음 연결할 때 점검표

1. 모터 전원(48 V 계열)과 CAN 선을 연결하고, **축에 사람이 닿지 않는 상태**로 둡니다.
2. 4절대로 `can0` 를 올립니다.
3. `candump can0` 를 다른 창에 켜 두면 프레임이 오가는 것이 보입니다.
4. **모터 번호 찾기**: `python3 bench_server.py --channel can0 --model RS04 --scan`
   * 보내는 것은 **힘 0 짜리 상태 요청**(Kp=Kd=토크=0 인 MIT 프레임)과, 응답한 번호에만
     **파라미터 읽기(Command 14)로 VBUS 한 번**뿐입니다. 켜기·끄기·모드·번호·프로토콜 변경
     프레임은 보내지 않고, 끝낼 때도 끄기 프레임을 보내지 않습니다.
   * 출력 예: `id 4: mode=Reset pos=... VBUS=47.9 V (Command 14 works)`. VBUS 줄에
     "no reply" 가 나오면 펌웨어가 낮은 것입니다(7절).
   * 모델(RS03/RS04)을 모르면 둘 다 돌려 보십시오. 번호 찾기만 목적이면 모델이 틀려도 번호는
     보이지만 위치 눈금은 틀립니다.
5. 서버를 켭니다 → 브라우저 → **연결** → 위치·온도·전압이 나오는지 → 토크 꺼진 상태에서 손으로
   축을 돌려 위치 그래프가 따라오는지 확인 → 그 다음에 **토크 켜기**.
6. 처음에는 **Kp 를 낮게**(기본 10) 시작하십시오. 목표를 ±5° 단추로 조금씩 움직여 보고 올립니다.

## 6. 화면

* **연결**: 힘 0 짜리 프레임으로 상태만 읽기 시작합니다(토크 꺼짐). 이때 읽은 위치가 **원점**(목표
  슬라이더 0°)이 됩니다. 응답이 없으면 "모터 응답 없음"이 뜨고, 응답이 오는 순간 원점이 잡힙니다.
* **토크 켜기(Enable)**: 켜는 순간 **목표 위치를 방금 측정한 현재 위치로 맞춥니다.** 그래서 켠다고
  축이 튀지 않습니다(시뮬레이션에서 확인: 켠 뒤 위치 변화 0.1° 이하).
* **끄기(Disable) / `Esc` 키**: 언제든 눌립니다(입력칸에 커서가 있어도). 끄기 프레임을 3번 보냅니다.
* **고장 해제**: 고장 지우기 프레임을 보냅니다. 지운 뒤에는 다시 **토크 켜기**를 눌러야 합니다.
* **Kp / Kd / 목표 위치**: 숫자칸은 모터 프레임이 담을 수 있는 범위(RS03·RS04: Kp 0~5000, Kd 0~100,
  위치 ±720°)까지 입력되고, 슬라이더는 Kp 0~100, Kd 0~10, 목표 ±180° 입니다. 목표는 **연결 시점
  위치 기준 상대 각도**입니다. ±5°, ±30° 단추와 "현재 위치로" 단추가 있습니다.
* **그래프 5개**(표시 구간 5~60초): ① 목표 대 실제 위치 ② 속도 ③ 토크(왼쪽 축)와 q축 전류(오른쪽
  축) ④ 버스 전압과 구간 안 최소·최대 ⑤ 되먹임 전력 = 토크×속도(음수 = 전원 쪽으로 되돌림,
  `System_ID/regen_test.py` 와 같은 정의).
* **상태 칸**: 온도, 모드(Reset/Cali/Motor), 고장·경고(고장값을 비트 이름으로 풀어 줌), 제어 루프
  속도와 최근 1초 최대 간격, 잃은 프레임 수, 파라미터 읽기 응답률.
* **기록**: 켜면 `~/System_ID/data/emf_<날짜_시각>.csv`(서버가 도는 머신 기준)에 **모든 표본**을
  씁니다. 파일 이름과 행 수가 화면에 나옵니다. 열: `t_s, unix_s, pos_deg, vel_deg_s, tau_nm, temp_c,
  mode, fault, warn, target_deg, kp, kd, enabled, vbus_v, iqf_a, power_w`. 전압·전류는 그 표본에서
  읽은 값이 없으면 **빈칸**입니다(앞 값을 복사해 채우지 않음).

### 시뮬레이션에서 확인한 것 (실물 아님)

`ux_check_bench.py` 가 실제 브라우저(크로미움)로 연결 → 토크 켜기 → Kp·Kd 변경(숫자칸·슬라이더) →
목표 슬라이더 60° → +30° 단추 → 기록 켜고 끄기 → `Esc` → 고장 유발·해제 → 연결 해제를 눌러 27개
항목이 모두 통과했습니다. 스크린샷은 `ux_shots/` 에 있습니다. 시뮬레이션에서 60° 단계 이동 때 속도
409°/s, 되먹임 전력 최소 −18 W, 전압 48.0 → 49.3 V 로 보입니다(시뮬레이션 모터의 임의 모델 값이며
**실제 모터의 사양이 아닙니다**).

## 7. 전류와 전압은 어떻게 읽는가, 그리고 한계

MIT 상태 응답에는 위치·속도·토크·온도·모드·고장 깃발만 있고 **전류와 버스 전압이 없습니다.** 그래서
매 제어 주기마다 상태 요청 1개 + **파라미터 읽기(Command 14) 1개**를 보내고, 파라미터는
VBUS 와 iqf 를 번갈아 읽습니다(각각 약 100 Hz). 한 모터에 **동시에 3개를 넘기면 모터가 버리므로**
(2026-09-09 측정, `rs_direct_socket.py` 주석) 항상 2개만 보냅니다.

매뉴얼 근거(RobStride 사용자 매뉴얼, github.com/RobStride/Product_Information):

| 항목 | RS04 (`Motor_Spec/manuals/RS04_User_Manual_260713.pdf`) | RS03 (`Motor_Spec/manuals/RS03_User_Manual_261013.pdf`) |
|---|---|---|
| Command 14 프레임 | 6.17절, 인쇄 쪽 82~83 | 6.17절, 인쇄 쪽 79~80 |
| 파라미터 표 (0x7019~0x701C) | 인쇄 쪽 50~51 | 인쇄 쪽 48~49 |
| **필요 펌웨어** | **0.4.1.29 이상** | **0.3.1.41 이상** |

* 요청: 11비트 ID = `(3 << 8) | 모터번호`, Byte0~1 = 파라미터 번호(**작은 자리 먼저**), Byte2~7 = 0.
  예) 모터 4번의 VBUS = ID `0x304`, 자료 `1C 70 00 00 00 00 00 00`.
* 응답: ID 는 요청과 같고(매뉴얼 표에 "3 / 7F" 로 같게 적힘), Byte0~1 = 번호, **Byte4~7 = 값(32비트
  실수, 작은 자리 먼저)**.
* 번호(둘 다 읽기 전용 실수): **VBUS = 0x701C**(전원선 전압, V), **iqf = 0x701A**(걸러낸 q축 전류, A;
  RS04 ±90 A, RS03 ±43 A). 참고로 0x7019 mechPos(rad), 0x701B mechVel(rad/s)도 같은 표에 있습니다.
* `Motor_Spec/manuals/RS0x_User_Manual_251112.pdf`(저장소에 있는 판본)는 **옛 판본**이라 MIT 장이
  Command 11 에서 끝나고 Command 14 가 없습니다. 파라미터 표(RS04 26쪽)와 private 프로토콜의
  "Type 17 읽기" 예(27쪽, 응답 `1E 70 00 00 00 00 F0 41` = loc_kp 30.0)만 있어서, 응답의 값 위치
  (Byte4~7)는 이 예와 Command 15 표에서 **추정**한 것입니다.
* 답이 안 오면 화면은 그 채널을 **"응답 없음"** 으로 표시하고 그래프에 아무 값도 그리지 않습니다.
  토크에서 전류를 추정해 채우는 일은 하지 않습니다.

**측정의 한계**

* 전압은 **약 100 Hz 로 읽은 값**입니다. 역기전력의 **마이크로초~밀리초 단위 뾰족한 전압(스파이크)은
  잡지 못합니다.** 그 최고점이 필요하면 전원선에 **오실로스코프**를 물려야 합니다. 이 화면은 느린
  변화(수십 밀리초 이상)와 평균적인 상승을 봅니다.
* 속도는 모터가 보고하는 값이라 RS04 는 ±859°/s, RS03 은 ±1146°/s 에서 **잘립니다.** 그 이상으로
  돌면 되먹임 전력이 실제보다 작게 보입니다.
* 위치는 ±720°(±4π)에서 **한 바퀴 감겨** 처음으로 돌아옵니다. 원점이 ±720° 근처이면 그래프에
  톱니가 생깁니다.
* 토크도 모터가 전류에서 계산해 보고하는 값입니다. Kp=Kd=0 으로 힘 0 을 보낼 때 값 눈금이
  0 을 정확히 못 담아 −0.03 N·m(RS04) 정도 치우쳐 보입니다(코덱의 양자화).
* 모터 자체의 **과전압 고장은 60 V, 저전압 고장은 12 V** 입니다(매뉴얼 3.3.7절). 48 V 전원에서 흡수
  장치가 약하면 이 60 V 에서 고장이 나며 모터가 토크를 끕니다(상태 칸에 "과전압"으로 표시).

### 실물에서 아직 확인되지 않은 것

1. Command 14 응답이 위 배치(Byte4~7 실수)로 오는지 — `--scan` 의 "Command 14 works" 줄이 곧
   그 확인입니다.
2. 모터 펌웨어가 위 최소 버전 이상인지(옛 펌웨어는 응답이 없음).
3. 호스트 번호(응답 프레임의 CAN ID)가 기본 `0xFD` 인지. 상태 응답은 "ID 가 0x100 보다 작고
   Byte0 = 모터 번호"인 프레임으로 알아봅니다.

## 8. 있는 것과 **없는 것** (사용자가 지시하지 않은 안전장치는 넣지 않았습니다)

* **있다**: 끄기 단추와 `Esc`, 고장 해제 단추, 프로세스가 정상 종료할 때(`Ctrl+C`, `SIGTERM`) 모터에
  끄기를 5번 보내고 소켓을 닫음(`rs_direct_socket.Motor.close` 와 같은 순서).
* **없다**: 자동 끄기, 시간 제한, 토크를 자동으로 빼는 감시 장치, Kp·Kd·목표의 사용자 쪽 상한,
  목표 이동 속도 제한(목표는 한 번에 바로 갑니다). 값을 막는 것은 **모터 프레임이 담을 수 있는
  범위**뿐입니다(그 밖의 값은 코덱이 가장자리 값으로 잘라 보냄. 서버도 같은 범위로 잘라 화면에
  "잘림"을 알립니다).
* 주의: `kill -9` 로 죽이거나 서버 컴퓨터가 죽으면 끄기가 나가지 않고 **모터가 마지막 명령을 계속
  붙듭니다.** 모터 자체에 "CAN 명령이 일정 시간 없으면 Reset" 기능(파라미터 0x7028 canTimeout,
  기본 0 = 꺼짐)이 있으나 이 벤치는 건드리지 않습니다.

## 9. F_CMD 규칙 (모터를 못 쓰게 만들 뻔한 사고에서)

"모두 0xFF" 제어 프레임은 `FF FF FF FF FF FF F_CMD 명령` 모양이고 `F_CMD`(Byte6)가 **0xFF 일 때만**
기본 동작입니다: `0xFC` 켜기, `0xFD` 끄기, `0xFB` 고장 지우기. **다른 값이면 같은 명령 바이트가 다른
명령**이 됩니다 — `0xFC` + 값 = 제어 모드 변경, `0xFD` + 값 = **통신 프로토콜 변경**(전원을 다시
넣으면 적용되어 모터와 통신이 끊김; 모터 12개가 거의 먹통이 될 뻔했음), `0xFB` + 값 = 고장값 조회.
그래서 이 벤치는 제어 프레임을 `emf_frames.control_frame()` 한 곳으로만 만들고(F_CMD 를 0xFF 로
고정), 예외는 문서화된 **고장값 조회**(`0xFB` + F_CMD `0x00`, 읽기 전용; 고장 깃발이 켜지는 순간 한 번
보냄) 하나뿐입니다. `test_frames.py` 가 이를 검사합니다. 새 프레임을 추가할 때는 `emf_frames.py` 첫머리의
설명부터 읽으십시오.

## 10. 영상 기록 — 이 시험은 면제 (사용자 결정 2026-10-15)

프로젝트 규칙은 "실물 모터에 힘이 들어가는 모든 순간은 영상으로 남긴다" 이지만, 사용자가 이 벤치(RS04 4번 단독,
역기전력 흡수 시험)에 한해 "역기전력 테스트만 하는 것이라 영상 체크는 패스" 라고 정했습니다. 그래서 이 시험에서는
녹화 확인 없이 토크를 켭니다. 다른 실물 구동(다리·로봇)에는 원래 규칙이 그대로 적용됩니다.
CSV 의 `unix_s` 열은 나중에 다른 기록과 시각을 맞출 때 씁니다.
